The End-to-End Statistical Pipeline

FeatureEngineer

⚙ Kailash Engine

FeatureEngineer has two methods. generate(df, schema, strategies=[...]) creates candidate features from the columns a FeatureSchema declares — "temporal" (month, day-of-week, hour from a datetime) and "interactions" (pairwise products of numeric fields). select(data, generated, target=..., top_k=...) then ranks the candidates (by tree-model importance) and keeps the best. It does not replace domain knowledge — it amplifies it: you decide which raw fields go into the schema, and you sanity-check what it selects. (The engine is marked experimental in kailash-ml 2.2 and prints an ExperimentalWarning.) 

import polars as pl
from kailash_ml import FeatureEngineer, FeatureField, FeatureSchema
from shared.mlfp02.ex_8 import load_hdb_resale

df = (
    load_hdb_resale()                    # HDB file + parsed transaction_date
    .with_row_index("id")
    .with_columns(pl.col("transaction_date").cast(pl.Datetime))
)
schema = FeatureSchema(
    name="hdb",
    entity_id_column="id",
    features=[
        FeatureField("floor_area_sqm", "float64"),
        FeatureField("lease_commence_date", "int64"),
        FeatureField("transaction_date", "datetime"),
    ],
)

fe = FeatureEngineer(max_features=10)
gen = fe.generate(df, schema, strategies=["temporal", "interactions"])
print([c.name for c in gen.generated_columns])

best = fe.select(gen.data, gen, target="resale_price", top_k=3)
print(best.selected_columns)
['floor_area_sqm_x_lease_commence_date', 'transaction_date_dow', 'transaction_date_hour', 'transaction_date_month']
['floor_area_sqm_x_lease_commence_date', 'floor_area_sqm', 'transaction_date_month']

Sanity-check the candidates: transaction_date_hour and transaction_date_dow are meaningless here, because the file records only the sale month (every date is the 1st at midnight). The engine generated them mechanically; your domain knowledge is what throws them out.

FeatureStore

⚙ Kailash Engine

FeatureStore (from kailash_ml.features) persists feature tables through a DataFlow database and serves them with point-in-time correctness: get_features(schema, timestamp=T) returns only rows stamped at or before T — never values from the future. Writing a feature group with materialize also returns a lineage hash that identifies exactly which data produced the stored features. The calls are asynchronous.

One detail trips people up: the store needs the FeatureSchema from kailash_ml.features (the top-level kailash_ml.FeatureSchema used by FeatureEngineer above is a different type the store rejects). Exercise 8's helpers in shared.mlfp02.ex_8 wrap that wiring for you. 

import asyncio
from datetime import datetime
from pathlib import Path

from shared.mlfp02.ex_8 import (
    build_schema_v1, compute_v1_features, create_feature_store,
    load_hdb_resale, materialize_features, validate_v1_features,
)

# Validated features: storey midpoint, remaining lease, price per sqm
df, _ = validate_v1_features(compute_v1_features(load_hdb_resale()))
schema = build_schema_v1()             # a kailash_ml.features.FeatureSchema

# An absolute path for the SQLite file keeps DataFlow from losing it
STORE_URL = f"sqlite:///{Path('mlfp02_ex8_features.db').resolve()}"


async def store_then_read(when):
    fs = create_feature_store(STORE_URL)        # FeatureStore(DataFlow(...))
    result = await materialize_features(fs, schema, df)
    snapshot = await fs.get_features(schema, timestamp=when)
    return result, snapshot


result, snap = asyncio.run(store_then_read(datetime(2023, 1, 1)))
print(f"Stored {result['row_count']:,} rows, lineage {result['lineage_hash'][:16]}")
print(f"Rows visible on 1 Jan 2023: {snap.height:,}")
print(snap.columns)
Stored 46,614 rows, lineage sha256:…
Rows visible on 1 Jan 2023: 37,017
['transaction_id', 'floor_area_sqm', 'remaining_lease_years', 'storey_midpoint', 'price_per_sqm']

The snapshot holds exactly the 37,017 validated sales dated on or before 1 January 2023; the 9,597 later sales are invisible to anything trained "as of" that date. (The lineage hash depends on the exact rows stored, so yours is printed in full rather than quoted here.) Writing ~46,600 rows takes a few minutes. In Jupyter or Colab, use await store_then_read(...) instead of asyncio.run(...).

🔵 Theory

Point-in-time correctness is critical for any time-series model. If your training data for January includes features computed from February data, your model learns from the future — and performs worse in production where the future is unknown. The store enforces the cut-off on retrieval; you still have to compute each feature from past data only (Exercise 8.3 shifts its town-level rolling medians by one month for exactly this reason).

Worked Example: Option A — HDB Resale Valuation

📝 Goal

Explain HDB resale prices from floor area, storey and remaining lease: validate the data, explore it, store the features, fit a regression, test each predictor, and write a recommendation a non-specialist can act on. These are the steps Exercise 8 guides you through, and the numbers match the lesson slides.

Step 1 — Load, validate and profile.

Exercise 8's helpers derive the features (storey midpoint from storey_range, remaining lease from the sale year and lease_commence_date, price per sqm) and then apply value rules a dtype check cannot express: a lease cannot start after the sale, the remaining lease must be within 99 years, and prices must be plausible (the raw file contains sentinel values such as 10 and 9,000,000).

The model is the Lesson 2.5 normal equations, wrapped in two Exercise 8 helpers: prepare_design_matrix builds $[1, X]$ and drops nulls; fit_ols returns coefficients, standard errors, $t$, $p$, $R^2$ and $F$.

$H_0$: "this predictor has no effect, holding the others fixed". It is rejected decisively for floor area and not rejected for storey ($p = 0.54$) or remaining lease ($p = 0.84$). The 95% CI for the area effect is $9{,}096 \pm 1.96 \times 19.2$, i.e. about 9,060 to 9,130 per square metre.

Step 6 — Report findings.
Summary: In 46,614 validated HDB resales, floor area explains about 83% of the variation in price. Each extra square metre adds about SGD 9,100 (95% CI SGD 9,060–9,130). Once size is accounted for, we found no measurable effect of storey or remaining lease in this data. Limitations: one model of three predictors; town and flat type were left out; 3,536 records with impossible dates or prices were removed. Recommendation: value a flat first by its size; treat storey and lease adjustments as unproven until a model that includes location confirms them.

Every sentence is readable without statistics training, every number comes from the output above, and the limitations are stated rather than hidden.

Common Mistakes

⚠ Mistake 1: Feature leakage from the future

If you compute a 6-month rolling mean and include the current or future months in the window, your model sees the future. Compute rolling features from strictly earlier periods (shift before you roll, as Exercise 8.3 does) and retrieve training data with FeatureStore's point-in-time get_features(schema, timestamp=...).

⚠ Mistake 2: Engineering features without domain rationale

Creating 100 random interactions and selecting the ones that correlate with the target is p-hacking with extra steps. Every feature should have a domain reason.

⚠ Mistake 3: Reporting p-values without effect sizes

"Floor area is significant ($p < 0.001$)" tells the reader nothing useful. "Each additional square metre adds about SGD 9,100 to the price (95% CI SGD 9,060–9,130)" tells them what to do.
