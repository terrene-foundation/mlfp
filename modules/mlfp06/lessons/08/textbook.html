Lesson 6.8 Capstone — Full Production Platform

This is the culmination of the six-module programme. You deploy a complete, governed AI system via Nexus — one handler registered on the API, CLI and MCP channels at once. The system integrates the Kailash stack you have built up: kailash-align for the fine-tuned adapters, Kaizen for the agent, PACT for governance, Nexus for deployment with signed-token authentication, and kailash-ml's DriftMonitor for production monitoring. It is the architecture of a real production AI system, small enough to run on your laptop. And it is yours.

Why This Matters

Consider a bank deploying an internal question-answering assistant. It must serve three audiences: staff through an intranet portal (REST API), the operations team through scripted batch jobs (CLI), and AI copilots through MCP tool calls. Each caller must be authenticated, and what the assistant may do must depend on who is asking — a front-line user may get answers, but only model operators may update the model and only auditors may read the audit log. Every answer must be logged for audit, and the system must notice when the questions it receives stop looking like the ones it was validated on.

Building this from scratch means writing an API server, a CLI parser, an MCP server, an auth layer, a rate limiter, a logging pipeline, and a drift detector — all as separate codebases that need to stay in sync. Or you can use Nexus, which gives you all three channels from a single handler, put PACT governance inside that handler, and run DriftMonitor over the traffic. That is what you build today — the same system as Exercise 8.

Every box in this diagram maps to a lesson you have already completed. The capstone connects them into one running system. The scaffolding is minimal — you are connecting proven components, but you write the connections yourself.

Core Concepts

Nexus: One Codebase, Three Interfaces

Nexus is Kailash's multi-channel deployment platform. You register a handler — a plain Python function with app.handler_extract(name, func), or a built workflow with app.register(name, workflow.build()) — and Nexus exposes it on every channel: an API endpoint (POST /workflows/<name>/execute), a CLI command and an MCP tool. You write the logic once; Nexus handles serialisation, transport and error formatting for all three channels.

Foundations

Think of Nexus as a universal adapter. Your code speaks one language. Nexus translates it for three different audiences: web clients (API), terminal operators (CLI), and AI agents (MCP). Without Nexus, you would maintain three separate interface layers that inevitably drift apart.

Authentication and Authorisation (RBAC)

Authentication answers "who are you?" — here via a signed JWT. Authorisation answers "what are you allowed to do?". Nexus handles authentication through a plugin, NexusAuthPlugin, which verifies the token (missing or forged tokens get HTTP 401 before your code runs) and puts the verified user, including its roles claim, on request.state.user.

Authorisation is where PACT comes in. The capstone maps the role claim onto one of three governance tiers, each a role in the capstone org with its own envelope (Lesson 6.7): qa (public clearance, $1, may only answer and search), admin (confidential, $10, may also update the model, view metrics and monitor drift) and audit (secret, $50, may also read the audit log and generate reports). Inside the handler, engine.verify_action decides each request. The role always comes from the signed token — a role field in the request body is ignored, so a caller cannot promote itself.

Plugins and Middleware: Authentication, Rate Limiting, CORS

Nexus adds cross-cutting behaviour in two ways: constructor options and plugins (app.add_plugin(...)). The capstone uses both:

  • Authentication — NexusAuthPlugin(jwt=JWTConfig(...)) verifies HS256 tokens. The signing secret comes from the environment (MLFP_JWT_SECRET), never from source code.
  • Rate limiting — the same plugin takes rate_limit=RateLimitConfig(requests_per_minute=10, burst_size=5); over the limit, callers get HTTP 429. The limiter counts requests per client whether or not they carry a valid token, so it also absorbs floods of unauthenticated calls. (The constructor's own rate_limit is set to None so the limit is configured in one place.)
  • CORS (Cross-Origin Resource Sharing) — Nexus(cors_origins=[...]) controls which web origins a browser may call the API from. An allowed origin is echoed in Access-Control-Allow-Origin; any other origin gets no such header. Allow-list your intranet domain; never use * in production. One limitation of the installed release: the JWT check runs before CORS, so a browser's pre-flight OPTIONS request (which carries no token) is answered with 401. Server-to-server calls are unaffected; a browser front-end needs the pre-flight handled in front of Nexus.
  • Logging — every governed request also leaves records in the tier supervisor's hash-chained audit log (Lesson 6.7), which is the evidence an auditor reads.

Production Monitoring with DriftMonitor

A system validated on one population of inputs may behave poorly when the inputs change. DriftMonitor (from Lesson 3.8) compares a window of current data with a stored reference window, column by column, using three statistics: the Population Stability Index (PSI), the Kolmogorov–Smirnov (KS) test and the Jensen–Shannon divergence (JSD). What you feed it decides which kind of drift you catch:

Drift typeColumn you monitorExample
Input (feature) driftA numeric feature of each requestThe capstone monitors question length: exam-style questions are much longer than the short factual questions the assistant was validated on
Output driftA numeric feature of each responseAnswer length, or a model score, shifting over time
Data qualityNot DriftMonitor's jobMissing or invalid fields are caught by schema and validation checks at ingestion (Module 1)
Theory

Population Stability Index (PSI) quantifies how much a distribution has shifted. A common rule of thumb: below 0.1 is stable, 0.1–0.25 is a moderate shift worth investigating, above 0.25 is a significant shift. The capstone alerts at 0.2, DriftMonitor's default psi_threshold. The formula compares the expected proportion $e_i$ (reference data) against the actual proportion $a_i$ (current data) across $k$ bins:

$$ \text{PSI} = \sum_{i=1}^{k} (a_i - e_i) \cdot \ln\!\left(\frac{a_i}{e_i}\right) $$
$a_i$ — actual proportion in bin $i$ $e_i$ — expected proportion in bin $i$ $k$ — number of bins (10-20)

Mathematical Foundations: System Reliability

A production system composed of $n$ sequential components, each with independent availability $p_i$, has overall availability:

$$ A_{\text{system}} = \prod_{i=1}^{n} p_i $$
$p_i$ — availability of component $i$ $n$ — number of components in series

If each of 6 components (training pipeline, data store, agent, governance, Nexus, drift monitor) has 99.5% availability, the system availability is $0.995^6 \approx 0.970$ — only 97%. This is why production systems need health checks, retries, and graceful degradation. Nexus's middleware provides the first layer of defence; DriftMonitor provides the continuous validation.

Advanced

For higher availability, components can be deployed with redundancy. If a component has two independent replicas, each with availability $p$, the redundant availability is $1 - (1 - p)^2$. Two replicas at $p = 0.995$ yield $1 - 0.005^2 = 0.999975$ per component. Kubernetes or cloud auto-scaling implements this transparently for Nexus services.

Worked Example: Deploying the Governed Capstone Assistant

Goal

Deploy the governed capstone question-answering agent from Exercise 8 via Nexus. One handler is registered on all three channels; callers authenticate with signed JWTs, the role claim selects a PACT governance tier, requests are rate-limited and CORS-restricted, and a DriftMonitor watches the incoming questions. The agent answers on the local Ollama model (OLLAMA_CHAT_MODEL), so nothing leaves your machine.

Step 1 — Rebuild the governed stack.

compile_capstone_governance() loads the capstone org YAML, builds the GovernanceEngine and applies its clearances and envelopes. build_capstone_stack(engine) attaches a full five-dimension envelope to each tier's role address and builds one GovernedSupervisor per tier. 

from shared.mlfp06.ex_8 import (
    build_capstone_stack, compile_capstone_governance, handle_qa,

engine, _loaded = compile_capstone_governance()
agents_by_role, tiers = build_capstone_stack(engine)
for t in tiers:
    print(f"{t.role:<6} {t.address}  ${t.budget_usd:>4.1f}  {t.clearance:<12} {t.tools}")
# qa     D1-R1-T1-R1  $ 1.0  public       ['generate_answer', 'search_context']
# admin  D1-R1-T2-R1  $10.0  confidential ['generate_answer', 'search_context', 'update_model', 'view_metrics', 'monitor_drift']
# audit  D1-R1-T3-R1  $50.0  secret       ['generate_answer', 'search_context', 'view_metrics', 'access_audit_log', 'generate_report']
Step 2 — Create the platform: authentication, rate limit, CORS. 
import os
import secrets

from kailash.trust.auth.jwt import JWTConfig
from kailash.trust.rate_limit.config import RateLimitConfig
from nexus import Nexus, NexusAuthPlugin

# The signing secret comes from the environment; a random per-run secret is
# only acceptable for a local demo (tokens die with the process).
jwt_config = JWTConfig(
    secret=os.environ.get("MLFP_JWT_SECRET") or secrets.token_urlsafe(48),
    algorithm="HS256",
)

app = Nexus(
    api_port=8000,
    rate_limit=None,                          # configured on the plugin below
    cors_origins=["https://intranet.example.sg"],
    enable_durability=False,
)
app.add_plugin(NexusAuthPlugin(
    jwt=jwt_config,
    rate_limit=RateLimitConfig(requests_per_minute=10, burst_size=5),
))
Step 3 — Register one governed handler for all three channels.

The handler takes the role from the verified token, never from the request body. handle_qa refuses a role with no tier, runs engine.verify_action for the tier's address, and only then runs the tier's GovernedSupervisor with the Kaizen agent on Ollama. A governance refusal comes back as a normal response with "blocked": True and the verdict — not as an HTTP error. 

from starlette.requests import Request

async def serve_qa(question: str, request: Request) -> dict:
    user = request.state.user                       # set by the JWT plugin
    role = next((r for r in user.roles if r in agents_by_role), "")
    result = await handle_qa(question, role=role,
                             agents_by_role=agents_by_role, engine=engine)
    result["user"] = user.user_id
    return result

app.handler_extract("capstone_serve_qa", serve_qa,
                    description="Governed capstone QA (role from JWT claim)")
# API: POST /workflows/capstone_serve_qa/execute
# The same handler is also registered as a CLI command and an MCP tool.
Step 4 — Test the API channel in-process.

httpx.ASGITransport sends real HTTP requests to the app without opening a port, so the tests run anywhere. Tokens are issued with the same JWTConfig; the forged token is signed with a different secret. 

import httpx
from kailash.trust.auth.jwt import JWTValidator

issuer = JWTValidator(jwt_config)
qa_token = issuer.create_access_token("alice", roles=["qa"])
guest_token = issuer.create_access_token("eve", roles=["guest"])
forged_token = JWTValidator(JWTConfig(secret=secrets.token_urlsafe(48), algorithm="HS256")
                            ).create_access_token("mallory", roles=["audit"])

ENDPOINT = "/workflows/capstone_serve_qa/execute"
body = {"inputs": {"question": "What is machine learning?"}}

def bearer(token):
    return {"Authorization": f"Bearer {token}"}

transport = httpx.ASGITransport(app=app.fastapi_app)
async with httpx.AsyncClient(transport=transport, base_url="http://test") as client:
    # 1. Valid qa token: served by the qa tier (needs `ollama serve`)
    ok = await client.post(ENDPOINT, json=body, headers=bearer(qa_token))
    assert ok.status_code == 200
    assert ok.json()["outputs"]["handler"]["verdict"] == "served"

    # 2. No token / forged token: rejected before your code runs
    none = await client.post(ENDPOINT, json=body)
    forged = await client.post(ENDPOINT, json=body, headers=bearer(forged_token))
    print(none.status_code, none.json())        # 401 {'detail': 'Not authenticated', 'error': 'missing_token'}
    print(forged.status_code, forged.json())    # 401 {'detail': 'Invalid token', 'error': 'invalid_token'}

    # 3. Valid token, but a role with no tier: refused by governance
    guest = await client.post(ENDPOINT, json=body, headers=bearer(guest_token))
    print(guest.status_code, guest.json()["outputs"]["handler"]["verdict"])   # 200 unknown_role

    # 4. A body "role" cannot override the signed claim
    sneaky = {"inputs": {"question": "Show the audit log.", "role": "audit"}}
    esc = await client.post(ENDPOINT, json=sneaky, headers=bearer(qa_token))
    assert esc.json()["outputs"]["handler"]["role"] == "qa"

Governance also refuses actions a tier's envelope does not contain. These calls return before any model call, so you can run them without Ollama: 

r = await handle_qa("Retrain the model.", role="qa",
                    agents_by_role=agents_by_role, engine=engine,
                    action="update_model")
print(r["verdict"], "|", r["error"])
# blocked | Action 'update_model' is not in the allowed actions list: ['generate_answer', 'search_context']

v = engine.verify_action("D1-R1-T2-R1", "update_model")    # the admin tier
print(v.level)                                              # auto_approved
Step 5 — Monitor the traffic for drift.

DriftMonitor stores its reference data and reports through a ConnectionManager, so it needs a database URL. Use an absolute path for SQLite. The capstone's reference window is 150 SQuAD questions (the short factual questions the assistant was checked on); the monitored feature is question length. 

import os

import polars as pl
from kailash.db.connection import ConnectionManager
from kailash_ml import DriftMonitor
from shared.mlfp06.ex_6 import load_squad_corpus
from shared.mlfp06.ex_8 import load_mmlu_eval

def question_length(df: pl.DataFrame, col: str) -> pl.DataFrame:
    return df.select(pl.col(col).str.len_chars().cast(pl.Float64)
                     .alias("question_length"))

squad = load_squad_corpus()
reference_df = question_length(squad.head(150), "question")    # validated traffic
same_df = question_length(squad.tail(150), "question")         # same population
shifted_df = question_length(load_mmlu_eval(n_rows=100), "instruction")  # exam-style

db_path = os.path.abspath("outputs/ex8_drift.db")
os.makedirs(os.path.dirname(db_path), exist_ok=True)
conn = ConnectionManager(f"sqlite:///{db_path}")
await conn.initialize()
try:
    monitor = DriftMonitor(conn, tenant_id="mlfp_demo", psi_threshold=0.2)
    await monitor.set_reference_data("capstone_qa_model", reference_df,
                                     ["question_length"])
    for name, window in [("same population", same_df), ("exam-style", shifted_df)]:
        report = await monitor.check_drift("capstone_qa_model", window)
        feature = report.feature_results[0]
        print(f"{name:<16} PSI={feature.psi:.3f}  KS p={feature.ks_pvalue:.3g}  "
              f"severity={report.overall_severity}  drift={report.overall_drift_detected}")
finally:
    await conn.close()

Expect a PSI far above the 0.2 threshold for the exam-style window (those questions are several times longer) and a much lower value for the second SQuAD sample. Read overall_drift_detected together with the statistics: the report combines PSI, KS and JSD (feature.statistics_used), and on windows of only 150 rows the KS test can fire on sampling noise alone. Exercise 8.4 also mixes the two populations in steps (0%, 5%, … 60% exam-style) to show how quickly the PSI crosses the threshold.

The platform is now live on the API channel and registered on the CLI and MCP channels. Every audience shares the same handler, the same governance tiers and the same audit trail.

Debugging Agent Reasoning Chains

When an agent returns an unexpected result, look at what it actually did. Two records are available. The supervisor's audit log shows the governed steps (started, completed, failed, held) with their cost. The course's LLMObservatory captures an agent run event by event — every model turn and tool call — so you can see which tools were called, in what order, and whether the agent got stuck repeating itself. 

from shared.mlfp06._ollama_bootstrap import make_delegate
from shared.mlfp06.diagnostics import LLMObservatory
from shared.mlfp06.ex_5 import build_tool_registry, load_hotpotqa, make_tools

# 1. Governed steps of the capstone qa tier (after a handle_qa call)
for rec in agents_by_role["qa"].audit.to_list():
    print(rec["timestamp"], rec["record_type"], rec["action"], rec["details"].get("cost"))

# 2. Event-level trace of a tool-using agent (the Exercise 5 ReAct set-up)
delegate = make_delegate(tools=build_tool_registry(make_tools(load_hotpotqa())))
obs = LLMObservatory(run_id="capstone_debug")
trace = await obs.agent.capture_run(delegate, "Which film came out first?",
                                    run_id="debug_1")
print(obs.agent.tool_usage("debug_1"))     # tool, calls, errors, mean_latency_ms, total_cost_usd
print(obs.agent.detect_loops("debug_1"))   # the same call repeated = a stuck agent
obs.agent.plot_trace("debug_1")            # step-by-step timeline (plotly figure)
Common pitfall

Traces are verbose. Start from tool_usage (one row per tool) and detect_loops (empty when the agent never repeated a call), and open the full timeline only when those point at a problem. In production, store traces and audit records in a structured log, not on stdout.

Testing Agents: Automated Validation

Agent testing is fundamentally different from function testing. A function returns the same output for the same input. An agent may take different reasoning paths each time. Split the suite in two. Governance tests are deterministic: a refused request never reaches the model, so the verdict is exact and the tests run without Ollama. Behavioural tests call the model and assert properties of the result (served, non-empty, logged) rather than exact text. This suite mirrors the Exercise 8.4 harness; the first five tests pass on the installed stack without a model. 

import pytest
from shared.mlfp06.ex_8 import build_capstone_stack, compile_capstone_governance, handle_qa


@pytest.fixture(scope="module")
def stack():
    engine, _ = compile_capstone_governance()
    agents_by_role, _tiers = build_capstone_stack(engine)
    return engine, agents_by_role


# Governance tests: refused before any model call, so they run without Ollama
@pytest.mark.asyncio
@pytest.mark.parametrize("role, action, expected", [
    ("invalid_role", "generate_answer", "unknown_role"),
    ("qa", "update_model", "blocked"),
    ("qa", "access_audit_log", "blocked"),
    ("admin", "access_audit_log", "blocked"),
])
async def test_governance_refuses(stack, role, action, expected):
    engine, agents_by_role = stack
    r = await handle_qa("Any question", role=role, agents_by_role=agents_by_role,
                        engine=engine, action=action)
    assert r["blocked"] is True and r["verdict"] == expected


def test_tiers_allow_their_own_actions(stack):
    engine, _ = stack
    assert engine.verify_action("D1-R1-T2-R1", "update_model").allowed      # admin
    assert engine.verify_action("D1-R1-T3-R1", "access_audit_log").allowed  # audit


# Behavioural test: needs `ollama serve` — asserts properties, not exact text
@pytest.mark.asyncio
async def test_qa_tier_answers_and_logs(stack):
    engine, agents_by_role = stack
    r = await handle_qa("What is the capital of France?", role="qa",
                        agents_by_role=agents_by_role, engine=engine)

Common Mistakes

Mistake 1: Skipping auth in development

"I'll add auth later" is how production systems ship without auth. Configure authentication from day one, even in development. Issue test tokens with different roles from the same JWTConfig. Adding NexusAuthPlugin is a few lines; there is no excuse for deferring it.

Mistake 2: No drift monitoring

A model deployed without monitoring is a time bomb. The questions users ask change — a new product, a new regulation, a new kind of user — and an assistant validated on one population quietly degrades on another. DriftMonitor is not optional — it is the feedback loop that tells you when the traffic no longer looks like what you tested.

Mistake 3: Testing only the happy path

Your API returns 200 for valid requests — great. But does it return 401 for a missing or forged token? Does a valid token with the wrong role come back "blocked": true? Does the limiter answer 429? Does a role field in the body get ignored? Test every refusal path. The refusal paths are what keep a production system safe.

Mistake 4: Forgetting the CLI and MCP channels

Nexus registers the handler on three channels. The exercise tests the API channel in-process; before production, exercise the CLI (how batch jobs will consume the service) and MCP (how AI agents will consume it) too, and check that each channel authenticates its callers. If you only test the REST API, you are testing one third of your deployment surface.
