Speaker Notes — Lesson 6.6 Multi-Agent Orchestration and MCP

Total time: ~90 minutes  ·  12 slides  ·  ~7 min per slide average

Single agents compose into teams. The design payload: four composition patterns, memory as a four-type taxonomy, and the two protocols that make agents interoperable — MCP (tools) and A2A (tasks). The discipline point that ties it together: inter-agent communication is structured — typed Signatures in, typed fields out — never free-form text. The security slide is not optional garnish; multi-agent systems leak across agents by default unless you design the boundaries.

Slide 1~2 minTitle

Multi-Agent Orchestration and MCP

Open with the outcome: "Build a multi-agent ML pipeline and an MCP server. 6.5 built one agent; today we compose several — and give them a protocol to talk to the world."

→ "The four ways agents compose."
Slide 2~7 minFour patterns

Four multi-agent patterns

Walk the table. Supervisor-worker: one agent delegates to specialists — complex tasks with sub-problems. Sequential: output of one feeds the next — pipeline stages. Parallel: run simultaneously, aggregate — independent sub-tasks. Handoff: transfer to a specialist on topic change — multi-domain queries.

"The exercise series builds three of these: 6.1 is parallel fan-out, 6.2 is sequential, 6.3 adds an LLM router — the handoff pattern. Name the pattern before you build it; each has its own failure modes."

→ "The patterns, drawn."
Slide 3~6 minThree patterns picture

Three orchestration patterns

Walk the figure: supervisor-worker with its delegation arrows, sequential as a straight chain, parallel as a fan. "Sequential accumulates context — each stage sees the previous stage's work. Parallel accumulates perspective — each worker sees the same input, and the supervisor reconciles. Choose by whether the sub-tasks depend on each other."

→ "Who watches the workers? Budgets."
Slide 4~6 minDelegation budgets

Supervisors delegate with budgets

Walk the figure: the supervisor hands each specialist a task and a budget. "Delegation without a budget is a blank cheque — 6.5's turn ceilings apply to every agent you spawn. Each specialist runs inside its own envelope; the supervisor accounts for the total. This is 6.7's budget cascading, previewed in agent form."

→ "The pipeline, in code."
Slide 5~8 minFan-out, fan-in

Multi-agent pipeline: fan-out, fan-in

Walk the code. Three specialists from build_specialists() — factual, semantic, structural — each a BaseAgent with its own typed Signature. The fan-out: asyncio.gather runs all three concurrently on the same document and question.

Then the fan-in — read the comment: "The supervisor sees structured outputs, not free text: factual_claims, main_themes, key_entities, extracted by each specialist's Signature. This is the discipline point of the whole lesson: agents exchange typed fields, not paragraphs. Free-form text between agents is how errors propagate invisibly."

Read the footer: "Exercise 6.1 on SQuAD passages. Sequential (6.2) chains stages instead; 6.3 adds an LLM router that hands each query to the right specialist."

→ "What do agents remember?"
Slide 6~7 minAgent memory

Agent memory

Walk the four types with their course homes. Short-term: the current conversation — a sliding window (Ex 6.5) or Kaizen's BufferMemory(max_turns=...). Long-term: persistent across sessions — a fact store with recall in the exercise, a vector DB in production. Entity: structured — people, places, concepts; a mini knowledge graph. Shared: across agents — insights one agent leaves for others, via Kaizen's SharedMemoryPool (write_insight / read_relevant).

"Four scopes, four mechanisms. The common bug is using short-term memory for a long-term job — context windows are not archives."

→ "MCP — the tool protocol."
Slide 7~8 minMCP server

MCP — Model Context Protocol

Walk the code. MCPServer(name="mlfp06-analysis-server", transport="stdio"). The decorator: @server.tool() — "note the parentheses: it's a decorator factory; without them nothing registers." The function's type hints and docstring become the tool's published JSON schema.

Read the teal box: "Clients discover tools with the JSON-RPC tools/list method and invoke them with tools/call; Exercise 6.4 does both through a real MCP client. The tool you write once is callable by any MCP-speaking agent — that's the point of a protocol."

→ "The bigger picture."
Slide 8~5 minMCP picture

MCP: a universal protocol for LLM-tool integration

Walk the figure: hosts, clients, and servers — the LLM host talks to any number of tool servers through one protocol. "Before MCP, every agent framework had its own tool format. MCP is the socket standard: write the tool once, any compliant host can use it. Your corpus search from the last slide works in this course's harness and in any MCP client, unchanged."

→ "And agents talking to agents: A2A."
Slide 9~6 minA2A

A2A protocol

Walk the two records from kaizen.nodes.ai.a2a. A2AAgentCard — who an agent is: agent_id, agent_name, agent_type, version, primary and secondary capabilities. A2ATask — what's being asked: name, description, assigned_to, delegated_by, requirements, constraints, success criteria, and a state lifecycle.

"Capability cards let a router match tasks to agents — Exercise 6.3's router works on exactly this idea. The pattern repeats: structured identity, structured task, structured result."

→ "Architecture and security."
Slide 10~8 minArchitecture and security

Architecture and security considerations

Walk the six bullets in two groups. Architecture: modularity — one narrow Signature per specialist, so you can swap or test an agent without touching the rest; load balancing — several instances of a busy specialist, with independent workers parallelised by asyncio.gather; dynamic agent creation — a supervisor spawns a specialist only when a task needs it, inside its own budget and envelope.

Security: data isolation — agents with different access levels must not leak data; mask identifiers before text crosses agents. Injection defence — keep data separate from instructions and limit each agent's tools; "keyword filters are beaten by paraphrase — Exercise 6.5 shows a keyword guard failing live." Audit trail — log every inter-agent message for compliance. "6.7 turns these from guidelines into code."

→ "Common mistakes."
Slide 11~5 minMistakes

Common mistakes

Walk the three. One: too many agents — start with 2–3; every agent is a boundary to secure and a trace to read. Two: free-form inter-agent communication — use structured schemas; paragraphs between agents are unparseable, untestable, and leak-prone. Three: no security boundaries — prevent cross-agent data leakage by design, not by hope.

→ "Recap and bridge."
Slide 12~3 minRecap

What you can now do

Walk the checklist: implement supervisor-worker, sequential, and parallel patterns; build an MCP server; configure agent memory across the four types; and apply security to multi-agent systems. Tease 6.7: "Who's allowed to do what — AI Governance Engineering. PACT D/T/R, operating envelopes, budget cascading."
