Lesson 6.7 AI Governance Engineering

Governance is not a committee discussion or an ethics position paper. It is code — access controls that deny unauthorised access, operating envelopes that restrict agent behaviour, budget cascading that prevents runaway costs, and audit trails that prove compliance. Today you implement all four with PACT: D/T/R addressing, GovernanceEngine, GovernedSupervisor, and the five-dimension ConstraintEnvelopeConfig. The result: a multi-agent system where every action is checked against an attached envelope, every budget is enforced, and every decision is logged. You will also learn the one default that catches people out: in the installed PACT release, a role with no envelope is allowed to do anything.

Why This Matters

Financial regulators expect firms to be accountable for AI-driven decisions that affect customers — in Singapore, the Monetary Authority's FEAT principles (Fairness, Ethics, Accountability, Transparency) set out that expectation. In engineering terms, a recommendation engine that declines a loan must log why. An agent that executes a trade must record who authorised it, what envelope it operated under, and how much it was allowed to spend. "The AI decided" is not an acceptable audit response.

Without governance engineering, you get one of two failure modes. Either the system is wide open — any agent can access any data and spend any amount — which is a security and compliance disaster. Or governance is bolted on as an afterthought — a brittle layer of if-statements that breaks every time the system changes. PACT makes governance a first-class component: declared, compiled, enforced, and tested.

Core Concepts

D/T/R Addressing

PACT's addressing grammar breaks identity into three dimensions:

DimensionMeaningExample
Department (D)Top-level organisational unitD1 = mortgage-risk
Team (T)A team nested inside a departmentT1 = underwriting
Role (R)A position (human or agent); the first R after a D or T is its headR1 = the head of that unit

A role address is a dash-delimited path like D1-R1-T1-R1. The grammar rule: every D or T MUST be immediately followed by exactly one R — its head. So D1-R1-T1-R1 reads "the role heading Team 1, under the role heading Department 1". The GovernanceEngine is constructed from a loaded org YAML (load_org_yaml). Delegation is a separate concept: an envelope is defined by one role (usually the head above) for another role, and a child envelope may never be looser than the envelope of the role that defined it.

Foundations

Think of D/T/R as a postal address for permissions. The department is the street, the team is the building, the role is the apartment. When a request arrives, the system checks whether that address has the mailbox (envelope) for this type of mail (action). The grammar is strict: every D or T is immediately followed by exactly one R.

Operating Envelopes

An operating envelope defines the boundaries within which a role can operate. If D/T/R addressing answers "who is asking", envelopes answer "what may they do". A modern ConstraintEnvelopeConfig has five canonical dimensions, plus a confidentiality clearance and a delegation-depth cap:

Monotonic Tightening

The critical safety property of envelopes: they can only get stricter, never looser. A supervisor agent that allocates a $10 budget to a child agent cannot later increase it to $20. A task envelope that excludes deploy_model cannot later add it. This is monotonic tightening — trust flows downward and narrows at each level.

Theory

Monotonic tightening is a lattice property. If we define a partial order on envelopes where $E_1 \leq E_2$ means "$E_1$ is at least as restrictive as $E_2$", then the set of all envelopes forms a lattice with the most restrictive envelope (deny everything) at the bottom and the most permissive (allow everything) at the top. Child envelopes must always be below or equal to their parent in this lattice — they can only move downward.

Verdict Levels

There is one decision call: engine.verify_action(role_address, action, context). It returns a GovernanceVerdict with .allowed, .level and .reason. There are no enforcement modes to switch between — the level is decided by the role's envelope and the action's context. The four levels, with the reasons the installed engine actually returns (measured on the worked-example org below):

.level.allowedWhenExample .reason
auto_approvedTrueAction inside every envelope dimensionAction 'explore_data' is within all constraint dimensions
flaggedTrueAllowed, but close to a limit (cost within 20% of max_spend_usd)Action cost ($3.50) is within 20% of financial limit ($4.00)
heldFalseCost above requires_approval_above_usd — waits for a humanAction cost ($9.00) exceeds approval threshold ($8.00) -- held for human approval
blockedFalseAction blocked, not allowed, or over the spend limitAction 'deploy_model' is explicitly blocked by operational constraints

The Default You Must Know: No Envelope Means Allowed

In the installed release (kailash-pact 0.14.1), verify_action is fail-open for two cases: a role with no envelope on itself or on any role above it, and an address that is not in the org at all. (A role with no envelope of its own but an enveloped ancestor is governed by the ancestor's envelope.) Both return allowed == True, level == "auto_approved" with the reason "No envelope constraints -- action permitted". Loading the YAML with load_org_yaml and building GovernanceEngine(loaded.org_definition) compiles only the structure; until envelopes are attached (with engine.set_role_envelope(...), or apply_governance_specs(engine, loaded) for the envelopes declared in the YAML), every role in the org is auto-approved for every action.

The engine is fail-closed in one narrower sense: if verify_action itself raises internally, it returns a blocked verdict rather than crashing. But "no rule" is not an error — it is an approval. Deny paths exist only where an envelope is attached, so the engineering rule for this lesson is: attach an envelope to every role before you rely on a deny, and reject unknown addresses in your own code (Step 5 of the worked example shows how).

Advanced

The flagged and held levels give you a staged rollout without a separate "warn mode". Start a new role with a generous max_spend_usd and a lower requires_approval_above_usd: expensive actions are held for a human, near-limit actions are flagged (allowed, but visible in the verdict), and only actions outside the envelope are blocked. Review the flagged and held verdicts, then tighten the envelope.

Mathematical Foundations: Budget Cascading

Budget cascading is a constraint propagation problem. A parent agent with budget $B$ allocates portions to $n$ child agents:

$$ \sum_{i=1}^{n} b_i \leq B \quad \text{where each } b_i \geq 0 $$
$B$ — parent budget $b_i$ — allocation to child $i$ $n$ — number of children

The sum of all child budgets should not exceed the parent's total. Each child can further subdivide its allocation, but the total at every level is bounded. Note what PACT checks for you and what it does not: set_role_envelope rejects any single child whose max_spend_usd exceeds its parent's, but it does not add up the siblings — the sum constraint is yours to assert (Step 3 of the worked example does it).

What happens when the budget runs out? GovernedSupervisor checks the remaining budget before each plan step. A step that overspends still completes (its cost is recorded, so budget_consumed can end above budget_allocated), and every later step is HELD: the run returns success == False, any results produced before the hold are kept in result.results, and the audit log gains a held record. That is the graceful degradation — a bounded overspend, partial results, and a logged stop — rather than a hard kill mid-call.

Budgets also exist on single agents: a Kaizen BaseAgentConfig takes budget_limit_usd at construction (Lesson 6.5). On the course's local Ollama models every call costs $0, so dollar caps never trip there; the course exercises charge a notional price per 1,000 tokens when they need the financial dimension to be visible.

For a three-level hierarchy (supervisor, team leads, workers) with supervisor budget $B = \$50$:

$$ B_{\text{supervisor}} = \$50 \geq \underbrace{b_{\text{lead}_1} + b_{\text{lead}_2}}_{= \$20 + \$20} + b_{\text{reserve}} $$ $$ b_{\text{lead}_1} = \$20 \geq \underbrace{b_{\text{worker}_1} + b_{\text{worker}_2} + b_{\text{worker}_3}}_{= \$6 + \$6 + \$6} + b_{\text{lead reserve}} $$

Each allocation is a hard ceiling. Workers cannot request additional budget from the supervisor — they can only use what their team lead allocated. This prevents any single branch from consuming the entire budget.

Foundations

Budget cascading works like a company's departmental budgets. The CEO allocates to VPs; VPs allocate to directors; directors allocate to teams. Each level can only spend what it was given. No one can reach up to grab more money. If your team runs out, you stop and report back.

The Kailash Engine: PACT

Kailash Engine

pact provides: load_org_yaml and GovernanceEngine for compiling organisational structures (with apply_governance_specs from kailash.trust.pact.yaml_resolvers to apply the YAML's clearances and envelopes); engine.verify_action(role_address, action, context) as the single decision call; Address.parse("D1-R1-T1-R1") for D/T/R addressing; ConstraintEnvelopeConfig with five canonical dimensions (Financial, Operational, Temporal, Data Access, Communication) attached to roles with engine.set_role_envelope(RoleEnvelope(...)); and RoleEnvelope.validate_tightening(parent_envelope=..., child_envelope=...) (keyword-only) for monotonic-tightening checks. GovernedSupervisor (from kaizen_agents) is the pact-governed agent entry point. Together they transform governance from policy documents into executable, testable code.

Worked Example: Governed Multi-Agent System

Goal

Build a governed multi-agent system for mortgage-risk analysis on an HDB resale portfolio. A risk supervisor heads three specialist teams: data assessment (DataScientist), model selection (ModelSelector) and reporting (ReportWriter). Each role gets an envelope with its own budget and allowed actions. Out-of-envelope actions are blocked, budget overruns stop the run, unknown addresses are rejected, and every step is logged.

Step 2 — Define operating envelopes for each role.

Envelopes are ConstraintEnvelopeConfig instances with the five canonical dimensions (financial, operational, temporal, data access, communication) plus a confidentiality clearance and a delegation-depth cap (a positive integer, or None for unlimited). The financial dimension is where per-role budgets live. The supervisor's envelope must already contain every action it will hand down — a child may only narrow it.

Step 3 — Attach envelopes to roles and verify the budget sum.

Attach the parent first, then the children. set_role_envelope checks each child against the envelope of its defining role and raises MonotonicTighteningError if the child is looser on any dimension. It does not add up siblings, so the sum check is an explicit assertion. 

from pact import MonotonicTighteningError

engine.set_role_envelope(RoleEnvelope(
    id="supervisor_role_env",
    defining_role_address="D1-R1",
    target_role_address="D1-R1",
    envelope=supervisor_env,
))

children = {"D1-R1-T1-R1": data_scientist_env,
            "D1-R1-T2-R1": model_selector_env,
            "D1-R1-T3-R1": report_writer_env}
for address, env in children.items():
    engine.set_role_envelope(RoleEnvelope(
        id=f"{env.id}_role",
        defining_role_address="D1-R1",      # the supervisor defines it
        target_role_address=address,
        envelope=env,
    ))

child_total = sum(env.financial.max_spend_usd for env in children.values())
assert child_total <= supervisor_env.financial.max_spend_usd, "over-allocation"
print(f"Total allocated to children: ${child_total:.2f}")
print(f"Supervisor reserve: ${supervisor_env.financial.max_spend_usd - child_total:.2f}")
# Total allocated to children: $10.00
# Supervisor reserve: $0.00

# A child that tries to loosen its parent is rejected when attached
greedy = ConstraintEnvelopeConfig(
    id="greedy_env",
    confidentiality_clearance=ConfidentialityLevel.RESTRICTED,
    financial=FinancialConstraintConfig(max_spend_usd=30.00),
    operational=OperationalConstraintConfig(allowed_actions=["explore_data"]),
    max_delegation_depth=1,
)
try:
    engine.set_role_envelope(RoleEnvelope(
        id="greedy_role", defining_role_address="D1-R1",
        target_role_address="D1-R1-T1-R1", envelope=greedy,
    ))
except MonotonicTighteningError as err:
    print(err)
# Monotonic tightening violation(s): Financial: child max_spend_usd (30.0) exceeds parent (10.0)
Step 4 — Run the work through a GovernedSupervisor.

GovernedSupervisor does not wrap an agent. It takes a model and three knobs — budget_usd, tools and data_clearance — and await supervisor.run(objective, execute_node=...) turns the objective into a plan, checks the budget before each step, calls your execute_node(spec, inputs) callback to do the model work, records the reported cost, and appends to a hash-chained audit log. run() builds a one-step plan (node task-0) whose spec.description is the objective; multi-step plans go through run_plan(plan, ...).

The two layers fit together inside the callback: before a specialist acts, ask the org engine whether its role may take that action. A raised exception marks the step FAILED and the run returns success == False. 

from kaizen_agents import GovernedSupervisor
from shared.mlfp06._ollama_bootstrap import (
    DEFAULT_CHAT_MODEL, make_delegate, run_delegate_text,
)

governed_supervisor = GovernedSupervisor(
    model=DEFAULT_CHAT_MODEL,          # from OLLAMA_CHAT_MODEL in .env
    budget_usd=10.00,
    tools=["explore_data", "compute_statistics", "feature_engineering"],
    data_clearance="restricted",       # public < restricted < confidential < secret < top_secret
)

def specialist_executor(role_address: str, action: str):
    """Build an execute_node callback that is gated by the org engine."""
    async def execute_node(spec, inputs):
        verdict = engine.verify_action(role_address, action)
        if not verdict.allowed:
            raise PermissionError(f"{role_address} may not {action}: {verdict.reason}")
        delegate = make_delegate(system_prompt="You are a mortgage-risk data scientist.")
        text, usage, _latency = await run_delegate_text(delegate, spec.description)
        return {"result": text,
                "cost": 0.0,                       # local Ollama is free
                "prompt_tokens": usage["prompt_tokens"],
                "completion_tokens": usage["completion_tokens"]}
    return execute_node

result = await governed_supervisor.run(
    objective="List three data-quality checks for an HDB resale mortgage portfolio.",
    execute_node=specialist_executor("D1-R1-T1-R1", "explore_data"),
)
print(result.success, result.budget_consumed, result.budget_allocated)
print(result.results["task-0"][:200])
# True 0.0 10.0, then the model's answer (needs `ollama serve`)

blocked = await governed_supervisor.run(
    objective="Train a default-risk model.",
    execute_node=specialist_executor("D1-R1-T1-R1", "train_model"),
)
print(blocked.success, [n.error for n in blocked.plan.nodes.values()])
# False ["D1-R1-T1-R1 may not train_model: Action 'train_model' is explicitly
#         blocked by operational constraints"]

The second run never reaches the model: the engine blocks the action, the callback raises, and the supervisor records the step as failed.

def governed_allowed(role_address: str, action: str, context=None) -> bool:
    """Deny unless the role exists AND has an envelope AND the verdict allows."""
    if engine.compute_envelope(role_address) is None:
        return False
    return engine.verify_action(role_address, action, context).allowed

print(governed_allowed("D99-R99-T99-R99", "read_data"))   # False
print(governed_allowed("D1-R1-T1-R1", "explore_data"))    # True
print(governed_allowed("D1-R1-T1-R1", "deploy_model"))    # False

Every supervised step — completed, failed or held — lands in that log with a timestamp, the agent, the action and its details (the cost, the node). Store the verify_action verdicts your code acts on next to it (each verdict has to_dict()), and you have the record a regulator or internal auditor will ask for: who acted, under which envelope, and why the engine said yes or no.

Clearance Levels

PACT's confidentiality clearance adds graduated access based on data sensitivity. The order is PACT's ConfidentialityLevel enum, lowest to highest: public < restricted < confidential < secret < top_secret. Note that restricted is the second-lowest tier, not the top (GovernedSupervisor also accepts "internal" as an alias for restricted). In the course organisation used by the exercises (shared.mlfp06.ex_7.compile_governance()), the department heads hold secret, the data analyst restricted and the customer-facing agent public.

RankLevelExample data in a lending businessIllustrative budget
1PUBLICPublished rates, FAQ answers$1
2RESTRICTEDAggregated portfolio statistics$5
3CONFIDENTIALCustomer-level loan records$20
4SECRETCredit-model internals, fraud investigations$50
5TOP_SECRETBoard-level or regulator-only materialby exception

Clearance appears in two places. A role clearance (the YAML's clearances: list, applied by apply_governance_specs, or engine.grant_clearance) says what the role may read. An envelope clearance (confidentiality_clearance on ConstraintEnvelopeConfig) caps what a delegated envelope may carry, and is subject to monotonic tightening like every other dimension. Clearance is only checked when the action names the data it touches: pass a KnowledgeItem as context["resource"]. 

from pact import ConfidentialityLevel, KnowledgeItem

for level in ["restricted", "confidential"]:
    loan_book = KnowledgeItem(item_id=f"loan_book_{level}",
                              classification=ConfidentialityLevel(level),
                              owning_unit_address="D1")
    v = engine.verify_action("D1-R1-T1-R1", "explore_data", {"resource": loan_book})
    print(level, v.level, v.reason)
# restricted auto_approved Action 'explore_data' is within all constraint dimensions
# confidential blocked Knowledge access denied: Effective clearance 'restricted'
#     is below item classification 'confidential'

Promotion is not a separate object — it is an envelope replacement on the role. The defining role issues a new RoleEnvelope at a higher clearance; monotonic tightening is enforced against the parent's envelope, so a promotion can go up to, but never beyond, what the supervisor itself holds. 

from pact import (
    RoleEnvelope, ConstraintEnvelopeConfig, FinancialConstraintConfig,
    OperationalConstraintConfig, ConfidentialityLevel, MonotonicTighteningError,
)

def build_envelope(level: ConfidentialityLevel, budget_usd: float,
                   actions: list[str]) -> ConstraintEnvelopeConfig:
    return ConstraintEnvelopeConfig(
        id=f"env_{level.name.lower()}",
        description=f"{level.name} clearance",
        confidentiality_clearance=level,
        financial=FinancialConstraintConfig(max_spend_usd=budget_usd),
        operational=OperationalConstraintConfig(allowed_actions=actions),
        max_delegation_depth=1,
    )

# The data scientist starts at PUBLIC with one action
initial = build_envelope(ConfidentialityLevel.PUBLIC, 1.00, ["explore_data"])
engine.set_role_envelope(RoleEnvelope(
    id="ds_env_v1", defining_role_address="D1-R1",
    target_role_address="D1-R1-T1-R1", envelope=initial,
))
print(engine.verify_action("D1-R1-T1-R1", "compute_statistics").level)   # blocked

# After a clean track record, the supervisor promotes it to RESTRICTED
promoted = build_envelope(ConfidentialityLevel.RESTRICTED, 3.00,
                          ["explore_data", "compute_statistics"])
engine.set_role_envelope(RoleEnvelope(
    id="ds_env_v2", defining_role_address="D1-R1",
    target_role_address="D1-R1-T1-R1", envelope=promoted,
))
print(engine.verify_action("D1-R1-T1-R1", "compute_statistics").level)   # auto_approved

# Promoting past the supervisor's own clearance (CONFIDENTIAL) is rejected
try:
    engine.set_role_envelope(RoleEnvelope(
        id="ds_env_v3", defining_role_address="D1-R1",
        target_role_address="D1-R1-T1-R1",
        envelope=build_envelope(ConfidentialityLevel.SECRET, 3.00, ["explore_data"]),
    ))
except MonotonicTighteningError as err:
    print(err)
# Monotonic tightening violation(s): Confidentiality: child clearance (secret)
#     exceeds parent (confidential)
Who may promote?

set_role_envelope checks the new envelope against the defining role's envelope; it does not check that the caller is that role, or that the defining role sits above the target (a sibling address is accepted). Treat the call as a privileged operation: only your supervisor code path may invoke it, and log every envelope change alongside the verdicts.

Advanced

Clearance promotion can be automated with a verification gradient. Define a scoring function that measures agent reliability (successful operations / total operations), governance compliance (violations / total checks), and cost efficiency (actual spend / allocated budget). When the score exceeds a threshold over a defined period, the agent is eligible for promotion. Demotion is immediate on any critical violation — trust is earned slowly and lost quickly.

Governance Testing Patterns

Governance testing is not optional — it is the most important testing you do. Functional tests verify that the system works. Governance tests verify that the system fails safely. The suite below runs as-is with pytest against the installed stack (no model calls: the supervisor tests use a callback that reports a fixed cost). It covers five patterns: deny paths on an attached envelope, the fail-open default and the guard that closes it, monotonic tightening, budget exhaustion, and audit-chain integrity. 

import pytest
from kaizen_agents import GovernedSupervisor
from kailash.trust.pact.yaml_resolvers import apply_governance_specs
from pact import (
    ConfidentialityLevel, ConstraintEnvelopeConfig, FinancialConstraintConfig,
    GovernanceEngine, MonotonicTighteningError, OperationalConstraintConfig,
    RoleEnvelope, load_org_yaml,
)
from shared.mlfp06._ollama_bootstrap import DEFAULT_CHAT_MODEL


def envelope(env_id, clearance, budget_usd, actions, blocked=()):
    return ConstraintEnvelopeConfig(
        id=env_id,
        confidentiality_clearance=clearance,
        financial=FinancialConstraintConfig(max_spend_usd=budget_usd),
        operational=OperationalConstraintConfig(allowed_actions=list(actions),
                                                blocked_actions=list(blocked)),
        max_delegation_depth=1,
    )


@pytest.fixture
def engine():
    """The worked-example org with envelopes ATTACHED — deny paths need them."""
    loaded = load_org_yaml("org/mortgage_risk.yaml")   # Step 1 of the worked example
    eng = GovernanceEngine(loaded.org_definition)
    apply_governance_specs(eng, loaded)
    eng.set_role_envelope(RoleEnvelope(
        id="sup", defining_role_address="D1-R1", target_role_address="D1-R1",
        envelope=envelope("sup_env", ConfidentialityLevel.CONFIDENTIAL, 10.0,
                          ["explore_data", "compute_statistics", "train_model"],
                          blocked=["deploy_model"])))
    eng.set_role_envelope(RoleEnvelope(
        id="ds", defining_role_address="D1-R1", target_role_address="D1-R1-T1-R1",
        envelope=envelope("ds_env", ConfidentialityLevel.RESTRICTED, 3.0,
                          ["explore_data", "compute_statistics"],
                          blocked=["train_model", "deploy_model"])))
    return eng


# Pattern 1: an action outside an ATTACHED envelope is blocked
def test_data_scientist_cannot_deploy(engine):
    verdict = engine.verify_action("D1-R1-T1-R1", "deploy_model")
    assert not verdict.allowed
    assert verdict.level == "blocked"


def test_data_scientist_cannot_overspend(engine):
    verdict = engine.verify_action("D1-R1-T1-R1", "explore_data", {"cost": 5.00})
    assert verdict.level == "blocked"           # $5 > the $3 envelope


# Pattern 2: pin the installed default, then prove your own guard closes it
def test_unknown_address_is_auto_approved_by_default(engine):
    verdict = engine.verify_action("D99-R99-T99-R99", "read_data")
    assert verdict.allowed and verdict.level == "auto_approved"   # fail-open


def test_guard_rejects_unknown_and_envelope_less_roles(engine):
    def governed_allowed(addr, action):
        if engine.compute_envelope(addr) is None:
            return False
        return engine.verify_action(addr, action).allowed
    assert not governed_allowed("D99-R99-T99-R99", "read_data")
    assert governed_allowed("D1-R1-T1-R1", "explore_data")


def test_role_without_own_envelope_inherits_its_parents(engine):
    # D1-R1-T2-R1 has no envelope of its own: the supervisor's envelope applies
    assert engine.verify_action("D1-R1-T2-R1", "deploy_model").level == "blocked"


# Pattern 3: monotonic tightening — keyword-only arguments
def test_child_envelope_cannot_loosen_parent():
    parent = envelope("parent", ConfidentialityLevel.RESTRICTED, 5.00, ["read"])
    child = envelope("child", ConfidentialityLevel.CONFIDENTIAL, 10.00, ["read"])
    with pytest.raises(MonotonicTighteningError, match="Confidentiality"):
        RoleEnvelope.validate_tightening(parent_envelope=parent, child_envelope=child)


# Pattern 4: budget exhaustion holds every later step
@pytest.mark.asyncio
async def test_budget_exhaustion_holds_further_work():
    tiny = GovernedSupervisor(model=DEFAULT_CHAT_MODEL, budget_usd=0.01,
                              tools=["answer_question"], data_clearance="public")

    async def costly_step(spec, inputs):          # test double: reports $0.02 per step
        return {"result": "draft", "cost": 0.02,
                "prompt_tokens": 100, "completion_tokens": 50}

    first = await tiny.run(objective="analyse portfolio", execute_node=costly_step)
    assert first.success                                   # the overspending step completes
    assert first.budget_consumed > first.budget_allocated  # ...and the overspend is recorded
    second = await tiny.run(objective="write the summary", execute_node=costly_step)
    assert not second.success and second.results == {}    # every later step is HELD
    assert any(r["record_type"] == "held" for r in tiny.audit.to_list())


# Pattern 5: the audit chain is intact
@pytest.mark.asyncio
async def test_audit_chain_is_valid():
    supervisor = GovernedSupervisor(model=DEFAULT_CHAT_MODEL, budget_usd=1.0,
                                    tools=["answer_question"], data_clearance="public")

    async def free_step(spec, inputs):
        return {"result": "ok", "cost": 0.0, "prompt_tokens": 0, "completion_tokens": 0}

    await supervisor.run(objective="answer one question", execute_node=free_step)
    trail = supervisor.audit.to_list()
    assert [r["record_type"] for r in trail] == ["genesis", "action"]
    assert supervisor.audit.verify_chain()

Two details matter. The engine fixture attaches envelopes before any deny test — without them every test in Pattern 1 would fail, because the default is to approve. And Pattern 2 deliberately pins the fail-open default: if a future PACT release changes it, that test fails and tells you to revisit the guard rather than leaving the change unnoticed.

Critical principle

Governance tests are negative tests. They test what does NOT happen. Every assert not verdict.allowed and every pytest.raises(MonotonicTighteningError) is a guardrail that prevents the system from doing something dangerous. If these tests fail, it means your governance has a hole. Treat governance test failures as critical — they are security vulnerabilities.

Common Mistakes

Mistake 1: Assuming the engine fails closed

If the governance check cannot reach a decision (missing rules, unknown role), your system should deny. The installed PACT engine does not do that for you: a role with no envelope in its chain, or an address that is not in the org, is auto_approved. A system that allows everything when its rules are missing is worse than no governance at all, because it creates a false sense of security. Attach an envelope to every role (or to a head whose envelope covers its subtree), reject addresses without an effective envelope in your own code, and pin that behaviour with a test.

Mistake 2: Testing only the happy path

"The analyst can read data" is a happy path test. The governance tests that matter are: "The analyst cannot deploy models", "The analyst cannot exceed budget", "The analyst cannot loosen their envelope". Test what is denied, not just what is granted.

Mistake 3: No audit trail

Compliance requires proving every access decision was checked. Record every verify_action() verdict your code acts on (verdict.to_dict()) — both grants and denials — next to the supervisor's hash-chained audit log. The engine keeps no audit record of its own unless you construct it with an audit_chain. The audit trail is not for debugging; it is for the regulator. MAS, PDPA, and GDPR all require demonstrable access control.

Mistake 4: Governance as philosophy instead of code

"We have an AI ethics framework" is not governance. Governance is engine.verify_action(addr, action) returning a blocked verdict and the tool call never running. If it is not in code, it is not enforced. If it is not tested, it does not work. This lesson is engineering, not philosophy.

Reflection

Governance is the hardest lesson in the programme to appreciate — until you deploy without it and face the consequences. An ungoverned agent with access to a production database can delete records, leak personal data, or spend thousands of dollars in minutes. An ungoverned multi-agent system can cascade errors across agents with no way to trace what happened.

What you built today — D/T/R addressing, operating envelopes, budget cascading, audit trails, governance tests — is the difference between a prototype and a production system. Prototypes work when everything goes right. Production systems work when everything goes wrong. PACT ensures that "wrong" is bounded, logged, and recoverable.

In Lesson 6.8, you deploy this governed system via Nexus — three channels, authenticated, rate-limited, monitored. That is the capstone. That is the finish line.
