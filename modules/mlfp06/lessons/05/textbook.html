Lesson 6.5 AI Agents — ReAct, Tool Use, and Function Calling

An LLM that only generates text is like a brain without hands. It can reason about problems but cannot solve them — it cannot query a database, call an API, train a model, or check a fact. Agents give the LLM the ability to act: reason about a task, select a tool, execute it, observe the result, and iterate until the task is complete. Today you build a ReAct agent with Kaizen — a Delegate whose ToolRegistry holds Python tools over the HotpotQA multi-hop question-answering dataset (Exercise 5), plus a profiling tool backed by kailash-ml's DataExplorer. The agent decides which tool to call and in what order, you capture and read its real trace, and you bound it with a hard turn ceiling and — on priced providers — a dollar budget.

Why This Matters

Picture (illustratively) an analytics team at a Singapore logistics firm that receives dozens of new datasets each quarter. Profiling each one by hand — load, inspect, check for nulls, look at distributions, try a baseline — takes the better part of an hour. An agent with the right tools can do the mechanical part in minutes and draft the summary. More importantly, it applies the same checklist every time, because the checklist lives in its tools and instructions rather than in someone's memory.

But an agent without guardrails is dangerous. It might call an expensive API in a loop, hallucinate tool names, or present fabricated results as real. Today you learn the three components that make agents useful and safe: structured reasoning (ReAct), structured tool interfaces (function calling), and bounds — a turn ceiling (max_turns) that works on every provider, and a dollar budget (budget_limit_usd, passed when the agent is constructed) that stops spend on priced providers.

Core Concepts

What is an Agent?

An agent is an LLM wrapped in a loop. On each iteration the LLM:

  1. Reasons about the current state of the task — what it knows, what it still needs.
  2. Decides on an action — which tool to call, with what parameters.
  3. Executes the action — the tool runs and returns a result.
  4. Observes the result — incorporates it into its working memory.
  5. Repeats or answers — loops if more work is needed, or returns a final answer.

This is the ReAct pattern (Reasoning + Acting), introduced by Yao et al. (2022). The key insight is that interleaving reasoning with action produces better results than either pure reasoning (chain-of-thought) or pure action (tool calls without explanation). The reasoning step forces the LLM to plan before acting, reducing random tool invocations.

The ReAct Loop

Foundations

Think of a ReAct agent like a junior analyst who talks through their reasoning before each step. "I think I should check if there are null values first" → runs the null check → "OK, 3% nulls in the income column. I should impute those before training" → runs imputation. The explicit reasoning makes the agent's logic transparent and debuggable.

Chain-of-Thought vs ReAct

Chain-of-thought (CoT) from Lesson 6.1 asks the LLM to reason step-by-step but does not let it act. It reasons about a question and returns an answer in a single pass. ReAct extends CoT by letting the LLM verify its reasoning against reality through tool calls. This matters because LLMs hallucinate — a CoT agent might reason correctly about a formula but apply it to hallucinated numbers. A ReAct agent can check the actual data.

Math Foundations

Agent design has less novel mathematics than deep learning, but there are two formal frameworks worth understanding to reason about agent behaviour.

Agents as Markov Decision Processes

An agent's interaction with its tools can be modelled as a simplified MDP (connecting to the RL formalism from Lesson 5.8). At each step:

$$ s_{t+1}, r_{t+1} = \text{env}(s_t, a_t) $$
$s_t$ — agent's state (conversation history + observations) $a_t$ — action (tool call or final answer) $r_{t+1}$ — implicit reward (task progress)

Unlike RL where the policy is learned through training, a ReAct agent's "policy" is the LLM itself — prompted to select the best action given the current state. The LLM's pre-training acts as a massive prior over useful action sequences.

Expected cost of an agent run

Each agent step incurs token costs. If the agent makes $K$ tool calls with an average of $T_{\text{in}}$ input tokens and $T_{\text{out}}$ output tokens per call:

$$ C_{\text{total}} = \sum_{k=1}^{K} \bigl( c_{\text{in}} \cdot T_{\text{in}}^{(k)} + c_{\text{out}} \cdot T_{\text{out}}^{(k)} \bigr) $$
$c_{\text{in}}$ — cost per input token $c_{\text{out}}$ — cost per output token $K$ — number of LLM calls

Context grows with each step because the agent carries the full conversation. Step $k$ has approximately $T_{\text{in}}^{(k)} \approx T_{\text{system}} + k \cdot T_{\text{avg\_turn}}$ input tokens. This means agent cost grows quadratically with the number of steps — a critical insight for cost budgeting.

Theory

The quadratic cost growth explains why agents stuck in loops are expensive. A 10-step agent costs roughly $\frac{10 \cdot 11}{2} = 55$ "step-units" of input tokens. A 20-step agent (just double the steps) costs $\frac{20 \cdot 21}{2} = 210$ step-units — nearly 4x more. This is why every agent needs a hard bound: a turn ceiling (max_turns on the Delegate) caps the number of steps on any provider, and a dollar cap (BaseAgentConfig.budget_limit_usd) caps priced spend. Without a bound, a confused agent on a priced API keeps paying for a growing context on every turn.

Function Calling Protocol

An agent needs a structured way to invoke tools. The function calling protocol defines tools as JSON schemas that the LLM can reference by name. The LLM does not execute code — it produces a structured JSON object specifying which function to call and with what arguments. The agent framework parses that JSON and executes the actual function.

Tool schema definition

A tool definition has three parts: a name, a description the model reads to decide when to call it, and a JSON Schema for its arguments. These are the schemas for two of the Exercise 5 tools over HotpotQA (the shape every tool-capable chat API expects): 

tool_schemas = [
    {
        "name": "search_documents",
        "description": "Search the QA corpus for documents matching a keyword query.",
        "parameters": {
            "type": "object",
            "properties": {
                "query": {"type": "string", "description": "Keywords to search for"},
                "top_k": {"type": "integer", "description": "Maximum documents to return"},
            },
            "required": ["query"],
        },
    },
    {
        "name": "run_query",
        "description": "Run a descriptive query against the QA dataset.",
        "parameters": {
            "type": "object",
            "properties": {
                "query_description": {
                    "type": "string",
                    "description": "e.g. 'count question types', 'find bridge-type questions'",
                },
            },
            "required": ["query_description"],
        },
    },
]

In Kaizen a tool exists for the model only once it is registered in a ToolRegistry: name, description, schema, and an async executor that runs your code and returns a string. Handing a Delegate a bare list of Python functions registers nothing — the model then has no tools and simply guesses. 

from kaizen_agents.delegate.loop import ToolRegistry
from shared.mlfp06.ex_5 import load_hotpotqa, make_tools, run_query

make_tools(load_hotpotqa())          # binds the HotpotQA frame to the tool functions


async def run_query_tool(query_description: str) -> str:
    return run_query(query_description)          # plain Python, returns text


registry = ToolRegistry()
registry.register(
    name="run_query",
    description="Run a descriptive query against the QA dataset.",
    parameters={
        "type": "object",
        "properties": {"query_description": {"type": "string"}},
        "required": ["query_description"],
    },
    executor=run_query_tool,
)
print(registry.tool_names)           # ['run_query']

shared.mlfp06.ex_5.build_tool_registry(tools) does exactly this for a list of functions, generating each schema from the function's signature and the first line of its docstring.

Foundations

Good tool descriptions are the agent equivalent of good documentation. The LLM decides which tool to call based entirely on the description field and the parameter names. A vague description like "does data stuff" leads to incorrect tool selection. A precise description like "Load and profile a dataset. Returns shape, column types, null counts, and basic statistics" tells the LLM exactly when this tool is useful and what to expect back.

The tool_choice parameter

Chat APIs that support function calling let the caller control how aggressively the LLM uses tools. Kaizen's Delegate loop always sends "auto" when tools are registered; the other settings are part of the protocol you will meet when calling a provider API directly:

tool_choiceBehaviourWhen to use
"auto"LLM decides whether to call a toolDefault — let the agent reason
"required"LLM must call at least one toolFirst step, when you know action is needed
{"type": "function", "function": {"name": "..."}}Force a specific toolDebugging, testing a particular path
"none"LLM cannot call toolsFinal summarisation step

Parallel function calling

Some LLM providers support parallel function calling — the LLM can request multiple tool calls in a single response. This is useful when the agent needs independent pieces of information simultaneously (e.g., profile two datasets at once). When one model turn contains several tool calls, the Kaizen Delegate loop runs their executors concurrently (asyncio.gather) and feeds all the results back in the next turn. Whether the model emits several calls in one turn depends on the model; small local models usually call one tool at a time.

The Kailash Engine: Kaizen Agents

Kailash Engine

Three Kaizen building blocks cover this lesson. A Delegate with a ToolRegistry is a ReAct loop: each model turn either emits tool calls (Thought + Action), which the Delegate executes and feeds back (Observation), or answers in plain text, which ends the loop. BaseAgent + Signature gives typed inputs and outputs for a single structured call (Exercise 5.3). And ChainOfThoughtAgent (in kaizen_agents.agents) reasons step by step without tools. Kaizen also ships a ReActAgent class, but in the installed release its tool executor dispatches only MCP tools, not Python functions — so for Python tools the course uses the Delegate. In course code, always build the Delegate with make_delegate() from shared.mlfp06._ollama_bootstrap: it wires the local Ollama adapter and takes the model from OLLAMA_CHAT_MODEL.

Building a ReAct agent with Kaizen

import polars as pl
from kailash_ml import DataExplorer
from shared.mlfp06._ollama_bootstrap import make_delegate
from shared.mlfp06.ex_5 import build_tool_registry, load_hotpotqa, make_tools

qa_data = load_hotpotqa()            # 500 HotpotQA rows: text, question, answer, level, type
tools = make_tools(qa_data)          # data_summary, search_documents, run_query, answer_question
registry = build_tool_registry(tools)


async def profile_dataset(dataset_name: str = "qa_data") -> str:
    """Profile the QA dataset with kailash-ml's DataExplorer: rows, column types, alerts."""
    profile = await DataExplorer().profile(qa_data)
    lines = [f"{profile.n_rows} rows x {profile.n_columns} columns"]
    lines += [f"{c.name}: {c.dtype}, nulls={c.null_pct:.1%}, unique={c.unique_count}"
              for c in profile.columns]
    lines += [f"alert: {a['type']} {a.get('column', '')}" for a in profile.alerts]
    return "\n".join(lines)


registry.register(
    name="profile_dataset",
    description="Profile the QA dataset with DataExplorer: rows, column types, nulls, alerts.",
    parameters={"type": "object", "properties": {"dataset_name": {"type": "string"}}, "required": []},
    executor=profile_dataset,
)

agent = make_delegate(               # model from OLLAMA_CHAT_MODEL; no model= here
    tools=registry,
    system_prompt=(
        "You are a research analyst working on the HotpotQA dataset. Use the tools "
        "to gather evidence before you answer; do not invent numbers."
    ),
    max_turns=8,                     # hard ceiling on Thought-Action-Observation cycles
)
print(agent.tool_registry.tool_names)

The last line prints the five registered tool names (data_summary, search_documents, run_query, answer_question, profile_dataset). Note that DataExplorer.profile is a coroutine, so the executor awaits it — executors are async precisely so tools can do I/O and call other async engines.

Caution — a tool that hands over the answer

answer_question looks up the dataset's ground-truth answer for a question. It is there so you can check the agent's work, but it also means an agent can "answer" a HotpotQA question without reasoning at all. When you want to see multi-hop reasoning, leave it out of the registry and let the agent work from search_documents.

Bounding the agent: max_turns and budget_limit_usd

Two different ceilings bound an agent, and they work in different places:

  • Turn ceiling — make_delegate(..., max_turns=N) stops the loop after $N$ model turns, whatever the model wants. It works on every provider, including free local Ollama.
  • Dollar cap — BaseAgentConfig(budget_limit_usd=...) on a BaseAgent stops the agent once its priced spend reaches the cap. It is only as good as the price table behind it: Kaizen prices a local Ollama call at $0, so on this course's stack a dollar cap can never trip (and make_delegate() deliberately sets the Delegate's own budget_usd to None). On a hosted, priced provider it is the control you want.
from kaizen import InputField, OutputField, Signature
from kaizen.core.base_agent import BaseAgent, BaseAgentConfig
from shared.mlfp06._ollama_bootstrap import DEFAULT_CHAT_MODEL, OLLAMA_BASE_URL


class BriefingSignature(Signature):
    """Write a one-paragraph briefing from a dataset summary."""

    dataset_summary: str = InputField(description="Statistical summary")
    briefing: str = OutputField(description="One-paragraph briefing")


def ollama_config(**extra) -> BaseAgentConfig:
    return BaseAgentConfig(llm_provider="ollama", model=DEFAULT_CHAT_MODEL,
                           base_url=OLLAMA_BASE_URL, use_async_llm=True, **extra)


capped = BaseAgent(config=ollama_config(budget_limit_usd=0.10), signature=BriefingSignature())
late = BaseAgent(config=ollama_config(), signature=BriefingSignature())
late.config.budget_limit_usd = 0.10          # the trap: set after construction

print(capped.execution_context.budget_limit)   # 0.1  -> enforced
print(late.execution_context.budget_limit)     # None -> NOT enforced
Theory

BaseAgent copies budget_limit_usd into its enforcement context only when it is constructed. Assigning agent.config.budget_limit_usd afterwards changes the config object but not the enforcement, so the agent runs uncapped — the snippet above prints 0.1 and then None (both checked on the installed Kaizen; no LLM call is made). Exercise 5.2 runs a tight (max_turns=2) and a normal (max_turns=12) agent on a deliberately expensive task and measures turns, tool calls and tokens against each ceiling. Budgets attached to the agent are the agent layer of its operating envelope; Lesson 6.7 adds the organisation layer, where PACT bounds spend per role.

Reasoning without tools: ChainOfThoughtAgent

When a task needs careful reasoning but no data access, Kaizen's ChainOfThoughtAgent runs a fixed step-by-step reasoning signature — five labelled steps (problem understanding, data identification, analysis, verification, answer formulation), then a final_answer and a confidence in [0, 1]. Its run method is synchronous and returns a dict. Its defaults point at a hosted provider, so pass the local provider and model explicitly. Like BaseAgent.run_async, it reports a failed LLM call as a dict with an error key instead of raising (with Ollama stopped it returns {"error": "Missing required output field: step1", ...}), so check the result before using it: 

from kaizen_agents.agents import ChainOfThoughtAgent
from shared.mlfp06._ollama_bootstrap import DEFAULT_CHAT_MODEL
from shared.mlfp06.ex_5 import require_agent_result

cot = ChainOfThoughtAgent(llm_provider="ollama", model=DEFAULT_CHAT_MODEL)
result = cot.run(
    problem="A bridge question needs facts from two documents. Why can a single "
            "keyword search miss the second document?",
)
require_agent_result(result, "ChainOfThoughtAgent")   # failures come back as {"error": ...}
for step in ("step1", "step2", "step3", "step4", "step5"):
    print(step, "->", result.get(step, "")[:120])
print("answer:", result.get("final_answer"), "| confidence:", result.get("confidence"))

The chain-of-thought agent can only reason from what the model already knows. Give it a question about this dataset ("how many comparison questions are there?") and it will produce a confident, unverifiable number; the ReAct agent calls run_query and reports the real count. That contrast is the whole argument for tools.

Agent Design Framework

Before writing code, answer four questions. This mental framework (from the MLFP agent design methodology) prevents the most common failure: an agent that calls tools randomly because its purpose was never clearly defined.

Advanced

The specialist description becomes the agent's system prompt. A vague specialist ("you are a helpful assistant") produces unfocused behaviour. A sharp specialist ("you are a research analyst for multi-hop question answering: gather evidence from each document the question depends on before answering, and never invent numbers") produces targeted, domain-appropriate reasoning. The more specific the specialist, the fewer wasted tool calls.

Worked Example: A Traced Research Agent on HotpotQA

Goal

Run the tool-using agent built above on a multi-step task over the HotpotQA dataset, capture its real trace with the course's LLMObservatory, and judge its behaviour from the trace rather than from its prose. This follows ex_5/01_react_agent.py. It needs the Ollama daemon running with a tool-capable chat model (OLLAMA_CHAT_MODEL, default llama3.2:3b); the code uses top-level await as in a notebook cell.

Step 1. Design decisions.
  • Five focused tools — summary, keyword search, descriptive queries, ground-truth lookup, DataExplorer profile. Enough to finish the task, few enough for reliable selection.
  • Precise descriptions — each tool's description says what it returns, because that is all the model sees.
  • A turn ceiling — max_turns=8, so a confused model cannot loop indefinitely.
  • A fresh agent per task — a Delegate keeps its conversation history between runs, so independent tasks get independent instances.
Step 2. Run the task under trace capture. 
from shared.mlfp06.diagnostics import LLMObservatory
from shared.mlfp06.ex_5 import require_llm_trace

task = (
    "Analyse the HotpotQA dataset: 1) profile it, 2) count question types and "
    "difficulty levels, 3) search for documents relevant to this question: "
    f"\"{qa_data['question'][0]}\", 4) write a short report of your findings."
)

obs = LLMObservatory(run_id="lesson_6_5_react")
trace = await obs.agent.capture_run(agent, task, run_id="react_main")
require_llm_trace(trace)                     # raises if the LLM call itself failed

tool_order = [ev.tool for ev in trace.events if ev.kind == "tool_start"]
answer = "".join(ev.content or "" for ev in trace.events if ev.kind == "token")
print("tool order:", " -> ".join(tool_order) or "(none)")
print("turns used:", agent.loop.usage.turns, "| tokens:", agent.loop.usage.total_tokens)
print(answer[:600])

require_llm_trace matters: Delegate.run turns a provider failure (daemon down, model not pulled) into an error event rather than an exception, so without the check a failed run looks like an empty but "successful" one.

Step 3. Read the trace, not the prose. 
print(obs.agent.tool_usage("react_main"))    # tool, calls, errors, mean_latency_ms, total_cost_usd
loops = obs.agent.detect_loops("react_main")  # same tool + same args repeated
print("stuck loops:", loops.height)

The exact tool order varies from run to run and model to model — that is the point of an agent. What you look for is the shape:

  • Good signals: general-to-specific order (profile or summary before search); every tool call's arguments match its schema; the final report uses all observations, and every number in it appears in some tool output.
  • Bad signals: no tool calls at all (the model guessed — check that the tools are registered and the model is tool-capable); the same tool with identical arguments several times in a row (detect_loops reports it); numbers in the answer that no tool returned.

total_cost_usd in the tool-usage table is 0 on local Ollama. Tokens are the real consumption measure: multiply agent.loop.usage.total_tokens by your provider's price to estimate what the same run would cost on a hosted model.

Step 4. Evaluate the agent's behaviour.

Compare the report with the tool outputs line by line. A small local model will usually call the right tools but may summarise loosely, mix up counts, or stop early when it reaches the turn ceiling — all visible in the trace. That is why Exercise 5.4 adds a critic agent that reviews the draft and requests a revision, and why every number an agent reports should be traceable to a tool call.

Agent Design Considerations

Iterative refinement

A critic agent can review another agent's output and recommend improvements. The data analyst agent produces a report; a reviewer agent checks for missing analyses, statistical errors, or unsupported conclusions. A separate critic, with its own instructions, catches errors the author's own framing hides. Exercise 5.4 builds this loop from three BaseAgents — analyst, critic (whose signature returns should_revise: bool) and refiner — and compares the initial and refined outputs.

Human-in-the-loop

For high-stakes or irreversible actions, the agent should pause and request human approval before proceeding. In a tool-using agent the natural place for that pause is the tool executor: the model may propose a call that moves money or deletes data, but the executor only acts after an approval callback says yes, and otherwise returns the refusal to the model as the observation. 

from typing import Callable


def gated(executor, approve: Callable[[str, dict], bool]):
    """Wrap an async tool executor so it runs only after human approval."""
    async def _run(**kwargs) -> str:
        if not approve(executor.__name__, kwargs):
            return f"REFUSED: a human reviewer did not approve {executor.__name__}({kwargs})"
        return await executor(**kwargs)
    return _run


async def delete_records(table: str) -> str:
    return f"deleted all rows in {table}"     # stands in for an irreversible action


def ask_console(name: str, args: dict) -> bool:
    return input(f"Approve {name}({args})? [y/N] ").strip().lower() == "y"


safe_delete = gated(delete_records, ask_console)   # register safe_delete, never delete_records

Kaizen also ships a HumanApprovalAgent with an approval_callback parameter, but in the installed release its run_async asks for approval of a placeholder decision without calling the model, so it demonstrates the callback shape rather than a working approval flow — the gated executor above is the pattern to use. Financial supervisors, including MAS, expect firms to keep appropriate human oversight over material AI-driven decisions; an approval gate is how that expectation becomes code.

Monitoring and logging

Every agent step — thought, action, observation — should be logged for debugging and audit. Kaizen's Delegate emits streaming events (text, tool start, tool end, completion, error), and LLMObservatory().agent.capture_run(delegate, prompt) records them as an AgentTrace that tool_usage, detect_loops and plot_trace analyse. This connects directly to the governance audit trails in Lesson 6.7.

Common Mistakes

Mistake 1: Too many tools

Agents perform better with 3-5 focused tools than 20 generic ones. With 20 tools, the LLM spends most of its reasoning capacity on tool selection rather than problem-solving. If you need more than 7 tools, consider splitting into multiple specialised agents (Lesson 6.6).

Mistake 2: No turn ceiling or budget

An agent stuck in a reasoning loop keeps calling the model, and every turn re-sends the growing context. Always set max_turns; on a priced provider also pass budget_limit_usd when the agent is constructed (setting it afterwards is not enforced). A good heuristic for the turn ceiling: estimate the steps the task needs and allow about 3x. Remember that on free local Ollama a dollar cap never trips — the turn ceiling is the control that actually stops a loop there.

Mistake 3: Treating agent output as authoritative

Agents hallucinate. The tool results are real (they come from actual code execution), but the agent's interpretation of those results can be wrong. "The model achieved 95% accuracy" might be correct, but "this means the model is ready for production" is the agent's opinion. Always verify critical conclusions against the raw tool outputs.

Mistake 4: Vague tool descriptions

The LLM selects tools based on their description field. "Processes data" is useless — the LLM cannot distinguish it from other data tools. "Load a CSV file and return shape, column types, null percentages, and descriptive statistics as a dictionary" tells the LLM exactly when this tool is appropriate and what to expect in the response.

Exercise A — Add a tool and see whether the agent uses it

Add a level_by_type tool that returns a cross-tabulation of question type (bridge / comparison) against difficulty level. Register it, then ask the agent "Are comparison questions harder than bridge questions?" and check in the trace whether it called the new tool.

Solution 
async def level_by_type(dataset_name: str = "qa_data") -> str:
    """Cross-tabulate question type against difficulty level (row counts)."""
    table = qa_data.group_by("type", "level").len().sort("type", "level")
    return str(table)


registry.register(
    name="level_by_type",
    description="Count HotpotQA questions by type (bridge/comparison) and difficulty level.",
    parameters={"type": "object", "properties": {"dataset_name": {"type": "string"}}, "required": []},
    executor=level_by_type,
)
agent_a = make_delegate(tools=registry, max_turns=6,
                        system_prompt="Use the tools to gather evidence before you answer.")
trace_a = await obs.agent.capture_run(
    agent_a, "Are comparison questions harder than bridge questions?", run_id="ex_a")

A tool-capable model should pick level_by_type because its description names exactly the two columns the question is about — the tool-usage table shows whether it did. If it calls run_query instead, sharpen the description; that is the "vague description" mistake in action. The answer itself must cite the counts in the tool output; the dataset is a 500-question sample, so the agent should say "in this sample".

Exercise B — Turn-ceiling sensitivity

Run the Step 2 task with three agents built with max_turns = 2, 4 and 12. For each, record turns used, tool calls, total tokens, and whether the run ended because of the ceiling. (A dollar budget would be the same experiment on a priced provider; on local Ollama it cannot trip.)

Solution 
import polars as pl

rows = []
for ceiling in (2, 4, 12):
    bounded = make_delegate(tools=registry, max_turns=ceiling,
                            system_prompt="Use the tools, one step at a time, then report.")
    tr = await obs.agent.capture_run(bounded, task, run_id=f"turns_{ceiling}")
    require_llm_trace(tr)
    steps = [ev for ev in tr.events if ev.kind in ("token", "tool_end", "error")]
    used = bounded.loop.usage.turns
    rows.append({
        "max_turns": ceiling,
        "turns_used": used,
        "tool_calls": len(tr.filter_kind("tool_start")),
        "tokens": bounded.loop.usage.total_tokens,
        "hit_ceiling": used >= ceiling and bool(steps) and steps[-1].kind != "token",
    })
print(pl.DataFrame(rows))

turns_used never exceeds max_turns — the ceiling holds whatever the model wants. With 2 turns the agent typically stops mid-investigation (its last step is a tool call, not a written answer), so hit_ceiling is True; with 12 it usually finishes on its own and uses fewer than 12 turns. Tokens grow faster than turns, because each turn re-sends the growing context — the quadratic-cost argument from the Math Foundations section, measured.

Exercise C — ChainOfThoughtAgent versus the ReAct agent

Ask both agents "How many comparison questions are in this HotpotQA sample, and what share of all questions is that?" Then compute the true answer with polars. Which agent's answer can you trust, and why?

Solution 
question = "How many comparison questions are in this HotpotQA sample, and what share of all questions is that?"

cot_result = require_agent_result(cot.run(problem=question), "ChainOfThoughtAgent")
react_agent = make_delegate(tools=registry, max_turns=6,
                            system_prompt="Use the tools to gather evidence before you answer.")
react_trace = await obs.agent.capture_run(react_agent, question, run_id="ex_c")
react_answer = "".join(ev.content or "" for ev in react_trace.events if ev.kind == "token")

n_comp = qa_data.filter(pl.col("type") == "comparison").height
print("truth:", n_comp, f"({n_comp / qa_data.height:.0%} of {qa_data.height})")

The chain-of-thought agent has never seen this sample, so whatever number it gives is a guess dressed as reasoning — its confidence field does not change that. The ReAct agent can call run_query("count question types") and quote the real count, which you can check against the polars line. Exercise D — Singapore context: an HDB resale analyst

Build a tool-using agent over the course's synthetic HDB resale teaching dataset (Module 1; 50,150 rows, 2015–2024). Give it two tools — median resale price by town, and a DataExplorer profile — and ask it which town has the highest median price and which columns have data-quality alerts.

Solution 
import polars as pl
from kailash_ml import DataExplorer
from kaizen_agents.delegate.loop import ToolRegistry
from shared import MLFPDataLoader
from shared.mlfp06._ollama_bootstrap import make_delegate

hdb = MLFPDataLoader().load("mlfp01", "hdb_resale.parquet")


async def median_price_by_town(top_n: int = 5) -> str:
    table = (hdb.group_by("town")
                .agg(pl.col("resale_price").median().alias("median_price"), pl.len().alias("sales"))
                .sort("median_price", descending=True)
                .head(int(top_n)))
    return str(table)


async def profile_hdb(dataset_name: str = "hdb_resale") -> str:
    profile = await DataExplorer().profile(hdb)
    return "\n".join(f"{a['type']}: {a.get('column', '')}" for a in profile.alerts)


hdb_tools = ToolRegistry()
hdb_tools.register(name="median_price_by_town",
                   description="Top towns by median HDB resale price, with number of sales.",
                   parameters={"type": "object", "properties": {"top_n": {"type": "integer"}}, "required": []},
                   executor=median_price_by_town)
hdb_tools.register(name="profile_hdb",
                   description="Data-quality alerts for the HDB resale dataset (DataExplorer).",
                   parameters={"type": "object", "properties": {"dataset_name": {"type": "string"}}, "required": []},
                   executor=profile_hdb)

hdb_agent = make_delegate(tools=hdb_tools, max_turns=6,
                          system_prompt="You are an HDB resale analyst. Use the tools; never invent prices.")
hdb_trace = await obs.agent.capture_run(
    hdb_agent, "Which town has the highest median resale price, and which columns "
               "have data-quality alerts?", run_id="ex_d")
print(await median_price_by_town(3))     # the ground truth to check the agent against

Running median_price_by_town(3) directly on the course file gives Toa Payoh (median S$973,887 over 1,463 sales), then Kallang/Whampoa and Bukit Timah — these are figures from the synthetic teaching data, not real HDB prices. The agent's answer is correct only if it names the same town and reports the alerts the profile actually returned — for this file, a highly skewed resale_price, duplicate rows, and several imbalanced categorical columns (town, flat_type, storey_range, flat_model). Notice what the profile does not flag: the impossible S$10 prices you found in Module 1 need an explicit range check, so an agent that claims "no data-quality problems" from this tool alone is over-reaching. A regression tool (the M3 TrainingPipeline) is the natural third tool; keep it out until you have split train and test data before any preprocessing, as Module 3 requires.

Reflection

You have built your first autonomous AI agent — a system that reasons about a task, selects and calls tools, observes results, and iterates until it has an answer. The three critical components are the ReAct loop (structured reasoning), function calling (structured tool interfaces), and bounds — a turn ceiling everywhere, a construction-time dollar budget on priced providers (structured safety). And you have learned to judge an agent by its trace, not by how convincing its prose sounds.

The agent design framework — goal, process, specialist, tools — is more important than the code. A well-designed agent with 3 tools outperforms a poorly-designed agent with 20. The specialist description is the single highest-leverage prompt engineering decision you make.

In Lesson 6.6, we move from single agents to multi-agent systems: teams of specialists coordinated by a supervisor, communicating through structured protocols, with shared and private memory. The data analyst agent you built today becomes one worker in a larger pipeline.
