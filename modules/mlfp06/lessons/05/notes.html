Speaker Notes — Lesson 6.5 AI Agents — ReAct, Tool Use, Function Calling

Total time: ~90 minutes  ·  8 slides  ·  ~11 min per slide average

The LLM starts acting in the world. Eight slides, long blocks: the ReAct loop, function calling with structured schemas, the design framework, and the Kaizen Delegate that makes it all real. The operational facts to land precisely: the Delegate's model comes from OLLAMA_CHAT_MODEL (never a hardcoded model=), budget_limit_usd is set at construction, and on free local Ollama every call is priced $0 — so dollar caps never trip; max_turns is the real limit.

Slide 1~2 minTitle

AI Agents — ReAct, Tool Use, Function Calling

Open with the outcome: "Build a ReAct agent with registered tools and hard limits. 6.4 answered questions from documents; today the model takes actions — searches, computes, and decides what to do next."

→ "The loop that makes it an agent."
Slide 2~12 minReAct trace

ReAct: a concrete reasoning trace

Walk the trace line by line — this is the lesson's foundation. Thought: reason about what's needed. Action: call a tool with arguments. Observation: read what came back. Repeat until the answer is assembled.

"Reasoning and acting interleaved. The thought is what separates an agent from a pipeline — the model decides what to do next based on what it just learned, not on a script you wrote. And the trace is your debugging artifact: when the agent goes wrong, read the thoughts."

Analogy: "A research assistant with a phone. They think about what they need, make a call (the tool), read the answer, think again. The loop ends when they can write the report."
→ "The mechanism: function calling."
Slide 3~12 minFunction calling

Function calling

Walk the code. The tool is plain Python — data_summary returns text. The ToolRegistry.register call has four parts: a name; a description — "the LLM reads this to choose; it's the tool's advertisement"; a parameters JSON Schema the LLM fills in; and the executor — the async callable you own.

"The LLM picks the tool and fills the arguments; your executor runs it. Structured schemas, not prompt parsing. Provider APIs add a tool_choice switch — auto, required, or a named function — and may return several calls in one turn: parallel function calling."

→ "Design before code."
Slide 4~12 minDesign framework

Agent design framework

Walk the four design questions. Goal: what is the agent supposed to achieve — one sentence, testable. Thought process: what reasoning steps should it follow? Specialist: be sharp — "data analysis researcher", not "researcher"; the system prompt's specificity is the agent's competence. Tools: versatile, fault-tolerant, with caching.

Then the safety rails: "A critic agent that reviews and requests revisions — Exercise 5.4 builds one. A human-in-the-loop pause before irreversible actions. And logged traces of every intermediate step. Design the rails when you design the agent, not after the first incident."

→ "Kaizen agents, live."
Slide 5~13 minKaizen agents

Kaizen agents

Walk the code. make_tools(load_hotpotqa()) builds the tool functions — data_summary, search_documents. Then make_delegate(tools=build_tool_registry(tools), system_prompt=..., max_turns=8). Two notes in the comments to read aloud: "bare callables register NOTHING — they must go through the registry. And the model comes from OLLAMA_CHAT_MODEL — there is no model= argument; the model is configuration."

Read the teal box carefully — it's the operational heart of the lesson: "A Delegate with a ToolRegistry is a ReAct loop — Exercise 5.1 proves it. Spend caps: budget_limit_usd goes in BaseAgentConfig at construction — setting it later is not enforced. And the honest local-lab consequence: on free local Ollama every call is priced $0, so dollar caps never trip — max_turns and token counts are the real limits here. For reasoning without tools, Kaizen's ChainOfThoughtAgent runs step-by- step reasoning before answering."

→ "The craft: tool design."
Slide 6~10 minTool design

Tool design principles

Walk the four principles. 3–5 tools max — more tools confuse the agent; every tool dilutes the choice. Clear descriptions — the LLM reads them to choose; write them like API documentation for a reader who's never seen your code. Error handling — tools should return errors as text, not crash; a crashed tool gives the agent nothing to reason from. Caching — avoid re-computing expensive operations across turns.

→ "Common mistakes."
Slide 7~9 minMistakes

Common mistakes

Walk the four. One: too many tools — agent performance degrades; back to the 3–5 rule. Two: no turn ceiling or budget — a looping agent keeps calling the model; cap max_turns and, on priced providers, the spend at construction. Three: trusting agent output — agents hallucinate; verify critical results, exactly as 6.4's grounding instruction did. Four: no observation logging — capture traces with LLMObservatory().agent.capture_run; an agent you can't replay is an agent you can't debug.

→ "Recap and bridge."
Slide 8~3 minRecap

What you can now do

Walk the checklist: build ReAct agents with custom tools, implement function calling with structured schemas, bound agents with turn ceilings and construction-time budgets, and design with the specialist framework. Tease 6.6: "Single agents compose into teams — multi-agent orchestration and MCP."

→ End of Lesson 6.5. Ten-minute break.
