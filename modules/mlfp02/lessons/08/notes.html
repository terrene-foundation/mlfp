Speaker Notes — Lesson 2.8 Capstone — Statistical Analysis Project

Total time: ~60 minutes  ·  14 slides  ·  ~4 min per slide average

The M2 capstone. Everything lands in one project: load, validate, engineer features with the Kailash engines, store them point-in-time, model with OLS, test hypotheses, and report. The guided walk is Option A (HDB resale valuation) with the exact Exercise 8 numbers — 3,536 impossible rows removed, R² 0.828, +9,096 per square metre. Keep the room on the numbers; they will reproduce them in Exercise 8.

Slide 1~1 minTitle

Capstone — Statistical Analysis Project

Open: "Seven lessons of statistics, one project. Today you'll see the whole pipeline — load to report — run end to end, with two new production tools: FeatureEngineer and FeatureStore." This is also the template for their capstone submission, so set that expectation.

Slide 2~3 minModule map

How Module 2 fits together

Walk the diagram by colour. Foundations (teal): 2.1 probability, 2.2 estimation. Inference (blue): 2.3 testing, 2.4 experiments. Modelling (amber): 2.5 linear, 2.6 logistic. Causal (rose): 2.7 CUPED and DiD. Every arrow feeds the capstone box.

→ "New tool one: FeatureEngineer."
Slide 3~4 minFeatureEngineer

FeatureEngineer

Walk the code. Load HDB via the ex_8 helper, index the rows, cast the date. Define a FeatureSchema naming the entity column and three base fields. Then FeatureEngineer(max_features=10): generate with temporal and interaction strategies adds month/day-of-week/hour columns and the area × lease-date interaction; select ranks the generated candidates against the target and keeps the top 3.

Read the teal box — this is the design philosophy of the whole course: "Domain knowledge decides which features. The engine handles how. And sanity-check the ranking: an _hour column is constant for monthly dates, so a high rank there would be a red flag, not a discovery."

→ "New tool two: FeatureStore."
Slide 4~4 minFeatureStore

FeatureStore: point-in-time correctness

Walk the code. The ex_8 helpers do the heavy lifting: compute_v1_features, validate_v1_features, and build_schema_v1 — which builds the kailash_ml.features.FeatureSchema the store accepts. create_feature_store wraps a DataFlow instance; materialize_features writes the versioned rows.

Then the key call: get_features(schema, timestamp=when) with 1 Jan 2023. "Rows stamped later never come back. The store answers the question 'what did we know as of this date?' — which is exactly the question training data must answer."

Read the blue box: "Point-in-time correctness prevents data leakage in time-series problems."

→ "Why that matters, in one picture."
Slide 5~3 minPIT picture

Point-in-time correctness

Walk the timeline. The training date $T$ splits the world. Green zone to the left: the feature lookback window — safe, only past data. Blue zone just right of $T$: the label window, where the outcome is observed. Red hatched zone beyond: the forbidden future.

Point at the two examples. Safe: lag_1, rolling_mean_6 — computed from the lookback window only. Leakage: next_month_price — uses data after the training date. "The store's get_features at timestamp $T$ is the mechanical enforcement of this picture: only rows stamped at or before $T$ come back."

→ "Step 1."
Slide 7~3 minStep 1 load

Step 1: Load and profile

Walk the code. Load, compute the v1 features, validate — and read the printed numbers: the cleaned frame is (46,614, 16), and 3,536 impossible rows were removed. Then profile with run_profile and count the alerts.

Read the footer slowly: "Validation drops sentinel prices — the 10-dollar and 9-million-dollar sales from M1 — and impossible leases before any statistic is computed. Cleaning after modelling is not cleaning; it's cosmetics."

→ "Step 2 — look at the data."
Slide 8~2 minStep 2 EDA

Step 2: EDA

Walk the code: three candidate predictors correlated against price. Floor area: r = 0.910 — overwhelming. Storey midpoint: 0.009 — nothing. Remaining lease: −0.008 — nothing.

Read the footer: "Shortlist predictors with a domain rationale; correlation is a first look, not the test. The hypothesis tests come in Step 5, inside the model, where area is held fixed."

→ "Step 3 — store the features."
Slide 9~2 minStep 3 store

Step 3: Engineer + store features

Walk the code. Storey midpoint and remaining lease years were already engineered in Step 1 — this step materialises the frame into the store. Read the printout: row count and the first 16 characters of the lineage hash.

"The lineage hash is your reproducibility receipt: which code, which data version, which schema. When someone asks 'where did this training set come from?', the store answers."

→ "Step 4 — the model."
Slide 10~3 minStep 4 model

Step 4: Model

Walk the code. prepare_design_matrix assembles $[1, X]$ and drops nulls; fit_ols is the 2.5 normal equations packaged for the project. Read the fit: R² = 0.828, adjusted R² = 0.828, F ≈ 75,042.

"Three predictors, 83% of price variance explained. The adjusted R² matches to three decimals because $n$ is huge and $k$ is tiny — the complexity penalty barely bites. Compare with the 0.22 you'd get on the unvalidated data: cleaning was worth 60 points of R²."

→ "Step 5 — test the coefficients."
Slide 11~4 minStep 5 tests

Step 5: Hypothesis tests

Walk the printed table. Floor area: β = +9,096 dollars per square metre, t = 474.4, p < 1e-300 — the overwhelming effect. Storey midpoint: −24, p = 0.54 — nothing once area is held fixed. Remaining lease: +7, p = 0.84 — nothing either.

Read the footer as the reporting template: "Each extra square metre adds about SGD 9,100 to the price (95% CI SGD 9,060–9,130). Effect size, interval, then p-value — in that order. And the ceteris paribus lesson from 2.5 is back: storey and lease show no effect once area is in the model — their raw correlations with price were already near zero."

→ "Step 6 — the report."
Slide 12~3 minStep 6 report

Step 6: Report

Walk the five sections. Summary — two or three sentences, what did you find. Key predictors — direction, magnitude, significance. Model fit — R², adjusted R², F. Limitations — missing data, selection bias, confounders; every honest report has this section. Recommendation — what should the stakeholder actually do.

Read the green box: "A non-technical reader should understand every sentence in the report. If you can't say it without jargon, you don't understand it well enough yet."

→ "Three ways capstones go wrong."
Slide 13~2 minMistakes

Three mistakes to avoid

Walk the three red boxes — they map to the three tools of the day. One: feature leakage from the future — the FeatureStore exists precisely to prevent this. Two: features without domain rationale — FeatureEngineer generates candidates; you decide which make sense. Three: p-values without effect sizes — "+9,096 per square metre" informs; "p < 0.001" alone does not.
