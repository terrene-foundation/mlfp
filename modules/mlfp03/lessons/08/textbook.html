Lesson 3.8 Production Pipeline — DataFlow, Drift, and Deployment

A model in a notebook is a prototype. A model in production persists results to a database, monitors for drift, documents its limitations, and reports prediction uncertainty. This lesson completes the production story: DataFlow for database persistence, DriftMonitor for detecting distribution shift with PSI and KS tests, Model Cards for documentation, and conformal prediction for prediction sets with a coverage guarantee that needs no distributional assumption beyond exchangeability.

DataFlow: Persisting ML Results

⚙ Kailash Engine

DataFlow provides zero-config database operations. Define a model with @db.model, and DataFlow generates CRUD operations automatically. For ML, this means persisting predictions, model metadata, and evaluation results to a database without writing SQL.

A short primer on async / await

Database calls spend most of their time waiting for disk or network. DataFlow, ConnectionManager, ModelRegistry and DriftMonitor therefore expose coroutines: functions defined with async def that can pause at each await while the event loop runs other work. Three rules cover everything in this lesson:

  1. await is only legal inside an async def function (Jupyter is the exception: its cells already run inside an event loop, so top-level await works there and nowhere else).
  2. From a normal script, start the coroutine once with asyncio.run(main()).
  3. Open a connection, use it, and close it in a finally: block, so a failure does not leave the database locked.
import asyncio

async def main():
    await db.initialize()          # pauses until the tables exist
    rows = await db.express.list("Prediction")
    return len(rows)

n_rows = asyncio.run(main())       # the one entry point from plain Python

Persisting predictions

import asyncio
from pathlib import Path
from dataflow import DataFlow

# Use an ABSOLUTE path: a relative "sqlite:///monitoring.db" is resolved
# from the filesystem root and fails with "unable to open database file"
db = DataFlow(f"sqlite:///{Path('monitoring.db').resolve()}")

@db.model
class Prediction:
    id: int
    customer_id: str
    probability: float
    model_version: int

async def crud_demo():
    await db.initialize()
    # Create — model name as a string, fields as a dict
    await db.express.create("Prediction", {
        "customer_id": "C001", "probability": 0.73, "model_version": 1})
    await db.express.create("Prediction", {
        "customer_id": "C002", "probability": 0.12, "model_version": 1})

    # Read — MongoDB-style filter operators
    high_risk = await db.express.list(
        "Prediction", filter={"probability": {"$gt": 0.7}})
    row = high_risk[0]                       # C001

    # Update and delete — by primary key
    await db.express.update("Prediction", row["id"], {"probability": 0.68})
    await db.express.delete("Prediction", row["id"])
    return await db.express.list("Prediction")   # only C002 is left

remaining = asyncio.run(crud_demo())

The package is imported as dataflow (there is no kailash_dataflow module and no field() helper): plain type annotations define the columns, and id: int is the primary key. In Exercise 3.8 the same pattern stores one DriftCheck row per monitoring run, so alerts can be read back, acknowledged (updated) and cleaned up (deleted) later.

DriftMonitor

A model trained on January data may fail on July data if the distribution has shifted. DriftMonitor detects this using two statistical tests:

PSI: Population Stability Index

$$\text{PSI} = \sum_{i=1}^{k} (p_i - q_i) \cdot \ln\!\left(\frac{p_i}{q_i}\right)$$
$p_i$ = proportion in bin $i$ (reference) $q_i$ = proportion in bin $i$ (current)
PSIInterpretationAction
< 0.1No significant shiftContinue serving
0.1 - 0.25Moderate shiftInvestigate
> 0.25Significant shiftRetrain

These bands are an industry rule of thumb, not a statistical test. Exercise 3.8 alerts at PSI > 0.2. PSI is undefined when a bin is empty on either side, so implementations add a small floor to every proportion — and the bin edges must be extended to ±∞ so that current values outside the training range are counted, not silently dropped.

KS test: Kolmogorov-Smirnov

The KS test compares two empirical CDFs and returns the maximum vertical distance between them. A small p-value indicates the distributions differ. Two cautions for monitoring. First, with tens of thousands of rows the test detects even trivial shifts, so a significant p-value is a prompt to look at PSI and model performance, not a verdict. Second, you test every feature at once: 33 tests at $\alpha = 0.05$ produce a false alarm on a clean batch most of the time. Exercise 3.8 therefore uses a Bonferroni-style cut-off of 0.001 (about $0.05 / 33$). 

import asyncio
from pathlib import Path
from kailash.db import ConnectionManager
from kailash_ml import DriftMonitor
from shared.mlfp03.ex_8 import load_credit_split, to_frame

split = load_credit_split()       # leak-free credit data, 33 features
X_train, X_test = split["X_train"], split["X_test"]
names = split["feature_names"]

# A production batch where income has jumped by 3 standard deviations
batch = X_test.copy()
i = names.index("income_sgd")
batch[:, i] += 3 * X_train[:, i].std()

async def check():
    # The monitor gets its OWN SQLite file (absolute path). Sharing the
    # model registry's file fails: the registry already has a table with
    # the same name and a different layout.
    conn = ConnectionManager(f"sqlite:///{Path('drift.db').resolve()}")
    await conn.initialize()
    try:
        monitor = DriftMonitor(conn, tenant_id="_single",
                               psi_threshold=0.2,
                               ks_threshold=0.001)   # Bonferroni for 33 tests
        await monitor.set_reference_data(
            "credit_scorer", to_frame(X_train, names), names)
        for label, X_batch in (("clean", X_test), ("income +3 sd", batch)):
            report = await monitor.check_drift(
                "credit_scorer", to_frame(X_batch, names))
            flagged = [(f.feature_name, round(f.psi, 2))
                       for f in report.feature_results if f.drift_detected]
            print(label, report.overall_drift_detected, flagged)
    finally:
        await conn.close()

asyncio.run(check())

On the clean test batch nothing is flagged, so no false alarm across 33 features. On the shifted batch only income_sgd is flagged, with a PSI around 14 and severity "severe": every value has moved past the top of the training range, far beyond the 0.25 "retrain" line. In Exercise 3.8 each check is also written to a DataFlow DriftCheck table so the alert can be read back, acknowledged and audited later.

Model Cards

A Model Card (Mitchell et al., 2019, "Model Cards for Model Reporting") documents a model's purpose, performance, limitations, and fairness findings. Every model promoted to production should have one. The paper proposes nine sections:

SectionContents for the credit model
Model detailsName, registry version, type, training date, owner
Intended useDecision support for unsecured-loan applications; out-of-scope uses
FactorsGroups the model is evaluated across: race, gender, age band
MetricsAUC-ROC, AUC-PR, Brier; the decision threshold $t^* = 0.130$ and the cost matrix behind it
Evaluation dataThe held-out test split, its size and default rate
Training dataSource, size, preprocessing, the columns dropped as leaks
Quantitative analysesMeasured per-group results: disparate impact, TPR/FPR, calibration by group
Ethical considerationsWho is harmed by each error type; the human sign-off for failed fairness screens
Caveats and recommendationsKnown failure modes, data gaps, drift thresholds and retraining triggers

Every number in the card must be measured on the registered model, not typed in — Exercise 3.8 writes the card from the same evaluation run, and its readiness check fails if the card's AUC differs from the live model's.

Conformal Prediction

Traditional ML gives a point prediction: "this customer will default with probability 0.73". Conformal prediction adds a prediction set (for regression, an interval) with a coverage guarantee:

🔵 Theory — What the guarantee says, and what it needs

Split conformal prediction needs no model of the data distribution. It needs one assumption: the calibration rows and the new row are exchangeable (for example, drawn i.i.d. from the same distribution). Pick a miscoverage level $\alpha$ — the error rate you accept, so $\alpha = 0.10$ targets 90% coverage. Compute a nonconformity score on $n$ held-out calibration rows, take the finite-sample-corrected quantile

$$\hat{q} \;=\; \text{the } \tfrac{\lceil (n+1)(1-\alpha) \rceil}{n} \text{ quantile of the calibration scores,}$$

and include in the prediction set every label whose score is at most $\hat{q}$. Then $P(Y_{\text{new}} \in C(X_{\text{new}})) \ge 1 - \alpha$. The guarantee is marginal: it holds on average over new applicants, not for each applicant or each subgroup. It also breaks under drift, because drift is exactly a violation of exchangeability — which is why conformal coverage belongs on the monitoring dashboard.

For a classifier, the usual score is one minus the probability the model gave to the true class. On the credit model: 

import numpy as np

# model fitted on X_fit; X_cal / y_cal: held-out rows it never saw
p_cal = model.predict_proba(X_cal)[:, 1]
scores = np.where(y_cal == 1, 1 - p_cal, p_cal)   # 1 - p(true class)
n, alpha = len(scores), 0.10
q_hat = np.quantile(scores, np.ceil((n + 1) * (1 - alpha)) / n,
                    method="higher")

p_new = model.predict_proba(X_test)[:, 1]
has_default = (1 - p_new) <= q_hat     # "default" is in the set
has_repay = p_new <= q_hat             # "repay" is in the set
both = has_default & has_repay         # the model cannot tell: route to a human

On the leak-free credit data (LightGBM, 20% of train held back for calibration, $\alpha = 0.10$), $\hat{q} \approx 0.62$ and test coverage comes out at 89.9% — the guarantee holds. About 94% of applicants get a single-label set and 6% get {default, repay}, the cases to route to a human; no set is empty. Now split the coverage by outcome: 99.6% for applicants who repaid, but only 25% for those who defaulted. That is what marginal means: the 90% is an average dominated by the majority class. If you need a guarantee per class, calibrate a separate $\hat{q}$ per class (class-conditional, or "Mondrian", conformal).

The Full Production Pipeline

📝 Goal

Take the credit model to production the way Exercise 3.8 does: a calibrated model, decisions at the cost-optimal threshold, a registry with a rollback path, persisted predictions, a drift monitor, a model card built from measured numbers, and a readiness check that a human signs off.

Step 1 — Calibrate, then decide at t* = 0.130.

Train the LightGBM through TrainingPipeline, calibrate it on held-out training rows with TrainingPipeline.calibrate (Lesson 3.5), and decline when the calibrated default probability is at least $t^* = c_{FP}/(c_{FP} + c_{FN}) = 1500/11500 \approx 0.130$. Calibration comes first, because $t^*$ is only valid on honest probabilities.

Step 2 — Register, promote, and keep a rollback target. 
async def promote_and_rollback(registry, name, new_version, old_version):
    # A new version starts in "staging"; promote it once its gate passes
    await registry.promote_model(name, new_version, "production",
                                 reason="readiness gates passed")
    # Rollback: retire the bad version, bring the previous one back
    # through staging (archived -> staging -> production)
    await registry.promote_model(name, new_version, "archived",
                                 reason="AUC dropped after release")
    await registry.promote_model(name, old_version, "staging",
                                 reason="rollback candidate")
    await registry.promote_model(name, old_version, "production",
                                 reason="rollback")
    return await registry.get_model(name, stage="production")

There is no registry.promote; every stage change is a promote_model(name, version, target_stage, reason=...) call, so the reason for each move is recorded. Promoting a new version to production automatically moves the previous production version to archived — that archived version is your rollback target.

Step 3 — Persist predictions and monitor drift.

Score each batch, write the scores with DataFlow (db.express.create("Prediction", {...}), absolute SQLite path), and run DriftMonitor.check_drift against the training reference, with the monitor on its own database file and KS threshold 0.001. Write each check to a DriftCheck table so the alert has an audit trail.

Step 4 — Conformal sets for the uncertain cases.

Use the split-conformal recipe above with $\alpha = 0.10$. Applicants whose set is {default, repay} — about 6% here — go to a human underwriter instead of an automatic decision.

Step 5 — Model card from measured numbers.

Fill the nine Mitchell sections from the evaluation run itself: test AUC-ROC, AUC-PR and Brier, the threshold 0.130 and its cost matrix, per-group disparate impact, TPR/FPR and calibration for race, gender and age band (Lesson 3.6), the drift thresholds, and the known limitations. Never type a number into the card that the code did not compute.

Step 6 — Readiness: 11 computed gates plus human sign-off.

Exercise 3.8 turns the deployment checklist into 11 boolean gates, each an expression over evidence:

  1. Test AUC-ROC meets the 0.70 policy floor.
  2. Calibrated: Brier beats the base-rate forecast.
  3. Conformal coverage within 2 points of 90%.
  4. The model card exists.
  5. The card describes this model (its AUC matches the live model's).
  6. The card reports race, gender and age fairness.
  7. Four-fifths rule passes for race and gender.
  8. Calibrated within every group (gap under 0.02).
  9. The drift monitor is quiet on clean data and alarms on a shift.
  10. Reproducible: the live registry model equals the retrained model.
  11. A rollback target (an archived version) exists.

A missing piece of evidence fails its gate; a gate written as True checks nothing. What code cannot decide is listed separately for human sign-off. The failing age-band disparate-impact screen from Lesson 3.6 goes to the model-risk owner, who either accepts the trade-off in writing or blocks the release. Deployment needs all 11 gates green and that signature.

Common Mistakes

⚠ Mistake 1: No drift monitoring

A model without drift monitoring degrades silently. By the time someone notices, the predictions have been wrong for weeks.

⚠ Mistake 2: PSI on the wrong features

Monitor the features the model actually uses, not all features in the dataset. Irrelevant features drifting do not affect predictions.

⚠ Mistake 3: Point predictions without uncertainty

"This applicant will default with probability 0.73" hides how sure the model is. A conformal prediction set — {default}, {repay}, or {default, repay} when the model cannot tell at the chosen error rate — makes the uncertainty explicit and tells you which cases to route to a human. It costs one held-out calibration set.
