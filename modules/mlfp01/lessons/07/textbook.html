Lesson 1.7 Automated Data Profiling

For six lessons you have profiled data by hand: describe, head, null counts, correlations, histograms. Today you meet the engine that does all of it in one call and adds eight kinds of quality alerts you might not have thought to check. DataExplorer is the first Kailash engine you use as a consumer rather than a builder — the same shift you will make again and again as the course progresses toward higher-level tools.

Why This Matters

Real datasets are messy. Sensors drop readings. Systems change schemas mid-stream. Manual entry produces "N/A", "n/a", "unknown", and blank cells in the same column. Dates arrive as three different string formats. Economic indicators spike during crises and break your assumptions about normality. Every one of these issues costs hours to diagnose if you find it late; it costs seconds to catch if you find it early.

The ritual you built in Lesson 1.1 — shape, columns, head, describe — catches the obvious problems. But it misses the subtler ones: a column with 12% nulls (bad but not empty), a feature that is 98% zero, two columns that are 99% correlated and add nothing independent, a category so rare it barely appears. DataExplorer catches those automatically. It does not catch everything: a date column with three formats hidden inside looks to the profiler like ordinary unique text, so that check stays yours.

Core Concepts

Engines as services

Up to now you have used Polars primitives and written your own logic. DataExplorer is the first time you consume a service — a pre-built engine whose job is to look at any DataFrame and tell you what is wrong with it. You do not need to know how the internals work; you only need to know the shape of the input, the shape of the output, and the configuration knobs you can turn.

🟢 Foundations

The shift from "write it yourself" to "configure a service" is the single biggest productivity jump in data engineering. Services handle edge cases you would not think of, scale to data sizes you cannot profile manually, and come with test coverage you cannot match in a notebook. The trade-off is that you cede control to the service's defaults. That is why you need to understand what it is doing — so you can tune it when the defaults are wrong.

The eight alert types

DataExplorer runs each of its eight quality checks and returns an alert whenever a value is greater than its threshold (for imbalanced, smaller than). Each alert is a dictionary with a type, a column (or columns for a correlated pair), a value, and a severity ("warning" or "info").

AlertFires when (default)MeaningFix
high_nullsnull share > 0.05Column has too many missing valuesImpute, drop, or flag
constantunique values ≤ 1Column carries no informationDrop the column
high_cardinalityunique / rows > 0.9Near-unique columnBin, hash, or treat as ID
high_skewness|skew| > 2.0Extreme right or left tailLog-transform or winsorise
high_zeroszero share > 0.5Column has many exact zerosCheck if zero is real or missing-coded
high_correlation|r| > 0.9 for a pairPair of columns is near-collinearDrop one, or flag for VIF check

🟢 Outliers are not an alert

These eight are the complete list. There is no "outlier" alert and no "type mismatch" alert. Outliers are reported per column instead: every numeric ColumnProfile carries outlier_count and outlier_pct. Look there when you want them.

AlertConfig: tuning the thresholds

The default thresholds are set for typical tabular ML data. Your data is probably not typical. Economic time series are structurally correlated (high_correlation fires constantly with defaults). Property data has long right tails (high_skewness fires constantly). Every dataset has its own shape, and every shape has its own sensible thresholds. 

from kailash_ml import AlertConfig, DataExplorer

alert_config = AlertConfig(
    high_correlation_threshold=0.95,   # raise from 0.90 default (fires less)
    high_null_pct_threshold=0.10,      # relax from 0.05 default (fires less)
    skewness_threshold=3.0,            # raise from 2.0 default (fires less)
    zero_pct_threshold=0.30,           # lower from 0.5 default (fires more)
)

explorer = DataExplorer(alert_config=alert_config)

The other fields and their defaults: constant_threshold=1 (a unique-value count, not a fraction), high_cardinality_ratio=0.9, imbalance_ratio_threshold=0.1 and duplicate_pct_threshold=0.0.

Every threshold should be a deliberate choice, not a default. Document the rationale in a comment so a reviewer understands why you picked those numbers.

Running a profile: the sync wrapper

The quickest way to profile a DataFrame is the course helper run_profile. It works the same in a script, in VS Code and in Jupyter/Colab: 

from shared import MLFPDataLoader, run_profile

cpi = MLFPDataLoader().load("mlfp01", "sg_cpi.csv")
profile = run_profile(cpi)                            # default thresholds
profile = run_profile(cpi, alert_config=alert_config) # your thresholds

print(profile.n_rows, profile.n_columns, len(profile.alerts))

Under the hood: async profiling

DataExplorer.profile() is an async function. Async is a Python feature for running operations concurrently: while one task waits, another can make progress. run_profile hides that from you, but you will meet async code in later modules, so here is what it looks like in a plain script: 

import asyncio

from kailash_ml import DataExplorer


async def profile_dataset(df):
    explorer = DataExplorer(alert_config=alert_config)
    profile = await explorer.profile(df)
    return profile

profile = asyncio.run(profile_dataset(cpi))   # in a .py script

Two pieces of vocabulary: async def marks the function as asynchronous; the await keyword waits for the result of another async operation. asyncio.run(...) creates an event loop, runs the function, and returns the result. One catch: Jupyter and Colab already run an event loop, so there asyncio.run raises RuntimeError. In a notebook cell you can write profile = await explorer.profile(df) directly — or simply use run_profile, which handles both cases.

🔵 Theory: sync vs async

Synchronous code runs top to bottom, blocking on every operation. Asynchronous code can suspend at an await point and let other work run in the meantime. Async pays off when tasks spend time waiting — on a network, a disk, a database — for example when profiling several remote files at once. For a single in-memory DataFrame it is not faster; it is simply the interface the engine exposes. Full async is a chapter of its own — for this lesson, the wrapper and the template above are all you need.

Error handling with try / except

Real profiling pipelines fail. The file might not exist. The schema might have changed. A column might have values the profiler cannot handle. Python's try / except lets you catch errors gracefully and continue — or re-raise with a clearer message. 

try:
    df = loader.load("mlfp01", "nonexistent.csv")   # expect-error
    profile = run_profile(df)
except FileNotFoundError as e:
    print(f"Dataset not available: {e}")
    profile = None
except ValueError as e:
    print(f"Bad schema: {e}")
    profile = None

Name each exception you expect and handle it explicitly. Never write a bare except: pass — it swallows every error, including the ones you did not anticipate, and the pipeline fails later with no clue why.

The Kailash Engine: DataExplorer in detail

⚙ Kailash Engine

DataExplorer profiles any Polars DataFrame and returns a DataProfile object with structured metadata: per-column statistics (type, mean, std, nulls, unique count, skewness), pairwise correlations (Pearson and Spearman), duplicate counts, and a list of alerts. It also supports compare(df_a, df_b) for differences between two snapshots, to_html(df) for a shareable report and visualize(df) for the underlying charts. All four methods are async; shared.run_profile, run_compare and run_report are their sync wrappers. Module 4's DriftMonitor applies the same idea — compare two snapshots — to production data.

Worked Example: Profiling Messy Singapore Economic Data

📝 Goal

Load three messy Singapore economic datasets (monthly CPI, quarterly employment, daily FX rates), merge them onto a monthly spine, and profile the result with DataExplorer. Interpret every alert, decide what to do about it, and confirm with compare() that cleaning actually helped. These are synthetic course datasets modelled on published statistics: illustrative values, realistic mess.

Step 1.

Load the three datasets and inspect them individually. Notice the deliberately different reporting frequencies and date formats.

import polars as pl
from kailash_ml import AlertConfig
from shared import MLFPDataLoader, run_compare, run_profile, run_report

loader = MLFPDataLoader()
cpi = loader.load("mlfp01", "sg_cpi.csv")
employment = loader.load("mlfp01", "sg_employment.csv")
fx_rates = loader.load("mlfp01", "sg_fx_rates.csv")

print(f"CPI:         {cpi.height:,} rows (monthly)")
print(f"Employment:  {employment.height:,} rows (quarterly)")
print(f"FX:          {fx_rates.height:,} rows (daily)")
CPI:         300 rows (monthly)
Employment:  93 rows (quarterly)
FX:          1,305 rows (daily)

Three different keys, too: CPI has a text date column, employment has a text quarter column such as "2000 Q1", and FX has a proper Date column. Each CPI column is exactly 5% null (15 of 300 rows), and FX covers only 2020–2024 while CPI runs from 2000 to 2024.

Step 2.

Normalise the messy CPI date column. The source has three formats in one column: 01/2000, 2000-02, and 200003.

cpi = cpi.with_columns(
    pl.col("date")
    .str.replace(r"^(\d{2})/(\d{4})$", "$2-$1-01")
    .str.replace(r"^(\d{4})(\d{2})$", "$1-$2-01")
    .str.replace(r"^(\d{4})-(\d{2})$", "$1-$2-01")
    .str.to_date("%Y-%m-%d")
    .alias("date")
)
print(cpi["date"].min(), cpi["date"].max(), cpi["date"].null_count())
# → 2000-01-01 2024-12-01 0

Chained str.replace calls walk through the three possible formats, converting each to YYYY-MM-01. Then str.to_date parses the clean form. Zero nulls after parsing proves every row matched one of the three patterns. This is the pattern for any "three formats in one column" mess — and note that DataExplorer will not detect mixed date formats for you; to the profiler they just look like unique text.

Step 3.

Turn each quarter into its first month, then merge everything onto a monthly spine: forward-fill the quarterly employment series and average the daily FX rates per month.

# "2000 Q1" → 2000-01-01, "2000 Q2" → 2000-04-01, ...
employment = employment.with_columns(
    pl.date(
        pl.col("quarter").str.slice(0, 4).cast(pl.Int32),
        (pl.col("quarter").str.slice(6, 1).cast(pl.Int32) - 1) * 3 + 1,
        1,
    ).alias("date")
).drop("quarter")

monthly_spine = pl.DataFrame({
    "date": pl.date_range(cpi["date"].min(), cpi["date"].max(),
                          interval="1mo", eager=True)
})

# Forward-fill quarterly employment onto the monthly spine
employment_monthly = (
    monthly_spine.join(employment, on="date", how="left")
    .sort("date")
    .with_columns([
        pl.col(c).forward_fill() for c in employment.columns if c != "date"
    ])
)

# Aggregate daily FX to monthly mean
fx_monthly = (
    fx_rates.group_by(pl.col("date").dt.truncate("1mo"))
    .agg([pl.col(c).mean() for c in fx_rates.columns if c != "date"])
)

economic = (
    cpi.join(employment_monthly, on="date", how="left")
    .join(fx_monthly, on="date", how="left")
    .sort("date")
)
print(economic.shape)   # (300, 13)
Step 4.

Configure alerts for the specifics of economic data. Structural correlation is expected, so only near-collinearity should fire.

alert_config = AlertConfig(
    # Macro indicators move together — raise from the 0.90 default
    high_correlation_threshold=0.95,
    # Relax from the 0.05 default: a few missing months are tolerable here
    high_null_pct_threshold=0.10,
    # A column with <= 1 distinct value is a pipeline failure (default 1)
    constant_threshold=1,
    # Raise from the 2.0 default: only flag severe tails
    skewness_threshold=3.0,
    # Stricter than the 0.5 default: flag columns from 30% zeros
    zero_pct_threshold=0.30,
)

Watch the direction of each change. Raising a threshold makes an alert fire less often; lowering it makes it fire more. Moving high_null_pct_threshold from 0.05 to 0.10 relaxes the null check — it does not tighten it.

Step 5.

Run the profiler and read every alert.

Step 6.

Translate each alert into a decision.

  • high_nulls on the four FX columns (80%). Not a quality defect — a coverage gap. FX data starts in 2020, CPI in 2000, so 240 of 300 months have no FX value. Decision: restrict FX analysis to 2020 onwards, or drop FX from the 25-year analysis. Imputing 20 years of exchange rates would be fabrication.
  • No high_nulls on the CPI columns. They are exactly 5% null, and the rule is "null share greater than the threshold" — so they stay silent even at the 0.05 default. A silent profiler is not proof of clean data.
  • high_correlation among CPI components and median_income. Prices and incomes trend upwards together over 25 years — a domain fact, not a defect. Keep the columns; flag them for a multicollinearity (VIF) check before any regression.
  • high_correlation between CPI and gbp_sgd (0.957). Computed on only the 60 months where both exist. Two trending series over a short window correlate easily; treat this one as spurious until shown otherwise.
  • high_cardinality (info). Every date is unique and continuous measurements are nearly unique. Expected; accept.

Notice what is not on the list. With the default AlertConfig the same data produces 28 alerts, including high_skewness on employment_rate (−2.25) and labour_force (−2.13); our 3.0 threshold deliberately silences those. And outliers never appear as an alert: each column profile reports outlier_count and outlier_pct instead (for example profile.columns[1].outlier_count).

Step 7.

Compare original vs cleaned. Clean the CPI table (parse dates, sort, interpolate the gaps) and ask compare() whether the cleaning changed what you intended — and nothing else.

cpi_raw = loader.load("mlfp01", "sg_cpi.csv")

Mathematical Foundations: Skewness

Two of the alerts above — high_skewness and high_correlation — deserve a short mathematical tour.

Skewness

Skewness measures the asymmetry of a distribution. A symmetric distribution has zero skewness; a right tail has positive skewness; a left tail has negative skewness.

$$g_1 = \frac{1}{n} \sum_{i=1}^n \left(\frac{x_i - \bar{x}}{s}\right)^3$$
$\bar{x}$ — mean $s$ — standard deviation cubed so that sign is preserved

Why cube the standardised deviations? Cubing preserves sign (unlike squaring) so positive deviations (right tail) and negative deviations (left tail) do not cancel. The third power also exaggerates distant observations, which is exactly what we want — outliers should pull the metric more than average observations.

Rules of thumb: $|g_1| < 0.5$ is approximately symmetric; $0.5 \le |g_1| < 1$ is moderately skewed; $|g_1| \ge 1$ is highly skewed. The engine's default alert threshold is $|g_1| > 2$; the worked example raises it to 3 so that only severe tails are flagged.

Pearson correlation

The correlation coefficient $r$ measures the strength of a linear relationship between two variables:

$$r = \frac{\sum (x_i - \bar{x})(y_i - \bar{y})}{\sqrt{\sum (x_i - \bar{x})^2 \sum (y_i - \bar{y})^2}}$$
$r \in [-1, 1]$ $r = 1$ perfect positive $r = -1$ perfect negative

$|r| \ge 0.95$ is near-collinearity — the two variables carry almost identical information. Including both in a regression model inflates the coefficient standard errors (the variance inflation factor, VIF, you will meet in Module 2) and makes interpretation unreliable.

Common Mistakes

⚠ Mistake 1: Ignoring alerts because defaults fire too often

Default thresholds are a starting point, not scripture. If the defaults produce 40 false alarms, tune them. Do not silence them; retune them so each alert still means something.

⚠ Mistake 2: Profiling before cleaning basic issues

Mixed date formats, unparseable numbers, and obviously wrong types should be cleaned before profiling. Otherwise the profile shows garbage-in statistics and the real issues hide in the noise.

⚠ Mistake 3: Fixing correlation alerts by dropping columns automatically

"cpi_all_items correlates 0.99 with median_income, so I'll drop income" — but both simply trend upwards over 25 years, and they measure different things. Alerts prompt investigation, not automated removal. Understand the relationship first.

⚠ Mistake 4: Using sync profile() in an async context

profile() is async. Calling it without await produces a coroutine object, not a profile, and nothing useful happens. In a script, wrap it in asyncio.run(...); in Jupyter or Colab, asyncio.run raises "cannot be called from a running event loop" — use await directly or, anywhere, the helper shared.run_profile().

Reflection

Automation is how you scale good habits. The 30-second ritual from Lesson 1.1 works for one dataset; it does not work for the hundreds of datasets a real data professional touches in a year. DataExplorer scales the ritual: one call, every column, eight alert types. You still have to interpret each alert and decide what to do — the engine does not make domain judgements for you — but it surfaces the decisions automatically instead of leaving them for you to stumble over later.

The mental shift today is toward consuming services instead of building them. Every higher-level Kailash engine you meet from here on (PreprocessingPipeline, TrainingPipeline, InferenceServer, DriftMonitor) follows the same pattern: a small API, a focused job, tunable configuration, and opinionated defaults. Your job is to know what the engine does, what it does not do, and how to configure it for your problem.

Lesson 1.8 is the capstone. You will combine everything from this module — filter, aggregate, join, window, visualise, profile — into a single end-to-end pipeline that turns messy Singapore taxi trip data into a clean, model-ready dataset with an HTML report at the end. It is your first taste of production-shaped work.
