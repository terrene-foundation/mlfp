Lesson 3.5 Model Evaluation, Imbalance, and Calibration

A model that reports 0.8 should mean "80% chance". A model with 92% accuracy on 10%-positive data is not necessarily any good. In the next 75 minutes you will learn how to evaluate classifiers honestly on imbalanced data using precision, recall, F1, ROC, PR, and log-loss; handle imbalance with SMOTE, cost-sensitive learning, and focal loss; and calibrate model probabilities so they can be used as decision thresholds. The running dataset is the synthetic Singapore credit data (12.9% default rate) with an illustrative business cost matrix: missing a default costs S$10,000; wrongly declining a good applicant costs S$1,500.

The Confusion Matrix and Its Offspring

Every classification metric ultimately comes from the 2×2 confusion matrix that counts predictions against labels.

The formulas you must know

$$\text{Accuracy} = \frac{TP + TN}{TP + TN + FP + FN}$$ $$\text{Precision} = \frac{TP}{TP + FP} \qquad \text{Recall} = \frac{TP}{TP + FN}$$ $$F_1 = 2 \cdot \frac{\text{Precision} \cdot \text{Recall}}{\text{Precision} + \text{Recall}}$$

Precision asks "when I predicted positive, how often was I right?". Recall asks "of the actual positives, how many did I catch?". F1 is their harmonic mean — it punishes extreme imbalance between the two.

🟢 Foundations — Accuracy is lying on imbalanced data

On our 12.9%-positive credit data, predicting "no default" for every single applicant scores 87% accuracy. F1 for that same classifier is exactly zero (precision = 0, recall = 0). If you only report accuracy, you cannot distinguish a useful model from the one that gives up.

ROC and PR Curves: Threshold-Free Views

A classifier outputs a probability score. A threshold turns that score into a hard prediction. Different thresholds give different precision/recall trade-offs. Instead of picking one threshold, ROC and PR curves show the trade-off at every threshold.

Why ROC-AUC fails on imbalanced data

ROC is defined by the true positive rate (TPR = recall) against the false positive rate ($FPR = FP / (FP + TN)$). When the negative class is huge, $TN$ dwarfs $FP$ and $FPR$ barely moves even when $FP$ grows by thousands. So the ROC curve still hugs the upper-left corner — the AUC looks great — while precision is quietly atrocious.

Precision-recall has no such blind spot. It ignores $TN$ entirely. $\text{Precision} = TP/(TP + FP)$ punishes every false positive, regardless of how many true negatives there are. For the credit data:

  • A model with no information (a constant or random score): ROC-AUC = 0.5, AP ≈ 0.13 (the base rate).
  • The leak-free LightGBM from Lesson 3.4: ROC-AUC about 0.78 — sounds decent — but AP about 0.37: at most recall levels, well under half of the flagged applicants actually default.
  • Report AP next to its base rate as your honest number; ROC-AUC is a ranking sanity check.
🔵 Theory — AUC-PR vs AUC-ROC

AUC-PR (average precision) is the integral of precision over the recall axis. On highly imbalanced data, two models with nearly identical ROC-AUC can have very different PR-AUCs, because PR-AUC is dominated by how clean the top of the ranking is. The rule of thumb: if the positive class is below 20%, report PR-AUC; if above 20%, either works.

Handling Imbalance: Four Techniques

1. SMOTE — synthetic minority oversampling

SMOTE (Chawla et al., 2002) creates synthetic minority-class examples by interpolating between each minority example and its $k$ nearest minority neighbours. For a minority point $x_i$ with a neighbour $x_{nn}$, a synthetic point is $x_{\text{new}} = x_i + \alpha(x_{nn} - x_i)$ for $\alpha \in [0, 1]$.

Pros: the training set becomes balanced without duplicating existing points. Cons: SMOTE breaks badly when (a) minority points are clustered in dense regions and SMOTE interpolates across the gap creating implausible samples, (b) the feature space has high dimensionality and "nearest" is no longer informative (the curse again), (c) minority points are noise, in which case SMOTE amplifies the noise.

⚠ SMOTE is not a free lunch

SMOTE-trained models are not automatically better. Modern practitioners usually prefer cost-sensitive learning or focal loss — both of which do not fabricate data. SMOTE remains useful when you must use a model family that ignores sample weights; otherwise pick a technique that adjusts the loss directly.

2. Cost-sensitive learning — weights in the loss

If missing a default costs far more than a false alarm, you can tell the model that. Pass sample_weight or class_weight into the classifier: 

from sklearn.ensemble import RandomForestClassifier
# class_weight='balanced' sets weights inversely proportional to class frequencies
model = RandomForestClassifier(class_weight="balanced")

# Or a custom cost ratio that matches the business (c_FN / c_FP)
model = RandomForestClassifier(class_weight={0: 1, 1: 10_000 / 1_500})

The loss is now $\sum_i w_i L(y_i, \hat{y}_i)$ and the optimiser naturally cares more about the high-weight examples. No fake data — but the predicted probabilities are no longer the true default rates: up-weighting defaulters $w$-fold pushes every score upwards. Keep that in mind for the threshold below.

3. Focal loss — down-weight easy examples

Focal loss (Lin et al., 2017) was invented for dense object detection where the imbalance is extreme (1000+ background boxes per foreground box). It modifies binary cross-entropy to down-weight already-correctly- classified examples:

$$\text{FL}(p_t) \;=\; -\alpha_t \,(1 - p_t)^\gamma\, \log(p_t)$$

where $p_t$ is the predicted probability for the true class, $\alpha_t$ balances classes, and $\gamma \ge 0$ is the focusing parameter. When $\gamma = 0$, focal loss is just weighted cross-entropy. When $\gamma > 0$, the factor $(1 - p_t)^\gamma$ is tiny for well-classified examples and close to 1 for hard ones. The loss automatically focuses on the hard cases.

🔵 Theory — Why focal loss works

Standard cross-entropy on an easy example with $p_t = 0.9$ still contributes $-\log(0.9) \approx 0.1$ — enough that over millions of easy examples it dominates the gradient. Focal loss with $\gamma = 2$ multiplies that by $(1 - 0.9)^2 = 0.01$, reducing the contribution 100×. Hard examples with $p_t = 0.3$ get multiplied by $(1 - 0.3)^2 = 0.49$ — barely changed. Net effect: the gradient is dominated by hard examples and the model keeps learning on them.

4. Threshold tuning from the business cost matrix

The default threshold 0.5 is rarely optimal. With a cost matrix $(c_{FP}, c_{FN})$, the expected cost of predicting positive is:

$$\mathbb{E}[\text{cost}] = c_{FP}(1 - p) + c_{FN} \cdot 0$$

and of predicting negative is:

$$\mathbb{E}[\text{cost}] = c_{FP} \cdot 0 + c_{FN} \cdot p$$

You should predict positive iff $c_{FN} \cdot p > c_{FP}(1 - p)$, i.e. when $p > c_{FP} / (c_{FP} + c_{FN})$. For our cost matrix that is $t^* = 1500 / 11500 \approx 0.130$ — not 0.5. A one-in-eight chance of default is already enough to decline, because a missed default costs 6.7 times a wrongly declined applicant.

⚠ Never count the costs twice

$t^*$ assumes $p$ is a calibrated probability from an unweighted loss. Class weights already move the decision boundary: a model trained with defaulters up-weighted $w$-fold has its natural 0.5 cut-off sitting near the true-probability point $1/(1 + w)$. Apply $t^*$ to such a model and you apply the cost ratio twice, flagging far too many applicants. Use one of: (a) an unweighted model with $t^*$; (b) a weighted model with threshold 0.5 or a validation-tuned one; (c) a weighted model, recalibrated on held-out rows (which removes the weight's shift), then $t^*$. The worked example below measures all three.

Calibration: Making Probabilities Mean What They Say

A model is well-calibrated if, among the samples it predicts with probability $p$, exactly a fraction $p$ are positive. Many models are not. Class-weighted or resampled models over-predict the positive class across the board. Boosted trees and naive Bayes often show a sigmoid-shaped distortion (Niculescu-Mizil & Caruana, 2005). Miscalibration is harmless if you only care about rankings but catastrophic if you feed the probabilities into cost calculations or thresholds like $t^*$.

🟢 Foundations — Reading a reliability diagram

Predicted probability on the $x$-axis, observed frequency on the $y$-axis. A point below the diagonal means the predicted probabilities in that bin are too high; a point above means they are too low. Over-confidence — probabilities pushed too close to 0 and 1 — shows as points above the diagonal in the low bins and below it in the high bins (a flattened, "transposed S"). Under-confidence — probabilities squeezed towards the middle — is the opposite S: below in the low bins, above in the high bins. That second shape is the classic boosted-tree distortion, and a sigmoid fit (Platt scaling) undoes it.

Platt scaling — fit a sigmoid on the model scores

Platt scaling (1999) fits a sigmoid $\sigma(Ax + B)$ to the raw model score $x$. Find the two parameters $A, B$ by maximum likelihood on a held-out calibration set. Cheap, and works when the miscalibration has an approximately sigmoidal shape.

Isotonic regression — non-parametric calibration

When the miscalibration is not sigmoidal, isotonic regression fits a non-decreasing piecewise-constant function instead. More flexible than Platt, but needs more data (at least a few hundred samples per calibration fold) to avoid overfitting.

kailash-ml's TrainingPipeline.calibrate wraps an already-fitted model (it is not re-trained) and fits the calibration map on rows the model never saw — here, 20% of the training split held back for the purpose: 

import asyncio
import polars as pl
from kailash_ml import TrainingPipeline

# model: fitted on X_fit; X_cal / y_cal: the held-out 20% of TRAIN
cols = [f"f{i}" for i in range(X_cal.shape[1])]
X_cal_df = pl.DataFrame(X_cal, schema=cols, orient="row")
y_cal_s = pl.Series("default", y_cal)

tp = TrainingPipeline(feature_store=None, registry=None)
platt = asyncio.run(tp.calibrate(model, X_cal_df, y_cal_s, method="sigmoid"))
iso = asyncio.run(tp.calibrate(model, X_cal_df, y_cal_s, method="isotonic"))
p_iso = iso.predict_proba(X_te)[:, 1]

The Brier score — a proper scoring rule

The Brier score is the mean squared error between predicted probability and actual label:

$$\text{BS} \;=\; \frac{1}{N}\sum_{i=1}^{N}(p_i - y_i)^2$$

Lower is better, and 0 means perfect prediction, not merely perfect calibration. Brier mixes calibration with discrimination (Brier = reliability − resolution + uncertainty): a perfectly calibrated model that always predicts the base rate $\bar{y}$ still scores $\bar{y}(1 - \bar{y})$ — about 0.112 on the credit data. To judge calibration itself, use the reliability diagram or the expected calibration error (ECE). Brier is a proper scoring rule: its expectation is minimised by reporting the true probability, so a model that cheats by pushing everything to 0 or 1 scores worse than one that reports honest uncertainty. Report it before and after calibration.

Worked Example: End-to-End on Credit Scoring

📝 Goal

Train LightGBM on the leak-free credit data (12.9% default) three ways — unweighted, cost-weighted, and cost-weighted then recalibrated — and measure AUC-PR, Brier and the business cost per application at the default threshold 0.5 and at $t^* = 0.130$. Find out which combinations are right and which count the costs twice. This mirrors Exercise 3.5.

Step 1 — Split three ways. 
import asyncio
import numpy as np, polars as pl, lightgbm as lgb
from sklearn.model_selection import train_test_split
from sklearn.metrics import average_precision_score, brier_score_loss
from kailash_ml import TrainingPipeline
from shared.mlfp03.ex_5 import load_credit_splits

# customer_id and the leak column are dropped inside the loader
X_tr, y_tr, X_te, y_te, pos_rate = load_credit_splits()   # 80k / 20k rows
# 20% of TRAIN is held back to fit the calibration map
X_fit, X_cal, y_fit, y_cal = train_test_split(
    X_tr, y_tr, test_size=0.2, stratify=y_tr, random_state=42)

C_FP, C_FN = 1_500, 10_000             # illustrative S$ costs
t_star = C_FP / (C_FP + C_FN)          # 0.130

def cost_per_app(p, t):
    pred = (p >= t).astype(int)
    fp = ((pred == 1) & (y_te == 0)).sum()
    fn = ((pred == 0) & (y_te == 1)).sum()
    return (fp * C_FP + fn * C_FN) / len(y_te)
Step 2 — Unweighted and cost-weighted boosters. 
plain = lgb.LGBMClassifier(n_estimators=300, random_state=42, verbose=-1)
plain.fit(X_fit, y_fit)
p_plain = plain.predict_proba(X_te)[:, 1]

weighted = lgb.LGBMClassifier(n_estimators=300, random_state=42, verbose=-1,
                              scale_pos_weight=(1 - pos_rate) / pos_rate)
weighted.fit(X_fit, y_fit)
p_w = weighted.predict_proba(X_te)[:, 1]
print(p_plain.mean(), p_w.mean())   # about 0.13 vs 0.34 (true rate 0.13)

Note the direction of scale_pos_weight: negatives over positives (about 6.8 here), so defaulters get more weight. The weighted model's average predicted probability is about 0.34 against a true default rate of 0.13 — its scores are no longer probabilities.

Step 3 — Recalibrate the weighted model on the held-out rows. 
cols = [f"f{i}" for i in range(X_cal.shape[1])]
tp = TrainingPipeline(feature_store=None, registry=None)
cal = asyncio.run(tp.calibrate(
    weighted, pl.DataFrame(X_cal, schema=cols, orient="row"),
    pl.Series("default", y_cal), method="isotonic"))
p_cal = cal.predict_proba(X_te)[:, 1]

for name, p in [("unweighted", p_plain), ("weighted", p_w),
                ("weighted + isotonic", p_cal)]:
    print(f"{name:20s} AP {average_precision_score(y_te, p):.3f}  "
          f"Brier {brier_score_loss(y_te, p):.4f}  "
          f"cost@0.5 {cost_per_app(p, 0.5):5.0f}  "
          f"cost@t* {cost_per_app(p, t_star):5.0f}")
unweighted           AP 0.363  Brier 0.0986  cost@0.5  1167  cost@t*   769
weighted             AP 0.370  Brier 0.1651  cost@0.5   783  cost@t*   982
weighted + isotonic  AP 0.357  Brier 0.0984  cost@0.5  1222  cost@t*   783

Reading the table (cost in S$ per application; approving everybody costs about 1,307):

  • The ranking barely changes. AUC-PR stays between 0.36 and 0.37 for all three: weighting and calibration move probabilities, not the order of applicants.
  • Each correct recipe lands near S$770–785. Unweighted + $t^*$ (769), weighted + 0.5 (783) and weighted + recalibration + $t^*$ (783) are three routes to the same decision boundary.
  • Double counting is expensive. Weighted + $t^*$ applies the cost ratio twice: it wrongly declines about 12,000 of the roughly 17,400 good applicants in the test set and costs 982 per application — about a quarter more than the correct recipes.
  • Calibration repairs the probabilities. The weighted model's Brier score (0.165) is worse than predicting the base rate for everyone (0.112); isotonic calibration on held-out rows brings it back to 0.098, the same as the unweighted model. That is why the calibrated model must use $t^*$, not 0.5: with honest probabilities, 0.5 throws away the cost asymmetry (1,222).

In a real project you would choose the threshold on out-of-fold predictions of the training set (cross_val_predict) and touch the test set once, as Exercise 3.5 does — the analytic $t^*$ is the starting point that tuning should confirm.

Stacking and Blending

Everything so far squeezes more out of one model. The last lever in this lesson combines several. Blending averages the base models' predicted probabilities (a soft vote), optionally with weights. Stacking trains a meta-model — usually a logistic regression — that learns how much to trust each base model, using their out-of-fold predictions as its input features:

$$\hat{p}_{\text{stack}}(x) \;=\; \sigma\Bigl(b_0 + \sum_{k=1}^{K} b_k\, \hat{p}_k^{\text{OOF}}(x)\Bigr)$$

The out-of-fold part is not optional. If the meta-model saw in-sample predictions, the most overfit base model would look the most accurate, and the meta-model would learn to trust exactly the wrong one. Gains come from diverse base models whose errors differ — a booster, a linear model and a forest — not from three copies of one booster. 

import polars as pl
from sklearn.ensemble import RandomForestClassifier
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from kailash_ml import EnsembleEngine

# EnsembleEngine requires fitted base models (it then clones and refits
# them on its own training split)
lgbm = lgb.LGBMClassifier(n_estimators=300, random_state=42,
                          verbose=-1).fit(X_tr, y_tr)
logreg = make_pipeline(StandardScaler(),
                       LogisticRegression(max_iter=1000)).fit(X_tr, y_tr)
forest = RandomForestClassifier(n_estimators=100, min_samples_leaf=20,
                                random_state=42).fit(X_tr, y_tr)

cols = [f"f{i}" for i in range(X_tr.shape[1])]
train_df = pl.DataFrame(X_tr, schema=cols, orient="row").with_columns(
    default=pl.Series(y_tr))

engine = EnsembleEngine()
stacked = engine.stack([lgbm, logreg, forest], train_df, target="default",
                       fold=5)          # meta-model on 5-fold OOF predictions
blended = engine.blend([lgbm, logreg, forest], train_df, target="default",
                       method="soft")   # plain probability average
print(stacked.metrics, blended.metrics)

Pass only training rows: both methods carve their own 20% holdout from train_df to report their metrics, and the test set is still used once, at the very end. On the credit data both reach an AUC of about 0.79 on that internal holdout, against about 0.78 for the single LightGBM on the test set — a gain of roughly 0.01–0.02, measured on different rows, so confirm it on the test set before you pay for three models in production. Stacking and blending rarely rescue weak features; they polish strong ones.

Common Mistakes

⚠ Mistake 1 — Reporting accuracy on imbalanced data

Already warned twice in the course. This one is the cheque your stakeholders will cash — so you must not write it in the first place. Report AUC-PR and Brier after calibration.

⚠ Mistake 2 — SMOTE-ing the test set

SMOTE is training-only. If you SMOTE the test set, you are measuring the model against synthetic points that do not exist in production. Split first, SMOTE the training split only.

⚠ Mistake 3 — Leaving the threshold at 0.5

For calibrated probabilities, 0.5 is the Bayes-optimal threshold exactly when the two error costs are equal — class balance does not matter, because the posterior already accounts for the base rate. Error costs are rarely equal in real problems. Derive the threshold from the cost matrix, or tune it on out-of-fold predictions.

Try It Yourself

🎯 Exercise A — Derive the cost-optimal threshold

Given $(c_{FP}, c_{FN}) = (1\,500, 10\,000)$, show that you should predict positive iff $p > 0.130$. Now repeat for (1000, 1000): what threshold? And for (100, 10)?

Solution

Predict positive when the expected cost of doing so, $c_{FP}(1 - p)$, is below the expected cost of predicting negative, $c_{FN}\,p$. Rearranging: $p > c_{FP}/(c_{FP} + c_{FN})$. (1500, 10000) → 1500/11500 = 0.130. (1000, 1000) → 0.5: equal costs give the familiar threshold. (100, 10) → 100/110 ≈ 0.909: when a false alarm costs ten times a miss, only flag near-certain cases. All three assume calibrated probabilities.

Train an XGBoost with a custom focal-loss objective at $\gamma \in \{0, 1, 2, 5\}$. Plot AUC-PR and Brier against $\gamma$. Does focal loss improve the ranking, the calibration, both, or neither on the credit data? Why must you recalibrate before applying $t^*$?
