Speaker Notes — Lesson 1.8 Data Pipelines and End-to-End Project

Total time: ~60 minutes  ·  20 slides  ·  ~3 min per slide average

This is the capstone. Every skill from Lessons 1.1 through 1.7 appears in one pipeline. The pace is faster because the tools are familiar. The new content — null handling, ETL, REST APIs, PreprocessingPipeline — connects to what they already know. Run the full pipeline live if possible; seeing all the pieces click together is the emotional payoff of Module 1.

Data Pipelines and End-to-End Project

"This is the finale of Module 1. Everything you have learned converges into one pipeline. By the end of this lesson you will have built a complete data pipeline that takes 50,000 messy taxi trip records and produces a clean, model-ready dataset with an HTML report."

If beginners look nervous: "You already know every individual step. Today we just connect them."
→ "The five stages."

Five stages, one pipeline

Walk the diagram left to right, with the real numbers it carries: "Extract — 50,000 rows, 12 columns, planted defects. Profile — 12 alerts from DataExplorer, including a correlation of minus one between latitude and longitude, which should be impossible. Transform — down to 43,934 clean rows with hour, weekday and duration engineered. Visualise and report — the deliverables."

Point out the lesson connection for each stage: "Extract — that is Lesson 1.1's data loading. Profile — 1.7's DataExplorer. Transform — 1.2 through 1.5's Polars plus the new tools today. Visualise — 1.6's charts. Report — new today, and just HTML output. The bottom strip is the promise: data quality measurably improves at each stage."

→ "What is ETL?"
Slide 3~2 minETL definition

ETL: the universal data pattern

"ETL stands for Extract, Transform, Load. It is the standard name for what we are building today. Every company that works with data runs ETL pipelines — the tools change from team to team, but the structure never does. Learn the shape once; recognise it everywhere."

→ "The first new tool: null handling."
Slide 4~3 minNull handling

Null handling: three tools

Walk the table. Then show the code. "is_null() tells you where the holes are. fill_null() fills them. drop_nulls() removes rows with holes. The order matters: inspect first, then decide whether to fill or drop."

Walk the three code examples — each encodes a decision: "A missing tip almost certainly means no tip — fill with zero. A missing CPI month in a sorted time series — forward-fill carries the last reading forward. A missing distance with 50,000 rows — the median is a robust stand-in. The fill is never mechanical; it is a claim about what the null means."

Emphasise the rule: "Never drop nulls without checking how many there are. If 30% of rows have nulls, you are throwing away a third of your data."

For beginners: "Think of nulls as blank cells in a spreadsheet. You can fill them with a reasonable guess, or you can delete the whole row. Filling is usually better."
→ "Which filling strategy?"
Slide 5~3 minImputation strategies

Which imputation strategy?

Walk the boxes. Forward-fill for time-series data — it assumes continuity, which is exactly right for a CPI series and exactly wrong for unordered rows. Median for cross-sectional data — robust where the mean is not. Group-aware median — per zone, per town — is the least biased when groups differ.

The bottom box: dropping is the last resort — a few percent of uninformative rows, verified with null_count() first.

→ "Where does data come from? Not always a CSV."
Slide 6~3 minREST APIs

Extracting data from APIs

"Many datasets are live services. Singapore's OneMap API gives you geolocation for any address, and its search endpoint needs no key. The pattern: send a GET request with query parameters, get JSON back. GET asks for data; POST sends data in the request body."

Point at the two safety lines: "timeout=10 — a slow server cannot hang your pipeline. raise_for_status() — a 404 or 500 becomes an exception you can catch with Lesson 1.7's try/except, not silent garbage parsed as data."

Run it live if you have network; otherwise say plainly that the response counts on screen are examples — live numbers vary as the service data changes.

If beginners are confused by APIs: "Think of it as typing a URL in your browser and getting data back instead of a webpage. The URL is the API endpoint. The parameters are the search terms."
→ "How to turn JSON into a DataFrame."
Slide 7~2 minJSON to DataFrame

JSON → DataFrame

Walk the code. "Take the list of dictionaries from the JSON response, create a DataFrame, select and rename the columns you need, fix the types. pl.DataFrame(list_of_dicts) is the whole trick — the dict keys become column names. The coordinates arrive as text, so cast(pl.Float64) makes them numbers you can compute with."

→ "Now the second Kailash engine."
Slide 8~3 minPreprocessingPipeline

PreprocessingPipeline: automated preparation

"Just like DataExplorer automates profiling, PreprocessingPipeline automates preparation — turning a clean table into model-ready data. The constructor takes no arguments. One call to setup() detects numeric versus categorical columns, imputes nulls, one-hot encodes, scales, and splits into train_data and test_data."

Two things to state precisely. First: "setup() needs a target column — this engine prepares data for a model. It does not repair bad rows; negative fares and duplicate IDs are cleaned with the Polars you already know, before the pipeline."

Second, the shape change: "7 columns in, 44 out — one-hot encoding expands payment_type and pickup_zone into binary indicator columns. And result.task_type prints 'regression' — the engine inferred it from the numeric target."

→ "A critical distinction."
Slide 9~3 minsetup vs transform

setup() vs transform()

This is one of the most important concepts in the entire course. Walk the diagram slowly. "setup() learns — the medians, the category sets, the scaling statistics. transform() applies what was learned to new rows. The pairing is the whole game: learn on training rows, apply to test rows."

Then the warning on the slide, word for word: "setup() learns from every row you pass, and splits afterwards. So hold out your test rows first, and pass only training rows to setup(). If test rows reach setup, their statistics leak into the learned rules, and your evaluation stops being honest. That is data leakage — Module 3 holds you to it."

For experts: "This is the same reason you never standardise before splitting. The course's shared helpers (split_then_preprocess and friends) wrap exactly this order — split, fit on train, transform test — so the exercises can never get it backwards."
→ "Time to build the pipeline. First, meet the data."
Slide 10~3 minThe taxi dataset

The dataset: Singapore taxi trips

Introduce it honestly, as the slide does: "A synthetic trip log built for this course — the zone names and coordinates are realistic Singapore places, but the trips are not real records. 50,000 rows, 12 columns: timestamps, zones, distance, fare, tip, payment, passengers, coordinates."

Read the planted-defect list as the hunt briefing: "250 rows with latitude and longitude swapped. 1,000 non-positive fares. 500 passenger counts below 1. 500 trips dated in the future — 2025 to 2027. 15 spellings of 4 payment methods. 500 rows sharing trip_ids. Plus nulls in the zones and tips. Seven defect types — your pipeline must find and handle every one."

For beginners: "Predict first. Before we profile, which of these do you think DataExplorer will catch automatically — and which need human eyes? Hold your answer for two slides."
→ "Step 1 — extract."
Slide 11~2 minStep 1: Extract

Step 1: Extract

Deliberately anticlimactic — that is the point. "Same loader, same pattern, one line. (50000, 12). By now this should feel boring. Boring is good — boring means the skill is yours."

Note the one wrinkle the slide flags in the pipeline diagram: the timestamps are stored as text. Parsing them is Step 3's job.

→ "Step 2 — profile."
Slide 12~3 minStep 2: Profile

Step 2: Profile

Run it live. 12 alerts fire. Read the interesting ones aloud: "high skewness on distance_km. high_nulls on tip_sgd — 78% null. Skew on both coordinate columns. And the smoking gun: high_correlation between pickup_latitude and pickup_longitude, r = minus 1.00."

Decode it together: "A perfect negative correlation between a latitude and a longitude is physically odd — these are independent quantities. That is the fingerprint of the 250 swapped rows: for those rows, the latitude is a longitude. The profiler found a GPS defect without knowing what GPS is."

Close the loop with the predictions from slide 10: "Negative fares raised no alert — a fare of −49 is statistically unremarkable to the engine. describe()'s min finds them. Engine first, eyes second — you need both."

→ "Step 3 — transform."
Slide 13~4 minStep 3: Transform

Step 3: Transform

Walk the chain block by block, one auditable step per defect: "Parse the two timestamp columns from text. Repair the swapped coordinates — a Singapore latitude can never exceed about 1.5, so a 'latitude' above 100 is unambiguously a longitude; swap those pairs back. Normalise the 15 payment spellings into 4 labels with lowercase matching. Filter: positive fares, at least one passenger, trips before 2025, and no duplicated trip_ids. Fill the null tips with zero and the null zones with 'Unknown'."

Then the feature engineering the slide's diagram promised: "From the parsed timestamps, derive hour, day of week, and trip duration in minutes. One caution that costs students marks every cohort: Polars dt.weekday() is ISO numbering — Monday is 1, Sunday is 7 — so the weekend filter is >= 6, and Friday is 5. Get this wrong and every weekday chart is silently mislabelled."

For experts: "Notice the design — each defect gets exactly one step, and each step is independently checkable. When a cleaning stage fails review, you can name the line. That is the difference between cleaning and hoping."
→ "Step 4 — prepare for a model."
Slide 14~3 minStep 4: PreprocessingPipeline

Step 4: PreprocessingPipeline

Walk the split-first pattern in the code: "Select the seven feature columns plus the target. Shuffle with a seed. Hold out a fifth of the rows as test. Then create the pipeline and call setup() on the training rows only."

Read the output: "(38,038, 7) becomes (38,038, 44) — one-hot encoding expanded payment_type and pickup_zone. And pipeline.transform(test_rows) applies the same learned rules to 9,509 test rows. The test rows never reached setup(), so nothing about them leaked into the medians, category sets, or scaling statistics."

→ "Step 5 — visualise."
Slide 15~3 minStep 5: Visualise

Step 5: Visualise demand by hour

Build the hourly aggregation and show the chart. Then read it honestly: "Every hour has between about 1,917 and 2,054 trips. Flat. There is no morning peak and no evening peak in this synthetic log — a real dispatch feed would show both."

Land the professional habit: "The chart says 'no peak'. Report what the data shows, not what you expected. If you write 'demand peaks at 8am' because taxis usually peak at 8am, you have invented a fact. This is the same discipline as Lesson 1.5's seasonality test: patterns are claims you must show, not stories you tell."

→ "Step 6 — verify the cleaning worked."
Slide 16~3 minStep 6: Re-profile

Step 6: Re-profile and compare

Run the re-profile and the comparison. Read it the way the slide teaches: "12 alerts before, 12 after — same count, different alerts. The coordinate skew and the impossible r = −1.00 are gone, and something new is visible: distance_km versus fare_sgd at r = 0.97. The real relationship was there all along, masked by the defects. And the shape check: 50,000 rows became 43,934 — about 5% dropped, each one accounted for by a filter you wrote."

The rule to repeat: "Always re-profile after cleaning — and read the alerts, not just the count. A flat count can hide a completely changed list. Cleaning can also introduce issues; the re-profile is where you catch your own mistake."

→ "How to structure a real project."
Slide 17~3 minProject structure

Structuring the project

"When a pipeline grows beyond 50 lines, split it into modules. Each file has one job: extract.py loads data, transform.py cleans and engineers, visualise.py makes charts, report.py writes the HTML, and main.py orchestrates. The layout on screen is the same five-stage pipeline from Slide 2, rendered as files."

Give the reproducibility test: "Delete the outputs, run main.py, get the same report back. If that fails, there is hidden state somewhere — a hand-edited file, a hardcoded path — and it will fail in production too."

→ "The four lines that run it all."
Slide 18~2 minOrchestrator

The orchestrator: main.py

Read the four lines of orchestration: "Load. Clean. Chart. Report. Each function lives in its own module, is independently testable, and can be swapped without touching the others — a new data source changes extract.py and nothing else."

Zoom out as the slide does: "Every production data pipeline looks like this at the top level. The tools get fancier — schedulers, orchestration frameworks, the Kailash workflow engine in later modules — but the top-level shape stays these four lines."

→ "Traps."
Slide 19~2 minMistakes

Four mistakes to avoid

Walk each one quickly. Mistake 2 (passing test rows to setup()) is the most important — it will come back in every module. Mistake 3 (hardcoded file paths) is why the data loader exists: "A pipeline that only works on your laptop is not a pipeline."
