Speaker Notes — Lesson 1.7 Automated Data Profiling

Total time: ~50 minutes  ·  16 slides  ·  ~3 min per slide average

This lesson marks a shift from hand-built exploration to engine-powered automation. Learners who have been writing describe() and null_count() for six lessons should feel the relief of having one engine do it all. Experts should appreciate the configurable thresholds and the compare() feature. Use the messy CPI dataset throughout — a synthetic course dataset modelled on published statistics, with three date formats in one column and exactly 5% nulls. Its value is that the mess is realistic while the values are illustrative.

Slide 1~2 minTitle slide

Automated Data Profiling

Open with: "For six lessons you have been the profiler — inspecting shape, columns, nulls, distributions. Today you meet the engine that does all of it in one call. DataExplorer checks every column for eight kinds of data quality problems and gives you a structured report."

Set expectations: "By the end of this lesson you will be able to profile any dataset, tune the alert thresholds, and compare two versions of a dataset — before and after cleaning."

If beginners look overwhelmed by 'engine': "Think of it as a pre-built function that does in one line what took you 20 lines before. You don't need to understand how it works internally — just what it gives you and how to configure it."
→ "Why do we need automation?"
Slide 2~3 minManual vs automated

Manual profiling does not scale

Walk the diagram. Left side: what they have been doing. Right side: what DataExplorer does. Emphasise the gap: "Manual profiling catches the obvious — nulls, shape, basic stats. But it is easy to skip checks: duplicate rows, a column that is mostly zeros, two columns that are 99.8% correlated, a category present in 1% of rows. Those are the issues that cost you hours downstream when your model behaves strangely."

Anchor it in the lesson's dataset: "By hand, would you check whether the CPI components correlate with each other? Whether the date column is nearly unique? DataExplorer checks all of it, every column, every time — and the same call works on every dataset you will ever load."

→ "Here's how the engine is structured."
Slide 3~3 minArchitecture diagram

DataExplorer in one picture

Walk the flow: "DataFrame in, three things out — alerts, statistics, and optionally a comparison. The alerts are the headline news. The statistics are the detail behind each alert. The comparison is for when you have two versions of the data."

Point out AlertConfig sitting inside the engine: "This is how you tune what counts as an alert. Default thresholds are sensible starting points but every domain has different expectations."

For experts: mention that DataExplorer is async internally (it profiles columns in parallel) but the sync wrapper hides that. The async API is available for advanced users who want to integrate profiling into async pipelines.
→ "What exactly does it check for?"
Slide 4~4 minEight alert types

Eight alert types

Walk the table row by row, with the course-data example for each:

  1. "high_nulls: null share above 5%. The CPI columns are exactly 5% null — the rule is strictly greater-than, so they stay silent at the default. Tighten to 2% and they fire."
  2. "constant: at most 1 unique value. A column that is all 'SG' carries no information — drop it. Note the threshold is a count of unique values, not a fraction."
  3. "high_skewness: |skew| above 2.0. HDB resale_price hits 11.4 — the planted S$10 and S$9M records from Lesson 1.1."
  4. "high_zeros: more than half the values are zero. A tip column that is mostly 0 — worth checking whether zero means 'no tip' or 'not recorded'."
  5. "high_cardinality: unique-values-per-row above 0.9 — a near-unique column. The CPI date column scores 1.00: every value is distinct text."
  6. "high_correlation: |r| above 0.9 for a column pair. cpi_all_items and cpi_housing correlate at 0.998 — a domain fact to note, not automatically a defect."
  7. "duplicates: any duplicate rows. The HDB data carries 300."
  8. "imbalanced: rarest category under 10%. HDB flat_type is flagged — MULTI-GENERATION is about 1% of sales."

Two honest limitations to say aloud, because they are on the slide: "Outliers are not an alert — each column reports an outlier_count statistic for you to judge. And mixed date formats are not detected at all — the engine sees unique text, not three formats. That check stays yours."

For beginners: "Don't memorise the thresholds. Memorise the eight kinds of problem. If you can name the problem, you can configure the threshold later."
→ "Let's run it."
Slide 5~3 minFirst profile — code

Running your first profile

Run this live. The dataset is sg_cpi.csv — 300 monthly CPI rows, synthetic but realistically messy. Walk each line: "Load the data, hand it to run_profile, print the alerts."

Explain the wrapper once, clearly: "DataExplorer's methods are async — a Python feature from a later module. run_profile(df) is a small course wrapper that runs the async profile for you, so it works identically in a script and in Colab. Same story for run_compare later."

When the 11 alerts print, read them aloud and point at the access pattern: "Each alert is a dict — keys are type, column (or columns, for a correlated pair), value, severity. So it is alert['type'], not alert.type — and the .get('column', .get('columns')) idiom handles both shapes."

→ "Let's look at the full profile output."
Slide 6~3 minProfile output diagram

What the profile returns

Walk the two boxes. Left: the alerts list — the headlines, with i for info and ⚠ for warning. Right: the per-column statistics — the detail. "For every column you get mean, std, null percentage, skewness, and an outlier_count. The alerts are just the statistics that crossed a threshold."

Show the programmatic access: profile.columns["cpi_all_items"].mean reads a single statistic; profile.correlation_matrix and profile.duplicate_count sit alongside. This is how you build automated cleaning rules from a profile.

→ "Now let's tune the thresholds."
Slide 7~3 minAlertConfig

Configuring thresholds

"Default thresholds are the engine's opinion. Your domain might disagree. Economic data with 10% nulls might be fine — agencies revise figures. Medical trial data with 2% nulls might be a crisis."

Walk the code and the direction rule: "Lower thresholds mean more alerts; higher mean fewer. We tighten the null threshold from 0.05 to 0.02 — now the four CPI columns at exactly 5% null fire, and the alert count goes from 11 to 12. And we raise the correlation threshold from 0.9 to 0.99 so only near-duplicate pairs flag."

For experts: "The correlation threshold is the most important to tune for this dataset. CPI components genuinely move together — all_items versus housing is r = 0.998. That is a domain fact, not a data-quality issue; 0.99 keeps only near-duplicates."
→ "Real messy data from Singapore."
Slide 8~3 minMessy data example

The messy economic dataset

Show the diagram and let it sink in. Then label it exactly as the slide does: "A synthetic course dataset modelled on published statistics — illustrative values, realistic mess. Three date formats inside one column: MM/YYYY (01/2000), YYYY-MM (2000-02), and bare YYYYMM (200003). Fifteen nulls in each CPI column — exactly 5%."

Set the expectation precisely: "The profiler will not tell you the date column mixes formats — it sees unique text, and flags high_cardinality instead. Reading the format mess is your job; the engine narrows where you look. And the 5% nulls sit exactly at the default boundary — the next slide shows why they stay silent."

Reassurance: "You are not expected to know how to fix all of these yet. Lesson 1.8 will show you how to build a cleaning pipeline. Today the goal is to find the problems."
→ "Let's read the actual profile output."
Slide 9~3 minProfile walkthrough

Reading the profile

Walk the printed output — 11 alerts at the default config — and for each family ask: "What should we do about this?"

  • high_cardinality on date (1.00): the three formats make every value unique text — parse to real dates (next slide)
  • high_cardinality on the CPI columns (0.94+): near-unique measurements — expected for continuous data, informational
  • high_correlation on six CPI pairs (up to 1.00): components move together — a domain fact to note, not a defect to remove

Then the two absences, which teach more than the alerts: "No high_nulls — the CPI columns are exactly 5% null and the rule is strictly greater-than-0.05. And no date alert — the engine cannot see format inconsistency. Profiling complements your own inspection; it does not replace it."

→ "Now let's verify the cleaning worked."
Slide 10~3 mincompare()

compare(): before vs after

"After you clean data, how do you know the cleaning helped? Re-profile and compare. run_compare(df_a, df_b) does this in one call and returns a dict."

Walk the cleaning code first — it is the payoff of the whole lesson: "Three str.replace passes normalise the three date formats into ISO, str.to_date parses them, a sort puts the series in order, and interpolate() fills the null gaps from neighbouring months. Then compare raw against cleaned."

Read the deltas: "For every CPI column, null_pct_delta is −0.05 — the 5% nulls are gone. compare() is the receipt that proves the cleaning did what you claimed."

→ "The comparison as a picture."
Slide 11~3 minComparison diagram

Comparison result

Walk the before/after diagram with the real numbers: "Before: 12 alerts, 7 of them warnings, CPI nulls at 5%, the date column as text in three formats. After: 8 alerts, 3 warnings, nulls at zero, a real Date column — and the row count unchanged at 300, because we filled gaps instead of dropping rows."

Then the judgement call, quoted from the slide: "The four high_nulls warnings are gone under the stricter config. The rest — near-unique measurements and correlated CPI components — are expected. Judge each alert; do not chase a count of zero. A profile with zero alerts on real-world data usually means your thresholds are asleep."

→ "A new mental model: using engines, not building them."
Slide 12~3 minClasses as users

Classes: using, not building

"DataExplorer is a class. You create an instance with (), then call methods on it. This is the same pattern for every Kailash engine: create, configure, call. You do not need to understand the internals — just the interface."

"In Module 3 you will build your own classes. Today we establish the consumer pattern: instantiate, configure, call, interpret."

If beginners ask 'what is a class?': "Think of it as a toolkit in a box. DataExplorer is the box. profile() and compare() are the tools inside. You open the box, pick a tool, and use it."
→ "What happens when things go wrong?"
Slide 13~3 mintry/except

Handling errors: try/except

"Real pipelines encounter errors: missing files, bad schemas, network timeouts. try/except lets you catch the error and handle it instead of crashing."

Walk the code: "The try block is the happy path. The except blocks catch specific error types. Always name the exception — never write bare except:."

If beginners ask 'when do I use this?': "Whenever you load external data — files, APIs, databases. If the data source might not be there, wrap it in try/except."
→ "Beyond cleaning: comparing train vs test."
Slide 14~3 minTrain/test comparison

compare() for train vs test

"Here is a preview of drift monitoring. Split the cleaned CPI series by time — first 80% of months for training, last 20% for testing — and compare the two halves. If the distributions differ, a model trained on the first half may fail on the second."

Walk the code and read the output: "cpi_all_items: mean shifted +68.4. Prices rise over time, so a time-ordered split always shifts — that is not a bug in your split, it is what trends do. The mean_delta tells you how much."

For experts: "This is the same concept as drift monitoring in production. In Module 3 you will use DriftMonitor to run this comparison continuously on deployed models."
→ "Traps to avoid."
Slide 15~2 minCommon mistakes

Three mistakes to avoid

Walk each one. Mistake 1 is the most common: "Beginners see 40 alerts and disable the engine. The correct response is to retune the thresholds so each alert means something."

Mistake 2: "Profile after cleaning the basics, not before. Fix obvious type issues first so the profile shows real problems, not noise."

Mistake 3: "The correlation alert says 'these two columns carry similar information'. It does not say 'drop one'. That decision requires domain knowledge."
