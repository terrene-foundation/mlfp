Lesson 1.8 Data Pipelines and End-to-End Project

This is the capstone of Module 1. Every skill from the previous seven lessons — variables, filtering, aggregation, joins, window functions, visualisation, profiling — converges into a single end-to-end pipeline that takes a messy (synthetic) Singapore taxi trip log and produces a clean, model-ready dataset with charts and a before/after profile. Along the way you will learn null handling, ETL concepts, REST API extraction, and PreprocessingPipeline — the second Kailash engine you use as a consumer.

Why This Matters

In a real data role, nobody hands you a clean CSV. Data arrives from APIs, databases, partner feeds, and spreadsheets — each with its own schema, its own null convention, its own date format. Your job is to build a pipeline that takes any version of the raw data and produces the same clean output every time. That pipeline is not a one-off script — it is a repeatable process you can run on tomorrow's data with zero changes.

Null Handling

Nulls are the most common data quality issue. Polars uses null (not NaN) to represent missing values. The three operations you need:

MethodWhat it doesWhen to use
is_null()Boolean mask: True where nullInspecting which rows are missing
fill_null(value)Replace nulls with a valueImputation: median, mean, forward-fill
drop_nulls()Remove rows with any nullWhen missing rows are few and uninformative
🟢 Foundations

Never drop nulls without checking how many there are. If 30% of rows have nulls, dropping them loses a third of your data. Impute first; drop only as a last resort.

Imputation strategies

import polars as pl
from shared import MLFPDataLoader

taxi = MLFPDataLoader().load("mlfp01", "sg_taxi_trips.parquet")

# Known meaning: a missing tip is no tip
taxi = taxi.with_columns(pl.col("tip_sgd").fill_null(0.0))

# Median imputation: robust to outliers
median_km = taxi["distance_km"].median()
taxi = taxi.with_columns(pl.col("distance_km").fill_null(median_km))

# Group-aware imputation: fill with the median of the row's group
taxi = taxi.with_columns(
    pl.col("distance_km").fill_null(
        pl.col("distance_km").median().over("pickup_zone")
    )
)

# Forward-fill: carry the last known value forward (sorted time series)
# cpi = cpi.sort("date").with_columns(pl.col("cpi_all_items").forward_fill())
🔵 Theory

Imputation introduces bias. Forward-fill assumes temporal continuity. Median imputation compresses the distribution toward the centre. Group-aware imputation is less biased but requires a meaningful grouping variable. Filling with a constant is only honest when the constant is the true meaning of "missing" — a missing tip really is a zero tip; a missing pickup zone is not "zone 0". In Module 2 you will learn when each strategy is statistically defensible.

ETL: Extract, Transform, Load

ETL is the universal pattern for data pipelines:

  • Extract: get the raw data from its source — files, APIs, databases.
  • Transform: clean, encode, scale, engineer features.
  • Load: write the result to a destination — parquet file, database, dashboard.

REST APIs: Extracting Data from the Web

Many datasets are not files — they are live services you query over HTTP. A REST API is a URL you send a request to and get structured data back, almost always as JSON. Singapore's public OneMap search API, for example, returns geolocation data for an address or place name. The pattern is always the same: 

import httpx

response = httpx.get(
    "https://www.onemap.gov.sg/api/common/elastic/search",
    params={"searchVal": "Tampines", "returnGeom": "Y",
            "getAddrDetails": "Y", "pageNum": 1},   # query parameters
    timeout=10,
)
response.raise_for_status()      # stop on 4xx / 5xx instead of parsing an error page
data = response.json()           # JSON text → Python dict

print(f"Found {data['found']} results across {data['totalNumPages']} pages")
print(f"First result: {data['results'][0]['SEARCHVAL']}")

Three ideas are packed into that call:

  • Query parameters. params= is turned into ?searchVal=Tampines&returnGeom=Y&… on the end of the URL. Each API documents which parameters it accepts.
  • Status codes. 200 means success; 4xx means your request was wrong (bad parameter, missing key); 5xx means the server failed. raise_for_status() turns any non-success into an exception you can catch with try / except.
  • JSON responses. The body is a nested structure of objects (dicts) and arrays (lists). OneMap returns {"found": …, "totalNumPages": …, "pageNum": …, "results": [...]}, where each result is a dict with keys such as SEARCHVAL, ADDRESS, POSTAL, LATITUDE and LONGITUDE — and the coordinates arrive as strings. Results come ten per page, so a full extraction loops over pageNum.
🟢 GET vs POST

GET means "give me data" — parameters travel in the URL and nothing changes on the server. POST means "here is data, do something with it" — the payload travels in the request body, usually as JSON: httpx.post(url, json={"name": "value"}, timeout=10). Search and lookup APIs use GET; submitting a form, creating a record or calling a prediction service uses POST. For data extraction in this course you will mostly use GET.

From JSON to DataFrame

import polars as pl

results = data["results"]                     # a list of dicts
df_locations = pl.DataFrame(results).select([
    pl.col("SEARCHVAL").alias("address"),
    pl.col("LATITUDE").cast(pl.Float64).alias("lat"),
    pl.col("LONGITUDE").cast(pl.Float64).alias("lon"),
])
print(df_locations.head(3))

pl.DataFrame(list_of_dicts) turns each dict into a row and each key into a column. .cast(pl.Float64) fixes the string-typed coordinates. A live API can be slow, rate-limited or offline, so production pipelines wrap the call in try / except httpx.HTTPError and fall back to the last saved copy of the data — the capstone below reads its trips from a file for exactly that reason.

PreprocessingPipeline

⚙ Kailash Engine

PreprocessingPipeline automates the transform step: it detects column types, imputes missing values, encodes categoricals, scales numerics, and splits the rows into train and test sets. Like DataExplorer, you use it as a consumer — create, set up, transform. 

from kailash_ml import PreprocessingPipeline

# train_rows / test_rows: rows you split off yourself (Step 4 below)
pipeline = PreprocessingPipeline()        # no constructor arguments
result = pipeline.setup(
    data=train_rows,                      # features + target column
    target="fare_sgd",
    imputation_strategy="median",
    categorical_encoding="onehot",
    normalize=True,                       # z-score the numerics
)
print(result.task_type)                   # 'regression'
print(result.original_shape, "->", result.transformed_shape)
print(result.train_data.shape, result.test_data.shape)

test_ready = pipeline.transform(test_rows)  # same learned rules, new rows
🔵 Theory: hold out test rows first

setup() learns its rules — medians for imputation, category sets for encoding, means and standard deviations for scaling — from every row you pass it, and only then splits those rows into train_data and test_data. So if you hand it the whole dataset, the test rows have already influenced the preprocessing: that is data leakage, and it makes test scores look better than they will be on genuinely new data. The fix is to set your test rows aside before calling setup(), fit on the training rows only, and apply the learned rules to the held-out rows with pipeline.transform(test_rows). The test rows never reach setup(), so nothing about them leaks.

Worked Example: Taxi Trip Pipeline

📝 Goal

Build a complete pipeline for a Singapore taxi trip log: extract from file, profile, clean, engineer features, prepare model-ready data without leakage, visualise demand, re-profile, and save the result. The question: what drives a fare, and when do people ride?

Step 1 — Extract. 
from datetime import datetime

import plotly.express as px
import polars as pl
from kailash_ml import ModelVisualizer, PreprocessingPipeline
from shared import MLFPDataLoader, run_compare, run_profile

loader = MLFPDataLoader()
df_raw = loader.load("mlfp01", "sg_taxi_trips.parquet")
print(f"Raw: {df_raw.shape}")   # → Raw: (50000, 12)
Columns: trip_id, pickup_datetime, dropoff_datetime, pickup_zone,
         dropoff_zone, distance_km, fare_sgd, tip_sgd, payment_type,
         passengers, pickup_latitude, pickup_longitude

This is a synthetic trip log with realistic places and deliberately planted problems: 250 rows with latitude and longitude swapped, 1,000 fares of zero or less, 500 trips with fewer than one passenger, 500 trips dated 2025–2027, 15 spellings of four payment methods, 500 rows sharing a trip_id, and nulls in the zone and tip columns. Both datetime columns arrive as text.

Step 2 — Profile. 
profile = run_profile(df_raw)
print(f"Alerts: {len(profile.alerts)}")
for alert in profile.alerts:
    where = alert.get("column", alert.get("columns"))
    print(f"  [{alert['severity']}] {alert['type']}: {where} = {alert['value']:.2f}")
Alerts: 12
  [info] high_cardinality: trip_id = 0.99
  [info] high_cardinality: pickup_datetime = 0.99
  [info] high_cardinality: dropoff_datetime = 1.00
  [info] high_skewness: distance_km = 7.42
  [warning] high_nulls: tip_sgd = 0.78
  [info] high_skewness: pickup_latitude = 14.03
  [info] high_skewness: pickup_longitude = -14.03
  [info] high_cardinality: pickup_longitude = 0.93
  [warning] high_correlation: ['pickup_latitude', 'pickup_longitude'] = -1.00
  [info] imbalanced: pickup_zone = 0.08
  [info] imbalanced: dropoff_zone = 0.09
  [info] imbalanced: payment_type = 0.07

The extreme coordinate skew and the r = −1.00 between latitude and longitude are the 250 swapped rows: a latitude near 103.8 is impossible. The 78% null tips are not a defect — most passengers do not tip. And notice what raises no alert at all: negative fares, zero passengers, future dates, payment spellings and repeated trip IDs. describe() min/max, n_unique() and is_duplicated() find those; the profiler complements domain checks, it does not replace them.

Step 3 — Transform: clean and engineer features. 
swapped = pl.col("pickup_latitude") > 100          # lat/lng the wrong way round
pay = pl.col("payment_type").str.to_lowercase()

df = (
    df_raw
    .with_columns(
        pl.col("pickup_datetime", "dropoff_datetime")
          .str.to_datetime("%Y-%m-%d %H:%M:%S"),
        pl.when(swapped).then(pl.col("pickup_longitude"))
          .otherwise(pl.col("pickup_latitude")).alias("pickup_latitude"),
        pl.when(swapped).then(pl.col("pickup_latitude"))
          .otherwise(pl.col("pickup_longitude")).alias("pickup_longitude"),
        pl.when(pay.str.contains("grab")).then(pl.lit("Grab"))
          .when(pay.str.contains("nets")).then(pl.lit("NETS"))
          .when(pay.str.contains("cash")).then(pl.lit("Cash"))
          .otherwise(pl.lit("Card")).alias("payment_type"),
    )
    .filter(
        pl.col("fare_sgd") > 0,
        pl.col("passengers") >= 1,
        pl.col("pickup_datetime") < datetime(2025, 1, 1),
        ~pl.col("trip_id").is_duplicated(),
    )
    .with_columns(
        pl.col("tip_sgd").fill_null(0.0),                        # no tip = 0
        pl.col("pickup_zone", "dropoff_zone").fill_null("Unknown"),
    )
    .with_columns(
        hour=pl.col("pickup_datetime").dt.hour(),
        day_of_week=pl.col("pickup_datetime").dt.weekday(),      # 1 = Mon ... 7 = Sun
        trip_duration_min=(pl.col("dropoff_datetime")
                           - pl.col("pickup_datetime")).dt.total_seconds() / 60,
    )
    .with_columns(
        is_weekend=pl.col("day_of_week") >= 6,                   # Sat = 6, Sun = 7
    )
)
print(f"Clean: {df.shape}")   # → Clean: (47547, 16)

One problem, one step. The swapped coordinates are repaired rather than dropped, because the fix is unambiguous. Impossible fares, passenger counts and dates are removed. Fifteen payment spellings collapse to four labels (Card 18,918, Cash 16,833, Grab 8,416, NETS 3,380). Both copies of every repeated trip_id are dropped, since we cannot tell which one is genuine. Note the weekday encoding: Polars dt.weekday() is ISO numbering, Monday = 1 to Sunday = 7, so the weekend is >= 6 — not >= 5, which would wrongly include Friday. Trip durations come out between 5 and 60 minutes (median 32.5).

Step 4 — Transform: PreprocessingPipeline, without leakage. 
features = df.select("distance_km", "trip_duration_min", "hour",
                     "day_of_week", "payment_type", "pickup_zone", "fare_sgd")

# Hold out the test rows BEFORE the pipeline sees anything
shuffled = features.sample(fraction=1.0, shuffle=True, seed=42)
n_test = shuffled.height // 5
test_rows, train_rows = shuffled.head(n_test), shuffled.slice(n_test)

pipeline = PreprocessingPipeline()
result = pipeline.setup(data=train_rows, target="fare_sgd",
                        imputation_strategy="median",
                        categorical_encoding="onehot", normalize=True)
print(result.task_type, result.original_shape, "->", result.transformed_shape)
# → regression (38038, 7) -> (38038, 44)

test_ready = pipeline.transform(test_rows)
print(test_ready.shape)   # → (9509, 44)

Seven columns become 44 because one-hot encoding turns every payment_type and pickup_zone value into its own 0/1 column. setup() also splits the 38,038 training rows it was given into result.train_data (30,430) and result.test_data (7,608) for model selection; the 9,509 rows we held out stay untouched until the very end.

Step 5 — Visualise. 
viz = ModelVisualizer()

hourly = df.group_by("hour").agg(pl.len().alias("trips")).sort("hour")
fig = px.bar(hourly, x="hour", y="trips",
             title="Taxi demand is flat across the day in this data")
fig.write_html("ex8_hourly_demand.html")

fig = viz.histogram(data=df, column="fare_sgd", bins=40,
                    title="Fares are right-skewed: many short trips, few long ones")
fig.write_html("ex8_fare_distribution.html")

fig = viz.scatter(data=df.sample(n=5_000, seed=42),
                  x="distance_km", y="fare_sgd", color="payment_type",
                  title="Distance drives the fare (r = 0.97)")
fig.write_html("ex8_fare_vs_distance.html")

Report what the data shows. Hourly demand is roughly flat — about 2,000 trips in every hour, with no morning or evening rush — and the seven days of the week are just as even. A real dispatch log would show peaks; this synthetic one does not, and a chart titled "rush-hour demand" would be fiction. The fare question has a clear answer: distance and fare correlate at 0.97.

Step 6 — Re-profile, compare and load. 
df_out = df.select(df_raw.columns)          # same columns as the raw data
profile_clean = run_profile(df_out)
comparison = run_compare(df_raw, df_out)

print(f"Alerts before: {len(profile.alerts)}")        # 12 (2 warnings)
print(f"Alerts after:  {len(profile_clean.alerts)}")  # 12 (1 warning)
print(comparison["shape_comparison"])
# → {'rows_a': 50000, 'rows_b': 47547, 'cols_a': 12, 'cols_b': 12}

df.write_parquet("taxi_clean.parquet")      # Load: the pipeline's output

Same alert count, different alerts — read them, not just the count. The coordinate skew and the r = −1.00 are gone; the tip column now shows as high_zeros (78%) instead of high_nulls, which is the honest description; and the real distance_km ↔ fare_sgd relationship (r = 0.97) surfaces as the one remaining warning. Cleaning removed 2,453 rows (4.9%).

Project Structure

As pipelines grow, putting everything in one file becomes unmanageable. Structure your project into modules: 

taxi_pipeline/
├── extract.py          # Data loading functions
├── transform.py        # Cleaning and feature engineering
├── visualise.py        # Chart generation
├── report.py           # HTML report generation
└── main.py             # Orchestrates the pipeline
# main.py — the orchestrator
from extract import load_taxi_data
from transform import clean_taxi_data, preprocess
from visualise import create_demand_charts
from report import generate_html_report

df_raw = load_taxi_data()
df_clean = clean_taxi_data(df_raw)
train_ready, test_ready = preprocess(df_clean)   # hold-out split inside
charts = create_demand_charts(df_clean)
generate_html_report(df_clean, charts, output="report.html")

Each file owns one responsibility, and main.py only calls them in order. from extract import load_taxi_data works because Python treats every .py file in the same folder as an importable module — the same mechanism as from shared import MLFPDataLoader, where shared is a folder of modules (a package). Each function can be tested on its own and replaced without touching the others.

🟣 Advanced

This is the simplest form of workflow orchestration — calling functions in sequence. In Module 3 you will use WorkflowBuilder to build the same pipeline as a node graph with automatic error handling, retry logic, and parallel execution.

Common Mistakes

⚠ Mistake 1: Dropping nulls without measuring the impact

Always check df.null_count() before dropping. If 25% of rows have nulls, you are throwing away a quarter of your data. Impute first.

⚠ Mistake 2: Fitting the pipeline on test data

Hold out the test rows first, call setup() on the training rows only, then transform() the test rows. Passing all rows to setup() — even with its train_size split — lets test-row statistics shape the imputation, encoding and scaling. The test set must remain unseen.

⚠ Mistake 3: Hardcoding file paths

Use MLFPDataLoader or environment variables. A pipeline that only works on your laptop is not a pipeline.

⚠ Mistake 4: No re-profiling after cleaning

Always re-profile. The cleaning step might introduce new issues (e.g., imputation changing the distribution shape). Compare before and after with run_compare(df_raw, df_clean), which wraps DataExplorer.compare().
