Lesson 3.1 Feature Engineering, ML Pipeline, and Feature Selection

Module 2 gave you statistics and a single linear model. In the next 75 minutes we will answer the question that decides whether a machine-learning project ships or dies: what goes into the model? You will engineer features from a messy multi-table ICU dataset, learn the seven stages of the ML pipeline, and apply three feature-selection families — filter, wrapper, and embedded — to shrink a pile of candidate features down to the ones that actually predict a long ICU stay. Along the way you will meet the single most expensive mistake in ML: feature leakage.

Why This Matters

There is an old saying among practitioners: "data beats models, and features beat data." An XGBoost model trained on the wrong features will lose to a logistic regression trained on the right ones — every time. The skill that separates a junior ML engineer from a senior one is not knowing more algorithms; it is knowing how to represent a real problem as a numeric tensor a model can learn from.

Singapore's clinical data illustrates this vividly. A raw ICU record has vital-sign time-series recorded at irregular intervals, medication start and stop times, laboratory panels that are ordered only when the doctor suspects a problem (so the presence of a lab test is itself a signal), and admission metadata. None of this is directly ingestible by a tree-based classifier. Before any model, there is engineering.

Core Concepts

Statistics vs ML: explaining the past vs predicting the future

In Module 2 you fitted a linear regression to HDB prices and read the coefficients: "each additional square metre adds a few thousand dollars to the resale price, holding the town fixed". That is a statistical exercise — the goal is to explain what is in the data using a small number of interpretable parameters.

Machine learning rewrites the goal. A machine-learning model does not care about coefficients; it cares about the expected loss on unseen data:

$$\text{ML objective:} \quad \min_{f} \; \mathbb{E}_{(x, y) \sim \mathcal{D}} \bigl[L\bigl(y, f(x)\bigr)\bigr]$$

where $L$ is a loss function (squared error, log loss, hinge), $f$ is the model, and $\mathcal{D}$ is the unknown distribution that produced both the training and the future data. The statistical exercise cares about inference on the parameters; the ML exercise cares about generalisation to new draws from $\mathcal{D}$. That single shift in objective is what justifies everything we are about to do: we will grow features like weeds because we do not care about their interpretability — we care about whether they help the loss.

🔵 Theory — The training vs test gap

Let $\hat{f}$ be the model fitted on a finite sample. The generalisation gap is $\mathbb{E}_{(x,y) \sim \mathcal{D}}[L(y, \hat{f}(x))] - \hat{L}_{\text{train}}(\hat{f})$. Every design decision in ML — regularisation, cross-validation, feature selection, early stopping — is ultimately a trick to estimate or minimise this gap. We will come back to it in Lesson 3.2 and formally decompose it into bias, variance, and irreducible noise.

Feature engineering: four families that cover most of the work

A feature is any deterministic function of the raw data that you hand to a model as a column. Most features fall into four families:

🟢 Foundations — A feature is a function

Do not think of a feature as "a column in the CSV". Think of it as a function applied to the raw data. The raw data is fixed; the feature space is something you design. The CSV that came out of your hospital database has maybe 30 raw fields; your final feature matrix will have 50–200. You are not transcribing — you are engineering.

Feature leakage: the most expensive mistake in ML

Leakage is when information that will not be available at prediction time sneaks into the training features. It makes your cross-validation scores look spectacular and your deployed model fall over as soon as the first real request arrives.

The rule is brutally simple: for a prediction made at time $t$, only use information produced strictly before $t$. Violate it and your model memorises the future. Enforce it and your cross-validation scores will drop — sometimes by a lot — but they will finally match what you see in production.

Feature selection: three families

You will often engineer many more features than you need. Feature selection is the act of keeping the predictive ones and dropping the noise. There are three classical families.

Filter: score each feature independently

Filter methods rank each feature against the target using a model-free statistic and drop the ones below a threshold. The most common statistic for a continuous target is mutual information:

$$I(X; Y) \;=\; \sum_{x}\sum_{y} p(x, y) \, \log \frac{p(x, y)}{p(x)\,p(y)}$$

$I(X; Y) = 0$ iff $X$ and $Y$ are independent; it captures non-linear dependencies that linear correlation misses. For a categorical target, the chi-squared statistic is the classic choice:

$$\chi^2 \;=\; \sum_{i} \frac{(O_i - E_i)^2}{E_i}$$

where $O_i$ is the observed count in cell $i$ of a contingency table and $E_i$ is the expected count under independence. Large $\chi^2$ means the feature's distribution differs from what independence would predict.

Wrapper: let the model vote

A wrapper method repeatedly re-trains the actual model with different feature subsets and keeps whichever subset scores best on cross-validation. The algorithms are greedy because trying every subset is $O(2^d)$ and intractable for $d > 20$:

  • Forward selection: start with no features; at each step add the feature whose addition most improves CV score. Stop when no addition helps.
  • Backward elimination: start with all features; at each step drop the feature whose removal hurts CV score least. Stop when every remaining feature is essential.
  • Recursive Feature Elimination (RFE): train the model, rank features by importance, drop the lowest, refit, repeat.

Embedded: selection falls out of training

Embedded methods fit one model and extract the selection from the fitted parameters. L1-regularised regression (Lasso) drives irrelevant coefficients to exactly zero — fit once, keep the nonzero ones. Tree ensembles expose a feature_importances_ array derived from total impurity reduction — again, one fit, one ranking. The cost is near zero; the tradeoff is that the selection is tied to the model family you used.

The Kailash Engines: FeatureSchema, FeatureEngineer, PreprocessingPipeline

⚙ Kailash Engine

Three kailash-ml pieces cover the mechanical parts of this lesson. FeatureSchema declares the feature contract — names, dtypes and the entity id each row belongs to. FeatureEngineer generate()s candidate columns (interactions, squares, bins) from the columns in the schema and select()s the top-k by a ranking method. PreprocessingPipeline imputes, encodes and scales a polars frame. Think of them as three verbs: declare, engineer, preprocess. Domain features such as the shock index are not generated for you — you write those in polars, as the worked example below shows. 

from kailash_ml import FeatureEngineer
from kailash_ml.types import FeatureField, FeatureSchema

# train_df: the imputed TRAINING rows from Step 6 of the worked example,
# plus admission_id and the long_stay label
schema = FeatureSchema(
    name="icu_admission_v1", entity_id_column="admission_id",
    features=[FeatureField("age", "int64"),
              FeatureField("bmi", "float64"),
              FeatureField("weight_kg", "float64")])

fe = FeatureEngineer(max_features=5)
cands = fe.generate(train_df, schema, strategies=["interactions"])
picked = fe.select(cands.data, cands, target="long_stay",
                   method="mutual_info")   # fit on train rows only
print([c.name for c in cands.generated_columns])  # age_x_bmi, age_x_weight_kg, ...
print(picked.selected_columns)

Two cautions. FeatureEngineer cannot handle nulls — impute first. And PreprocessingPipeline.setup(df, target) fits its imputer, encoder and scaler on every row you pass it and only then splits off a test set, so test-row statistics leak into training. Hold out your test rows yourself, call setup() on the training rows only, and apply the fitted pipeline to the test rows with transform().

Worked Example: Engineering Features for ICU Long Stays

📝 Goal

We have five tables from a synthetic Singapore ICU cohort (5,000 patients, 8,000 admissions): patients, admissions, vitals, medications, labs. The target is long_stay — 1 if the admission's length of stay is above the cohort median (15.1 days), 0 otherwise, so the classes are almost exactly balanced. The prediction is made 24 hours after admission. We need one row per admission, with features that obey point-in-time correctness. This is the same target Exercise 3.1 uses.

Step 1.

Load the tables, parse the timestamp columns (they are stored as strings) and derive the label from los_days. The label's source columns are recorded at discharge, so they can never be features.

import polars as pl
from shared import MLFPDataLoader

FMT = "%Y-%m-%d %H:%M:%S"
loader = MLFPDataLoader()
patients   = loader.load("mlfp02", "icu_patients.parquet")
admissions = loader.load("mlfp02", "icu_admissions.parquet")
vitals     = loader.load("mlfp02", "icu_vitals.parquet")

admissions = admissions.with_columns(
    pl.col("admit_time").str.to_datetime(FMT),
    pl.col("discharge_time").str.to_datetime(FMT),
    long_stay=(pl.col("los_days") > pl.col("los_days").median()).cast(pl.Int8),
)
vitals = vitals.with_columns(pl.col("timestamp").str.to_datetime(FMT))
Step 2.

Clip every vital reading to the first 24 hours of the admission it belongs to. This is where point-in-time correctness is enforced: a vital recorded at hour 48 cannot be a feature for an hour-24 prediction — and neither can one recorded before admission.

vitals_24h = (
    vitals.join(admissions.select(["admission_id", "admit_time"]),
                on="admission_id")
          .with_columns(
              hours_since_admit=(
                  pl.col("timestamp") - pl.col("admit_time")
              ).dt.total_hours()
          )
          .filter(pl.col("hours_since_admit").is_between(0, 24))
)
print(vitals.height, vitals_24h.height,
      vitals_24h["admission_id"].n_unique())   # 16435 996

Look at that output before going further. Of 63,452 vital-sign rows, 16,435 fall inside the 24-hour window, covering 996 of the 1,000 monitored admissions (the four missed are the deliberate discharge-before-admit data-entry rows). Medications (765 admissions) and labs (821 admissions) are sparser — not every monitored patient gets drugs or bloods in the first day — but the window is real. This is what a healthy feed looks like after the window audit did its job. The dataset you are holding is the fixed one: an earlier cut of this extract had event tables whose timestamps were not aligned to admissions at all (4 of 8,000 admissions had any first-24h vitals), and it was exactly this audit — row counts in the window, admissions covered — that caught it. Exercise 3.1 runs the same audit. Catching a broken feed before modelling is the point: the fix is in the data, not in the model.

Step 3.

Aggregate the time-series into a fixed-shape summary per admission: mean, std, min and max of heart rate, systolic BP and SpO₂. This collapses an irregular time-series into a flat row.

vital_features = vitals_24h.group_by("admission_id").agg([
    pl.col("heart_rate").mean().alias("hr_mean"),
    pl.col("heart_rate").std().alias("hr_std"),
    pl.col("heart_rate").max().alias("hr_max"),
    pl.col("systolic_bp").mean().alias("sbp_mean"),
    pl.col("systolic_bp").min().alias("sbp_min"),
    pl.col("spo2").min().alias("spo2_min"),
    pl.col("heart_rate").count().alias("n_vital_readings"),
])

Note the subtle feature n_vital_readings. In clinical data, the number of times a patient was measured is itself a signal — sicker patients get monitored more frequently. This is an informative missingness pattern, and tree-based models love it.

Step 4.

Engineer a domain-derived feature: the shock index, defined clinically as heart rate divided by systolic BP. A value above 1 is a red flag for shock. With good vitals coverage this single derived feature often outperforms the two raw inputs.

vital_features = vital_features.with_columns(
    shock_index=pl.col("hr_mean") / pl.col("sbp_mean")
)
Step 5.

Join everything onto the admission table. Then build X from numeric columns only, explicitly excluding the IDs, the label and the label's sources (los_days, discharge_time).

features = (
    admissions
      .join(patients,       on="patient_id",   how="left")
      .join(vital_features, on="admission_id", how="left")
)

LEAKY = ["los_days", "discharge_time", "long_stay"]   # label + its sources
IDS   = ["admission_id", "patient_id", "admit_time"]
numeric = [c for c, t in features.schema.items()
           if t.is_numeric() and c not in LEAKY + IDS]

y = features["long_stay"].to_numpy()
X = features.select(numeric)   # age, height_cm, weight_kg, bmi, hr_mean, ...
Step 6.

Split first. Learn the imputation values (medians) from the training rows only, then run all three selection families on the training split.

from sklearn.model_selection import train_test_split
from sklearn.feature_selection import mutual_info_classif, RFE
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import RandomForestClassifier
from sklearn.preprocessing import StandardScaler

idx_train, idx_test = train_test_split(
    range(features.height), test_size=0.2, stratify=y, random_state=42)
X_train, X_test = X[idx_train], X[idx_test]
y_train, y_test = y[idx_train], y[idx_test]

fill = {c: X_train[c].median() for c in X_train.columns}   # train only
X_train = X_train.with_columns([pl.col(c).fill_null(v) for c, v in fill.items()])
X_test  = X_test.with_columns([pl.col(c).fill_null(v) for c, v in fill.items()])
cols, Xtr = X_train.columns, X_train.to_numpy()

# 1) Filter: mutual information with the target
mi = mutual_info_classif(Xtr, y_train, random_state=42)
filter_top = sorted(zip(cols, mi), key=lambda t: -t[1])[:5]

# 2) Wrapper: RFE with logistic regression (scale first: LR needs
#    comparable units)
Xtr_scaled = StandardScaler().fit_transform(Xtr)
rfe = RFE(LogisticRegression(max_iter=2000), n_features_to_select=5)
rfe.fit(Xtr_scaled, y_train)
wrapper_top = [c for c, keep in zip(cols, rfe.support_) if keep]

# 3) Embedded: random-forest impurity importance
rf = RandomForestClassifier(n_estimators=200, random_state=42)
rf.fit(Xtr, y_train)
embedded_top = sorted(zip(cols, rf.feature_importances_),
                      key=lambda t: -t[1])[:5]

What you actually see. The three rankings disagree almost completely. Every mutual-information score is below 0.02 nats — next to nothing. RFE keeps five of the vital-sign columns, which are constant (the imputed median) for all but a handful of rows. The random forest puts height_cm, weight_kg, bmi and age on top with roughly a quarter of the importance each — not because they predict a long stay (their correlation with los_days is about 0.01), but because impurity importance favours continuous columns with many distinct split points.

That is the honest lesson of this dataset: when no feature carries signal, the selection methods return noise rankings, and each one is noisy in its own way. With real signal the methods agree much more. In practice you use the intersection (features every method ranks highly) as a robust core and the union as a candidate set for tuning — and when the intersection is empty, as here, you treat that as a warning that the data, not the model, is the problem.

Deeper Theory: Why Mutual Information Generalises Correlation

Pearson correlation captures linear dependence — that is, the extent to which $Y$ can be written as $aX + b + \varepsilon$. It is zero for perfect non-linear relationships like $Y = X^2$ when $X$ is symmetric about zero. Mutual information does not have this blind spot. From the definition:

$$I(X; Y) \;=\; H(X) + H(Y) - H(X, Y) \;=\; H(Y) - H(Y \mid X)$$

The last form is the cleanest: mutual information is how much the entropy of $Y$ drops once you know $X$. If knowing $X$ reduces your uncertainty about $Y$ by half, $I(X; Y) = H(Y)/2$. If $X$ is useless, $I(X; Y) = 0$. If $X$ determines $Y$ exactly, $I(X; Y) = H(Y)$. This holds for any functional form — linear, quadratic, threshold, whatever — which is why MI is the default filter statistic when you do not yet know what shape of relationship you are looking for.

🟣 Advanced — MI is invariant to monotonic reparameterisation

A subtle property: $I(X; Y) = I(g(X); Y)$ for any invertible $g$. Scaling, log-transforming, or rank-transforming a feature does not change its MI with the target. Pearson correlation is also unchanged by a change of units (any affine map $aX + b$ with $a > 0$), but it does change under non-linear monotone transforms such as a log. So the advantage of an MI filter is not unit-robustness: it is invariance to monotone non-linear re-expressions of a feature, plus the ability to detect non-linear dependence that correlation misses entirely.

Common Mistakes

⚠ Mistake 1 — Fitting the scaler on the full dataset

A standard scaler learns the mean and std from its input. If you fit it on the combined train+test data before splitting, test-set statistics leak into the training features. Always fit the scaler on train only, then transform both. sklearn's Pipeline inside cross_val_score does this per fold. kailash-ml's PreprocessingPipeline.setup() does not: it fits on every row you hand it before it splits, so hold out the test rows first and call setup() on the training rows only.

⚠ Mistake 2 — Using future-looking features

Any column whose value is only known after the prediction time is leakage. Classic offenders: length-of-stay, billed revenue, final diagnosis code, total medications prescribed over the admission. Draw the timeline explicitly and ask, for each feature, "would this number exist if I ran the model now?".

⚠ Mistake 3 — Selecting features before splitting

If you rank features by their correlation with the target and then split, you have already leaked information about the test set into the feature selection. The right order is: split first, then fit feature selection on the train split only, then apply the same selection to the test split.
