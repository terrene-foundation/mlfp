Five stages, one pipeline

ETL: the universal data pattern

  • Extract: get data from its source (file, API, database)
  • Transform: clean, encode, scale, engineer features
  • Load: write the result to a destination
🟢 Foundations: Every data project you will ever build follows this pattern. The tools change; the structure does not.

Null handling: three tools

MethodWhat it doesWhen to use
is_null()Boolean maskInspection
fill_null(val)Replace nullsImputation
drop_nulls()Remove rowsFew uninformative nulls
 

# Known meaning: a missing tip is no tip
taxi = taxi.with_columns(pl.col("tip_sgd").fill_null(0.0))

# Forward-fill for time series (sorted by date)
cpi = cpi.with_columns(pl.col("cpi_all_items").forward_fill())

# Median imputation for a numeric column
taxi = taxi.with_columns(
    pl.col("distance_km").fill_null(pl.col("distance_km").median())

Extracting data from APIs


import httpx

response = httpx.get(
    "https://www.onemap.gov.sg/api/common/elastic/search",

🟢 Foundations: GET = "give me data". POST = "here is data". Response is usually JSON — parse it into a DataFrame.

PreprocessingPipeline: automated preparation


from kailash_ml import PreprocessingPipeline

pipeline = PreprocessingPipeline()        # no constructor arguments
result = pipeline.setup(
    data=train_rows,                      # features + target column
    target="fare_sgd",
    imputation_strategy="median",
    categorical_encoding="onehot",
    normalize=True,                       # z-score the numerics
)
print(result.task_type)                   # 'regression'
print(result.original_shape, "->", result.transformed_shape)
print(result.train_data.shape, result.test_data.shape)

One call: detects numeric vs categorical columns, imputes nulls, one-hot encodes, scales, then splits into train_data / test_data. pipeline.transform(new_rows) applies the same learned rules.

The dataset: Singapore taxi trips


Shape:   (50000, 12)   synthetic trip log, realistic places
Columns: trip_id, pickup_datetime, dropoff_datetime, pickup_zone,
         dropoff_zone, distance_km, fare_sgd, tip_sgd, payment_type,
         passengers, pickup_latitude, pickup_longitude
Planted: 250 swapped lat/lng, 1,000 fares <= 0, 500 passengers < 1,

Question: what drives a fare, and when do people ride?
Pipeline: load → profile → clean → engineer hour/day/duration → prepare → visualise → report

Step 3: Transform


swapped = pl.col("pickup_latitude") > 100          # lat/lng the wrong way round
pay = pl.col("payment_type").str.to_lowercase()
df = (
    df_raw
    .with_columns(
        pl.col("pickup_datetime", "dropoff_datetime").str.to_datetime("%Y-%m-%d %H:%M:%S"),
        pl.when(swapped).then(pl.col("pickup_longitude")).otherwise(pl.col("pickup_latitude")).alias("pickup_latitude"),
        pl.when(swapped).then(pl.col("pickup_latitude")).otherwise(pl.col("pickup_longitude")).alias("pickup_longitude"),
        pl.when(pay.str.contains("grab")).then(pl.lit("Grab"))
          .when(pay.str.contains("nets")).then(pl.lit("NETS"))
          .when(pay.str.contains("cash")).then(pl.lit("Cash"))
          .otherwise(pl.lit("Card")).alias("payment_type"),
    )
    .filter(pl.col("fare_sgd") > 0, pl.col("passengers") >= 1,
            pl.col("pickup_datetime") < datetime(2025, 1, 1),
            ~pl.col("trip_id").is_duplicated())
    .with_columns(pl.col("tip_sgd").fill_null(0.0),
                  pl.col("pickup_zone", "dropoff_zone").fill_null("Unknown"))
    .with_columns(
        hour=pl.col("pickup_datetime").dt.hour(),
        day_of_week=pl.col("pickup_datetime").dt.weekday(),   # 1 = Mon ... 7 = Sun
        trip_duration_min=(pl.col("dropoff_datetime")
                           - pl.col("pickup_datetime")).dt.total_seconds() / 60,
    )
)
print(f"Clean: {df.shape}")   # → Clean: (47547, 15)

Needs from datetime import datetime. Polars weekdays are ISO: Monday = 1, weekend = 6 and 7.

Step 4: PreprocessingPipeline


from kailash_ml import PreprocessingPipeline

features = df.select("distance_km", "trip_duration_min", "hour",
                     "day_of_week", "payment_type", "pickup_zone", "fare_sgd")
shuffled = features.sample(fraction=1.0, shuffle=True, seed=42)
n_test = shuffled.height // 5
test_rows, train_rows = shuffled.head(n_test), shuffled.slice(n_test)

pipeline = PreprocessingPipeline()
result = pipeline.setup(data=train_rows, target="fare_sgd",
                        imputation_strategy="median",
                        categorical_encoding="onehot", normalize=True)
print(result.original_shape, "->", result.transformed_shape)  # (38038, 7) -> (38038, 44)
test_ready = pipeline.transform(test_rows)                       # (9509, 44)

7 columns → 44 (one-hot encoding expands payment_type and pickup_zone). The test rows never reach setup(), so nothing about them leaks into the learned rules.

Same count, different alerts: the swapped-coordinate skew and r = −1.00 are gone, and the real distance_km ↔ fare_sgd link (r = 0.97) now shows. Always re-profile after cleaning — and read the alerts, not just the count.

Structuring the project


taxi_pipeline/

├── report.py        # HTML report
└── main.py          # Orchestrator

Each file owns one responsibility. The orchestrator in main.py calls them in order — the same Extract, Transform, Visualise, Report pipeline from Slide 2, now as real code.

The orchestrator: main.py


# main.py
from extract import load_taxi_data
from transform import clean_taxi_data, preprocess
from visualise import create_demand_charts
from report import generate_html_report

df_raw = load_taxi_data()
df_clean = clean_taxi_data(df_raw)
charts = create_demand_charts(df_clean)
generate_html_report(df_clean, charts)

Four lines of orchestration. Each function lives in its own module, is independently testable, and can be swapped without touching the others.

This is the pattern. Every production data pipeline — from startup to enterprise — looks like this at the top level.

Four mistakes to avoid

1. Dropping nulls without checking count
Check null_count() first. 25% nulls = 25% data loss.
2. Fitting pipeline on test data
setup(train_rows), then transform(test_rows). Never pass test rows to setup().
3. Hardcoding file paths
Use the data loader. A pipeline that only works on your laptop is not a pipeline.
4. No re-profiling after cleaning
Always compare before/after. Cleaning can introduce new issues.
