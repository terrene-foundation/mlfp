Speaker Notes — Lesson 6.8 Capstone — Full Production Platform

Total time: ~120 minutes  ·  11 slides  ·  ~11 min per slide average

The culmination of the entire programme: a governed AI system served on three channels. Two hours, mostly on the code — the Nexus deployment, the role-tier table, drift monitoring, and the end-to-end verification that proves auth, governance, and prediction in one test run. The security facts to land precisely: middleware order (rate limit → JWT → handler → PACT), the role comes from the signed token and nothing else, and a valid token with no tier gets {"blocked": true} inside the handler — not a 403.

Slide 1~2 minTitle

Capstone — Full Production Platform

Open with the outcome: "Deploy a governed AI system accessible via API, CLI, and MCP. Everything from six modules lands in this lesson — and at the end, you'll have run the whole thing against real HTTP."

→ "The stack, layered."
Slide 2~10 minStack architecture

The complete Kailash stack — layered architecture

Walk the layered diagram bottom to top: the Core SDK's workflow engine; DataFlow for persistence; kailash-ml's lifecycle engines; Kaizen for agents; PACT for governance; MCP for tools; Nexus on top serving every channel. "Six packages, one platform. Every layer is one you used in isolation in an earlier lesson — today they're one system."

→ "Nexus: three channels."
Slide 3~14 minNexus deployment

Nexus: three channels, one codebase

Walk the code. The JWT config: HS256 with the secret from MLFP_JWT_SECRET — "from the environment, never in source; the secrets.token_urlsafe(48) fallback is for local runs." The Nexus app with its one allowed CORS origin. The NexusAuthPlugin bundling JWT with a rate limit — 10 requests/minute, burst 5.

Then the handler: serve_qa reads request.state.user.roles — "from the verified token, not the request" — and dispatches to the governed tier. One handler_extract call publishes it on all three channels: API, CLI, MCP.

Read the footer slowly — the order is the security model: "Middleware runs outermost first: rate limit (429) → JWT (401) → handler → PACT governance. Cheap rejections at the edge, expensive governance only for verified callers. CORS answers only the allowed origin."

→ "The token picks the tier."
Slide 4~12 minRole tiers

Role-based access: the token picks the tier

Walk the tier table — it's the capstone's RBAC in one view. qa: retail-facing QA, $1 budget, public clearance, two tools. admin: model operations, $10, confidential, plus update_model, view_metrics, monitor_drift. audit: compliance audit, $50, secret, plus access_audit_log and generate_report.

Walk the three bullets as the failure taxonomy. Missing, forged, or expired token: 401 at the JWT layer — it never reaches the handler. Too many requests: 429 at the rate limiter. Valid token but a role with no tier — guest: "PACT refuses inside the handler: the response is {"blocked": true}, not a 403. The HTTP layer succeeded; governance said no."

And the last bullet — read it twice: "The role comes from the signed token. A "role": "audit" field in the request body changes nothing. Authority is what you can prove, never what you claim."

→ "Watch the traffic: drift."
Slide 5~11 minDriftMonitor integration

DriftMonitor integration

Walk the code — M3.8's pattern in the new system. Its own SQLite file, tenant mlfp_demo, PSI threshold 0.2. Reference data: validated traffic with one numeric feature per question — question_length. Then check_drift per window of new traffic; when overall_drift_detected fires, print the severity and the PSI.

Read the footer: "Exercise 8.4 measures PSI on real traffic — SQuAD questions against a window that mixes in MMLU exam questions. PSI below 0.1: safe. 0.1–0.2: investigate. Above 0.2: alert. The exam-style questions are longer and more uniform — the monitor catches the shift without knowing anything about the content."

→ "Prove the whole thing works."
Slide 6~13 minE2E verification

End-to-end verification

Walk the test. httpx.ASGITransport(app=app.fastapi_app) — "real HTTP through the full middleware stack, no port, no server process." Three assertions:

Happy path: POST with the qa bearer token → 200, and the handler's role is "qa". Auth: the same POST with no token and with a forged token → 401 at the edge. Governance: the guest token — valid signature, no tier → outputs.handler.blocked is True.

"One test run proves the three layers independently: the edge rejects the unauthenticated, the handler serves the authorised, and governance refuses the out-of-tier. This is the definition of done for the capstone — not 'it started', but these assertions, green."

→ "Debug the agents inside it."
Slide 7~11 minDebugging agents

Debugging and testing agents

Walk the observatory code: capture_run records the agent's full trace; tool_usage prints one row per tool call, in order; detect_loops flags the same call repeated — a stuck agent; plot_trace renders the reasoning timeline. "The Delegate from 6.5 runs inside this platform too — and this is how you see what it's doing."

Then the testing principle: "Test structure, not wording — the right tool was called, typed fields are present, governance verdicts match. LLM text varies run to run; structure doesn't." And the two awareness notes: serving at scale — KV-cache reuse, flash attention, continuous-batching servers like vLLM cut latency per token; multimodal — vision-language models like the open LLaVA family take images and text through the same agent patterns.

M3: supervised ML, ensembles, production pipeline, drift monitoring. M4: unsupervised ML, NLP, recommenders, THE PIVOT, DL foundations. "Six modules, each building exactly on the last. The PIVOT in M4 said optimisation drives feature discovery; everything since has been that sentence at larger scale."
