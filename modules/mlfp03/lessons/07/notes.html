Speaker Notes — Lesson 3.7 Workflow Orchestration, Model Registry, and Hyperparameter Search

Total time: ~55 minutes  ·  12 slides  ·  ~4.5 min per slide average

The engineering lesson: scripts become pipelines, and models get a lifecycle. Three systems to land — WorkflowBuilder (explicit node graphs that fail loudly), HyperparameterSearch (Bayesian, via Optuna's TPE), and ModelRegistry (staging → shadow → production → archived, with promote_model recording a reason). The thread tying them together: nothing is silent — failures raise, gates are explicit, promotions are justified.

Slide 1~1 minTitle

Workflow Orchestration, Model Registry, and Hyperparameter Search

Open: "Every lesson so far ended with a trained model in a notebook cell. Today it becomes infrastructure: an automated pipeline with versioning. Outcome: automated ML pipeline with model versioning."

→ "Why scripts break."
Slide 2~4 minScripts to workflows

From scripts to workflows

Walk the two panels. Left — the sequential script: load, preprocess, train... and train dies with an OOM. Everything below — evaluate, register — never runs, and worse, nobody knows it never ran until someone asks where the model is.

Right — the WorkflowBuilder DAG: explicit nodes with declared dependencies, a Train node that fails loudly — execute() raises — and a metric gate that branches: pass goes to Promote, fail holds in staging. Read the bottom bar: "Explicit dependencies, branch on metrics, failures raise — nothing silently lost."

→ "The graph itself."
Slide 3~3 minNode graph

Workflow as a node graph

Walk the linear spine: Load → Preprocess → Train → Evaluate, then the gate diamond, then Promote. "Each arrow is a declared data dependency — output name to input name. The runtime topologically sorts the graph; you declare what connects, not when things run."

→ "In code."
Slide 4~5 minWorkflowBuilder code

WorkflowBuilder code

Walk the code. Custom node classes — registered with @register_node() — wrap load, preprocess, train, and evaluate. The gate is two stock nodes: a PythonCodeNode computing the promote flag, and a SwitchNode routing on it. Read the footer rule: "GATE_CODE: promote only if test AUC ≥ 0.75 and AP ≥ 2× the default rate. Two metrics, both from 3.5 — ranking quality and precision on the minority class."

Then the runtime: LocalRuntime(conditional_execution= "skip_branches") — the untaken branch is skipped, not executed-and-discarded. "And the failure contract: a failing node makes execute() raise. Errors are not swallowed and logged; they stop the pipeline with a stack trace."

For experts: the PythonCodeNode sandbox is deliberately restricted — it refuses third-party imports like polars or lightgbm (and the course's own shared helpers). Heavy lifting belongs in custom registered nodes; the inline gate is for plain-Python threshold logic only.
→ "Now tune the model inside the pipeline."
Slide 5~4 minBayesian search

Bayesian hyperparameter search

Walk the figure: the dashed grey is the true response surface, the teal curve is the surrogate model's current belief with its uncertainty band, and the amber point is where the acquisition function says to try next — high predicted value or high uncertainty.

"Bayesian optimisation = surrogate model + acquisition function. kailash-ml's strategy="bayesian" runs Optuna's TPE sampler — good hyperparameters in tens of trials, not the thousands a grid would need."

→ "The code."
Slide 6~5 minSearch code

HyperparameterSearch code

Walk the code top to bottom. The SearchSpace declares three distributions: n_estimators 100–800 uniform-int, max_depth 3–10, learning_rate log-uniform 0.01–0.3 — "log for lr, because the difference between 0.01 and 0.03 matters as much as between 0.1 and 0.3." The SearchConfig picks the bayesian strategy, 20 trials, maximising AUC.

Then the call: search.search(data=dev, ...) with an EvalSpec — note the comment: trials score a dev holdout, not the test set. "3.2's discipline inside the engine: the search never sees test data, so the final evaluation stays honest."

→ "Why Bayesian wins, visually."
Slide 7~4 minSearch comparison

Bayesian search focuses where it matters

Walk the three panels. Grid: 25 evaluations in a rigid lattice — 23 wasted, two lucky hits on the optimum region. Random: 15 scattered evaluations, 2 near the optimum — better odds per eval than grid, still uninformed. Bayesian: a few grey exploratory points, then the mass concentrates green around the optimum — 8 of 15 near it, with one amber exploration point still checking the unknown.

Read the bottom bar: "Bayesian uses a surrogate model to predict where good hyperparameters are, then samples there. Explore where uncertain, exploit where promising."

→ "The summary table."
Slide 8~3 minMethod table

Grid vs Random vs Bayesian

Walk the table. Grid: $k^d$ evaluations — exponential, uninformed — fine for one or two hyperparameters. Random: fixed budget, uninformed, surprisingly hard to beat in high dimensions with cheap evaluations. Bayesian: fixed budget, informed by the surrogate — worth its overhead when evaluations are expensive or the space is complex.

"Our three-parameter LightGBM space with a minute per fit: Bayesian, twenty trials. That's the default answer for this course's problems."

→ "Version the winner."
Slide 9~5 minModelRegistry

ModelRegistry

Walk the code. register_model stores the artifact bytes with metrics — a MetricSpec naming the value and the split it was measured on — and a ModelSignature: input schema, output columns, dtypes, model type. "The signature is the contract: what columns does this model eat, what does it emit. Serving and drift checks both read it."

Then the promotion: "New versions land in staging. The if gate["promote"] is computed from test metrics, never assumed — and promote_model takes a reason: 'AUC/AP gate passed on test'. Every transition in the registry is justified in writing."

→ "The full lifecycle."
Slide 10~4 minLifecycle

Model lifecycle

Walk the four states. Staging — where register_model() lands. Shadow — scores live traffic but isn't served; the gate labelled "shadow OK + sign-off" guards the move to Production. Production — serving live requests. Archived — kept for audit and rollback, when a model is replaced or drifted out.

Point at the dashed blue arrow: "Re-stage is the rollback path — an archived version comes back through staging. You don't un-promote; you re-stage and re-gate. And the centre label: promote_model() records a reason at every transition."

→ "Three mistakes."
Slide 11~2 minMistakes

Three mistakes to avoid

Walk the three red boxes. One: grid search with 5+ hyperparameters — exponential blowup; that's what Bayesian is for. Two: promoting models without a signature — serving has no contract to validate against; the first schema drift becomes a silent production bug. Three: no conditional gate on promotion — an ungated pipeline promotes the model that just finished training, not the model that earned it.

→ "Recap and bridge."
Slide 12~2 minRecap

What you can now do

Walk the bullets: build workflows as node graphs, run Bayesian hyperparameter search, register and promote models through the lifecycle, and gate promotion on metrics.
