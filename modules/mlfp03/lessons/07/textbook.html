Lesson 3.7 Workflow Orchestration, Model Registry, and Hyperparameter Search

Until now you have built ML pipelines as sequential Python scripts. That works for prototyping — it does not work for production. This lesson introduces WorkflowBuilder to build ML pipelines as node graphs that the runtime executes in dependency order, HyperparameterSearch to find good model configurations with Bayesian optimisation, and ModelRegistry to version models and promote them through the deployment lifecycle.

WorkflowBuilder

⚙ Kailash Engine

WorkflowBuilder turns your ML pipeline into a directed graph of nodes connected by data edges. Each node is a self-contained unit — load data, preprocess, train, evaluate — and LocalRuntime validates the graph and executes the nodes in dependency order. Errors are not swallowed: a failing node makes the run fail loudly instead of passing bad data downstream.

Three ideas are enough to read any Kailash workflow. Nodes are added by type name with an id and a config dict: add_node("PythonCodeNode", "gate_check", {"code": ...}). Edges connect one node's named output to another's named input: add_connection(from_node, from_output, to_node, to_input). And the runtime returns (results, run_id), where results[node_id] is that node's output dict. A PythonCodeNode runs a few lines of inline code: its inputs arrive as variables, and whatever it assigns to result becomes its "result" output.

Here is the promotion gate from Exercise 3.7 as a self-contained workflow. The test metrics come from the evaluation you ran earlier and are passed in at execution time: 

from kailash.runtime import LocalRuntime
from kailash.workflow.builder import WorkflowBuilder

GATE_CODE = """
min_ap = 2 * default_rate
result = {'auc_roc': test_metrics['auc_roc'], 'auc_pr': test_metrics['auc_pr'],
          'promote': test_metrics['auc_roc'] >= 0.75
                     and test_metrics['auc_pr'] >= min_ap}
"""

wf = WorkflowBuilder()
wf.add_node("PythonCodeNode", "gate_check", {"code": GATE_CODE})
wf.add_node("SwitchNode", "gate",
            {"condition_field": "promote", "operator": "==", "value": True})
wf.add_node("PythonCodeNode", "promote",
            {"code": "result = dict(payload, stage='production')"})
wf.add_node("PythonCodeNode", "hold",
            {"code": "result = dict(payload, stage='staging')"})

# add_connection(from_node, from_output, to_node, to_input)
wf.add_connection("gate_check", "result", "gate", "input_data")
wf.add_connection("gate", "true_output", "promote", "payload")
wf.add_connection("gate", "false_output", "hold", "payload")

# skip_branches: nodes on the branch the switch did NOT take are skipped
with LocalRuntime(conditional_execution="skip_branches") as runtime:
    results, run_id = runtime.execute(
        wf.build(),
        parameters={"gate_check": {
            "test_metrics": {"auc_roc": 0.776, "auc_pr": 0.363},
            "default_rate": 0.129}})

print(results["promote"]["result"]["stage"])   # production
print("hold" in results)                         # False: branch skipped

With those metrics the gate passes (AUC 0.776 ≥ 0.75 and AP 0.363 ≥ 2 × 0.129), so only promote runs. Feed it {"auc_roc": 0.70, "auc_pr": 0.20} and only hold runs. Exercise 3.7 builds the full pipeline the same way, with custom nodes (registered with @register_node()) for loading, preprocessing, training through TrainingPipeline, evaluation and promotion. (kailash 2.44.1 also logs an "Error tracking conditional execution performance" line in skip_branches mode; it comes from an internal metrics hook and the run itself is unaffected.)

Logic nodes: branching and merging

SwitchNode is the branching node: it evaluates input_data[condition_field] <operator> value and sends input_data to true_output or false_output. (There is no ConditionalNode in Kailash.) MergeNode is its partner for joining parallel branches: it combines up to five inputs (data1 … data5) into one merged_data output. Use it after branches that both run — for example a quality check and a fairness check that must both feed one report: 

wf = WorkflowBuilder()
wf.add_node("PythonCodeNode", "quality",
            {"code": "result = {'auc_ok': test_metrics['auc_roc'] >= 0.75}"})
wf.add_node("PythonCodeNode", "fairness",
            {"code": "result = {'di_ok': min(di.values()) >= 0.8}"})
wf.add_node("MergeNode", "checks", {"merge_type": "merge_dict"})
wf.add_connection("quality", "result", "checks", "data1")
wf.add_connection("fairness", "result", "checks", "data2")

with LocalRuntime() as runtime:
    results, _ = runtime.execute(wf.build(), parameters={
        "quality": {"test_metrics": {"auc_roc": 0.776}},
        "fairness": {"di": {"race": 0.96, "gender": 0.96, "age": 0.36}}})
print(results["checks"]["merged_data"])   # {'auc_ok': True, 'di_ok': False}

Do not put a MergeNode directly after a SwitchNode to "re-join" the two branches: in skip_branches mode one branch is skipped, its input never arrives, and the merge node fails with "Required parameter 'data1' not provided". Read the result of whichever branch ran instead, as above.

HyperparameterSearch

Grid search tries every combination and is wasteful. Random search is better but uninformed. Bayesian optimisation builds a cheap surrogate model of the objective from the trials so far and uses an acquisition rule (for example expected improvement) to choose the next point, balancing exploration of uncertain regions against exploitation of regions that already look good. The classic surrogate is a Gaussian process. kailash-ml's strategy="bayesian" runs Optuna's TPE sampler (Tree-structured Parzen Estimator), which models "good" and "bad" regions as two densities instead. Either way, good hyperparameters usually appear in tens of trials rather than thousands. 

import asyncio
from pathlib import Path
from kailash.db import ConnectionManager
from kailash_ml import HyperparameterSearch, ModelRegistry, TrainingPipeline
from kailash_ml.engines.hyperparameter_search import (
    ParamDistribution, SearchConfig, SearchSpace)
from kailash_ml.engines.training_pipeline import EvalSpec, ModelSpec
from shared.mlfp03.ex_7 import prepare_credit_frames, credit_feature_schema

# dev: everything selection may touch; test: used once, at the end
dev, test, feature_cols = prepare_credit_frames()
schema = credit_feature_schema(feature_cols)

space = SearchSpace(params=[
    ParamDistribution("n_estimators", "int_uniform", low=100, high=800),
    ParamDistribution("max_depth", "int_uniform", low=3, high=10),
    ParamDistribution("learning_rate", "log_uniform", low=0.01, high=0.3),
])
config = SearchConfig(strategy="bayesian", n_trials=20,
                      metric_to_optimize="auc", direction="maximize",
                      register_best=False)
base_spec = ModelSpec(model_class="lightgbm.LGBMClassifier",
                      framework="lightgbm",
                      hyperparameters={"random_state": 42, "verbose": -1})

# Absolute path: DataFlow-backed SQLite URLs must not be relative
DB_URL = f"sqlite:///{Path('mlfp03_registry.db').resolve()}"

async def run_search():
    conn = ConnectionManager(DB_URL)
    await conn.initialize()
    try:
        pipeline = TrainingPipeline(feature_store=None,
                                    registry=ModelRegistry(conn))
        search = HyperparameterSearch(pipeline=pipeline)
        return await search.search(
            data=dev, schema=schema, base_model_spec=base_spec,
            search_space=space, config=config,
            eval_spec=EvalSpec(metrics=["auc"], split_strategy="holdout",
                               test_size=0.2),   # trials score a dev holdout
            experiment_name="credit_hp_search")
    finally:
        await conn.close()

result = asyncio.run(run_search())
print(result.best_params, result.best_metrics["auc"])

Every trial is a real TrainingPipeline.train() call scored on the same seeded holdout of the dev frame, so the trials are compared fairly and the test frame never influences the choice. There is no built-in cross-validation in the search — if you want nested CV, you write the outer loop yourself. strategy also accepts "grid", "random" and "successive_halving".

ModelRegistry

⚙ Kailash Engine

ModelRegistry versions every model artefact, stores its metrics (MetricSpec) and I/O contract (ModelSignature), and tracks its stage. A newly registered version starts in staging; the stages are staging → shadow → production → archived, and promote_model moves a version between them with a recorded reason. 

import pickle
from kailash_ml.types import MetricSpec, ModelSignature

async def register_and_promote(model, test_auc, gate):
    conn = ConnectionManager(DB_URL)
    await conn.initialize()
    try:
        registry = ModelRegistry(conn)
        mv = await registry.register_model(
            "credit_scorer", pickle.dumps(model),
            metrics=[MetricSpec(name="auc_roc", value=test_auc, split="test")],
            signature=ModelSignature(
                input_schema=schema,
                output_columns=["default_probability"],
                output_dtypes=["float64"], model_type="classifier"))
        print(mv.version, mv.stage)            # e.g. 1 staging
        if gate["promote"]:                     # computed, never assumed
            await registry.promote_model(
                "credit_scorer", mv.version, "production",
                reason="AUC/AP gate passed on test")
        return await registry.get_model_versions("credit_scorer")
    finally:
        await conn.close()

There is no registry.register or registry.promote: the methods are register_model, promote_model, get_model(name, version) / get_model(name, stage="production") and get_model_versions. All are coroutines, so they run inside an async function, as here.

Common Mistakes

⚠ Mistake 1: Grid search when Bayesian is available

Grid search with 5 hyperparameters at 5 values each = 3,125 evaluations, most of them in regions that are obviously poor. A Bayesian search usually finds a comparable or better configuration in tens of trials — but compare strategies on the same validation rows, and report only once on the test set.

⚠ Mistake 2: Promoting without a signature

A model without a signature cannot validate its inputs in production. Always define input and output schemas.

⚠ Mistake 3: No conditional gate on promotion

Auto-promoting every model is dangerous. Always gate promotion on test metrics computed in the run — the gate node + SwitchNode pattern — and record the reason with promote_model.
