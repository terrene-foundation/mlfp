Lesson 1.6 Data Visualisation

A good chart answers a question faster than the best table in the world. A bad chart misleads its reader in seconds. Today you learn the six chart types that cover most of the questions a data analyst is asked, the Gestalt principles of visual perception that govern which shapes the eye groups together, the cardinal rules of truthful charts, and the ModelVisualizer engine that turns a Polars DataFrame into an interactive Plotly figure in one line.

Why This Matters

Every analysis has two audiences. The first is you — you are looking for patterns in the data. The second is the decision-maker you are writing the report for. For the first, a dense table works fine. For the second, a chart is usually the only thing they will actually read. The gap between the two audiences is the reason visualisation skill is a career-long differentiator.

Charts communicate by exploiting the human visual system. A reader's eye processes position, length, colour, and shape before any conscious thought. The Gestalt psychologists (Wertheimer, Koffka, Köhler, 1920s) catalogued the rules by which the eye groups shapes together. Those rules govern whether your chart communicates or confuses.

Core Concepts

The purpose of every chart

Before you pick a chart type, ask yourself one question: what decision should the reader make after seeing this? The chart exists to answer one question — not three, not ten. If you cannot state the question in a single sentence, the chart is not ready.

🟢 Single-question rule

Every chart should have exactly one question it answers. "Which town grew fastest last year?" is a question. "All the important patterns in the HDB market" is not. If your chart is trying to answer everything it will answer nothing.

Six chart types cover roughly 95% of the questions you will be asked. The rest (box plots, violin plots, sankey diagrams, maps) are specialist tools. Master the six and you can communicate almost anything; master the specialists when you actually need them.

Gestalt in practice

Six Gestalt principles matter for charts:

  • Proximity — elements close together appear grouped. Use spacing to separate clusters.
  • Similarity — elements with the same colour, shape, or size appear grouped. Use colour deliberately; random colour reads as random categories.
  • Closure — the eye completes partial shapes. You can suggest a trend line without drawing it.
  • Enclosure — a box around elements binds them tightly. Stronger than proximity.
  • Continuity — the eye follows smooth lines and curves. This is why line charts read as trends.
  • Connection — elements joined by a line read as related. Strongest grouping signal of all.

Visual order: the Z-pattern

Readers of left-to-right languages scan a page or dashboard in a rough "Z": across the top from left to right, diagonally down, then across the bottom. Put the most important element — the headline number or the chart that answers the main question — at the top left, and supporting detail lower and to the right. On a single chart the same logic applies: the title (top left) should state the takeaway, and the legend or annotation the eye needs next belongs along that path, not tucked into a far corner.

The attributes of a good chart

✅ Good chart

  • Answers one question
  • Truthful axes (0 baseline on bar, honest scale on line)
  • Direct labels instead of legends where possible
  • Colour used meaningfully
  • Text big enough to read at final size
  • No chartjunk (gratuitous gridlines, 3D, shadows)

❌ Bad chart

  • Tries to answer everything
  • Truncated y-axis exaggerates tiny differences
  • Legend forces eye saccades between chart and key
  • Colour is random or misleading
  • Text too small to read when embedded
  • 3D effects distort quantities

Charts to avoid

⚠ 3D charts

The 3D effect distorts the quantities. A reader cannot tell if the green bar is actually larger than the blue one because perspective shrinks the back bars. Never use 3D for quantitative communication.

⚠ Misleading pie charts

Pie charts ask the reader to compare angles — the single hardest perceptual task in charting. Five slices is the usable limit; ten slices is unreadable. Use a horizontal bar chart instead — position on a common axis is the easiest comparison for the human eye.

The Kailash Engine: ModelVisualizer

⚙ Kailash Engine

ModelVisualizer builds Plotly figures behind a consistent API for the chart types you use most often in EDA and model evaluation: histogram, scatter, box_plot, metric_comparison, training_history, and model-evaluation charts such as confusion_matrix and roc_curve. It accepts Polars DataFrames directly, returns Plotly Figure objects you can show inline (fig.show()), save as interactive HTML (fig.write_html(...)), or customise further with standard Plotly methods. Same engine in M1 EDA and in M5 model evaluation — consistent look and feel. 

from kailash_ml import ModelVisualizer

viz = ModelVisualizer()

fig = viz.histogram(
    data=hdb,
    column="resale_price",
    bins=40,
    title="HDB Resale Price Distribution",
)
fig.write_html("price_histogram.html")

The data-exploration methods follow the same shape: pass a DataFrame, pass the columns, pass a title, get back a Figure. For histogram and scatter the defaults work as-is. Methods built for model evaluation can be repurposed for EDA, but then you must set the axis titles yourself — the worked example shows how. For chart types the engine does not offer (heatmaps, stacked bars), use Plotly Express directly; it accepts Polars DataFrames.

Worked Example: Six Charts from the HDB Data

📝 Goal

Produce six charts that together describe the course's HDB prices: distribution, price vs area, price by town, price trend over time, correlation heatmap, and flat-type composition by town — plus a 100% stacked variant of the last one. Remember the data is synthetic: the charts show you how it was generated, not the real market.

Step 1.

Set up the visualiser and prepare the data.

import polars as pl
import plotly.express as px
from kailash_ml import ModelVisualizer
from shared import MLFPDataLoader

loader = MLFPDataLoader()
hdb = loader.load("mlfp01", "hdb_resale.parquet").with_columns(
    (pl.col("resale_price") / pl.col("floor_area_sqm")).alias("price_per_sqm"),
    pl.col("month").str.to_date("%Y-%m").alias("transaction_date"),
)

viz = ModelVisualizer()
Step 2 — Histogram.

Answering "how are prices distributed?". Bins = 40 gives enough resolution to see shape without over-fragmenting.

fig = viz.histogram(
    data=hdb,
    column="resale_price",
    bins=40,
    title="HDB Resale Price Distribution",
)
fig.write_html("ex6_price_histogram.html")

In the course data, 80% of sales fall between about S$538,000 and S$1,225,000, with a median of S$849,124. The tail is extreme: 144 records at S$9,000,000 pull the mean up to about S$881,800 and squash the histogram into a few bars until you filter them out. The 107 records at S$10 sit in the first bar. A histogram is the fastest way to spot both.

Step 3 — Scatter.

Answering "how does price relate to area?". Sample to 5,000 points — a scatter of 50,000 points is unreadable ink.

hdb_sample = hdb.sample(n=5_000, seed=42)
fig = viz.scatter(
    data=hdb_sample,
    x="floor_area_sqm",
    y="resale_price",
    title="HDB Resale Price vs Floor Area",
)
fig.write_html("ex6_price_vs_area.html")

Positive slope, wide vertical spread. On the full data the correlation is r = 0.47, so area alone explains only about 22% of price variance ($r^2 \approx 0.22$). Drop the 251 records at S$10 and S$9M and r jumps to about 0.91 — a handful of bad rows can hide a strong real relationship.

Step 4 — Bar.

Answering "which towns have the highest median price?". Aggregate first, then feed the named dict to metric_comparison. That method was built to compare model scores, so its default axis titles are "Model" and "Score" — set the real ones.

district_prices = (
    hdb.group_by("town")
    .agg(pl.col("resale_price").median().alias("median_price"))
    .sort("median_price", descending=True)
)

price_by_town = {
    town: {"Median Price (S$)": price}
    for town, price in zip(
        district_prices["town"].to_list(),
        district_prices["median_price"].to_list(),
    )
}

fig = viz.metric_comparison(price_by_town)
fig.update_layout(xaxis_title="Town", yaxis_title="Median resale price (S$)")
fig.write_html("ex6_median_by_town.html")

# With 27 long town names, a horizontal bar reads better still
fig = px.bar(
    district_prices, x="median_price", y="town", orientation="h",
    title="Seven central towns lead on median price",
)
fig.update_layout(yaxis={"categoryorder": "total ascending"})
fig.write_html("ex6_median_by_town_h.html")
Step 5 — Line chart.

Answering "how has price per sqm changed over time?". Aggregate to monthly first.

monthly = (
    hdb.group_by("transaction_date")
    .agg(pl.col("price_per_sqm").median().alias("median_psm"))
    .sort("transaction_date")
)

fig = viz.training_history(
    {"median_price_sqm": monthly["median_psm"].to_list()},
    x_label="Month", y_label="Median price per sqm (S$)",
)
# training_history plots against 1..N — put the real dates on the x-axis
fig.update_traces(x=monthly["transaction_date"].to_list())
fig.write_html("ex6_price_trend.html")

training_history was designed for ML training curves, so it assumes the x-axis is epochs 1, 2, 3, … and labels it "Epoch" unless told otherwise. Repurposing it is fine, but only if you fix the axis: the two extra lines give the chart real dates and real labels ("no misleading axes"). The line itself is flat — the monthly median stays between about S$8,656 and S$8,968 per sqm for ten years. No trend is a legitimate answer.

Step 6 — Heatmap.

Answering "how do numeric features correlate?". Compute the matrix with Polars, draw it with px.imshow.

numeric = hdb.select("resale_price", "floor_area_sqm", "price_per_sqm")
corr = numeric.corr()   # Polars correlation matrix

fig = px.imshow(
    corr.to_numpy(), x=corr.columns, y=corr.columns,
    text_auto=".2f", color_continuous_scale="RdBu_r",
    zmin=-1, zmax=1, title="HDB Feature Correlations",
)
fig.write_html("ex6_correlation.html")

With RdBu_r pinned to −1…+1, red means positive, blue means negative and white is zero. Price and price per sqm correlate at 0.82, price and area at 0.47, and area and price per sqm at about −0.01. Do not use ModelVisualizer.confusion_matrix for this: it takes true and predicted labels and computes a confusion matrix from them; it cannot draw an arbitrary grid.

Step 7 — Stacked bar.

Answering "how does flat-type composition vary across towns?".

composition = (
    hdb.group_by("town", "flat_type")
    .agg(pl.len().alias("count"))
    .sort("town", "flat_type")
)
# Plotly Express takes the Polars DataFrame directly — no pandas needed
fig = px.bar(
    composition,
    x="town", y="count", color="flat_type",
    title="HDB Flat Type Composition by Town",
)
fig.write_html("ex6_composition.html")
Step 8 — 100% stacked bar.

Answering "what share of each town's sales is each flat type?". Raw counts make big towns look different just because they are big; converting to shares puts every town on the same 0–100% scale. This is the standard chart for survey and Likert data ("strongly disagree … strongly agree"), where each bar is one question and the segments are the answer shares.

shares = composition.with_columns(
    (pl.col("count") / pl.col("count").sum().over("town") * 100)
    .alias("share_pct")
)

fig = px.bar(
    shares,
    x="share_pct", y="town", color="flat_type", orientation="h",
    title="Every town's sales are about 40% 4-room flats",
)
fig.update_layout(xaxis_title="Share of town's sales (%)")
fig.write_html("ex6_composition_pct.html")

Each bar now sums to exactly 100%. The 4-room share ranges only from about 38% to 44% across the 27 towns — the composition is nearly identical everywhere, which the raw-count chart hid behind different bar heights.

Mathematical Foundations: Perception Accuracy

William Cleveland and Robert McGill (1984) ranked the perceptual tasks used in charts by accuracy. Their finding is the empirical foundation of modern chart design:

The practical rule: for quantitative comparisons, prefer charts that use position on a common scale (bar charts, dot plots, scatter plots). Avoid charts that rely on angle (pie charts) or area (bubble charts) when accurate comparison matters. Colour is the least reliable quantitative channel — use it for categories, not for magnitudes.

Common Mistakes

⚠ Mistake 1: Too many points on a scatter

50,000 points on a scatter is a grey blob — you cannot see individual observations or the relationship. Sample down to 2,000–10,000 points for scatter, or switch to a 2D histogram / hexbin for density.

⚠ Mistake 2: Truncated y-axis on bar charts

If your bars start at 400 instead of 0, a 5% difference looks like a 50% difference. Bar charts must start at zero — the length of the bar encodes the value. Line charts may start at non-zero if you are emphasising change, but always label the axis clearly.

⚠ Mistake 3: Random colour choices

A chart with ten bars in ten random colours reads as chaos. Either use a single colour for non-categorical data, a sequential palette for ordered categories, or a diverging palette for values with a meaningful middle. Random rainbow palettes break the similarity principle.

⚠ Mistake 4: Title as header instead of takeaway

"HDB resale prices" is a label, not a takeaway. "Seven central towns sell for roughly 15% more than the rest" is a takeaway (and on the course data, a true one). Use chart titles to state the conclusion, not the topic.

Reflection

Visualisation is a design discipline as much as a technical one. The six chart types you met today cover almost every question you will be asked. The Gestalt principles tell you why one choice reads better than another. The Cleveland–McGill ranking tells you which perceptual task to pick for the comparison you want the reader to make. ModelVisualizer gives you the tools without the boilerplate.

The biggest habit you take away today: every chart answers one question. State the question before you build the chart. If you cannot, the chart is not ready. If you can, your chart-type choice follows automatically.
