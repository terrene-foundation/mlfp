Lesson 1.4 Joins and Multi-Table Data

Real questions almost never fit in a single table. "Do towns with more MRT stations, or towns nearer the city centre, sell for more?" requires an HDB table and an MRT table, joined on a shared key. Today you learn how to combine datasets with join, when to use left versus inner versus outer joins, and how to handle the nulls that appear when one side has no match. You also meet Python's if/elif/else statement and the import keyword — the final pieces needed to write multi-file programs.

Why This Matters

Every real analytics question is a join question waiting to happen. The HDB price you computed in Lesson 1.3 is a single number; the context that makes it meaningful lives in other tables: MRT proximity, school density, nearby amenities, historical cooling measures, household income for the postcode. Each of those data sources arrives as its own CSV or parquet file. Your job is to line them up by a shared key — usually a town name, a postal code, a date — and pull the relevant columns across.

Core Concepts

Imports and packages

Before we can join anything, a word about the tools. The import keyword tells Python to load a package and make its contents available. You have already used import polars as pl and from shared import MLFPDataLoader. Two forms, same idea: 

import polars as pl              # load whole package, call it pl
from shared import MLFPDataLoader  # load one name from a package

The as clause is an alias — a short nickname. The Polars convention is pl. When you type pl.col(...) you are saying "the col function inside the Polars package".

🟢 Foundations

A package is just a folder of Python files that someone has published so you can reuse their code. PyPI (the Python Package Index) hosts hundreds of thousands. You install packages with pip install <name>; you use them with import <name>. That two-step — install once, import whenever — is how every non-trivial Python program is built.

if / elif / else: code-level decisions

Lesson 1.2 introduced pl.when / then / otherwise for choosing values inside a column. Python also has an if statement for choosing what to do at the code level. The two are not interchangeable: pl.when operates on whole columns; if operates on whole program paths. 

def price_range_label(price: float) -> str:
    """Classify a resale price into a human-readable tier."""
    if price < 350_000:
        return "Budget"
    elif price < 500_000:
        return "Mid-range"
    elif price < 700_000:
        return "Premium"
    else:
        return "Luxury"

Read it: if the price is below 350k return "Budget". Otherwise, if it is below 500k return "Mid-range". Otherwise, if below 700k return "Premium". Otherwise return "Luxury". Python checks each condition in order and stops at the first one that is True.

Joins: the core vocabulary

A join combines two tables by matching rows on a shared key. Suppose the HDB table has a column town and the MRT table also has a column town. A join on that key lines up rows where the two town values are equal and produces a new table with columns from both sides. 

# one row per town, key in the same case as HDB ("BISHAN")
mrt_by_town = (
    mrt_stations.with_columns(pl.col("town").str.to_uppercase())
    .group_by("town").agg(pl.len().alias("station_count"))
)

hdb_enriched = hdb.join(mrt_by_town, on="town", how="left")
print(hdb_enriched.shape)   # (50150, 12): every HDB row kept

Four things to notice: the left-hand DataFrame (hdb) calls .join; the right-hand DataFrame is the first argument; the on parameter names the shared key; the how parameter chooses which kind of join. The two preparation steps on the right-hand side — upper-casing the town and collapsing to one row per town — exist because the raw tables disagree. The worked example shows what goes wrong without them.

Handling nulls after a join

A left join keeps every row from the left table. For rows where the right table has no matching key, the new columns are filled with null. You almost always need to decide what to do with those nulls. 

# Count unmatched rows
n_null = hdb_enriched["station_count"].null_count()
print(f"HDB rows with no MRT data: {n_null:,}")   # → 11,032

# Fill with a sentinel (0, -1, "Unknown") — only if it is TRUE
hdb_filled = hdb_enriched.with_columns(
    pl.col("station_count").fill_null(0),
)

# Or drop the unmatched rows entirely
hdb_matched = hdb_enriched.filter(pl.col("station_count").is_not_null())

Which choice is correct depends on the question. If you are counting stations and "no match" really does mean "zero stations", fill with 0. If "no match" means "data missing" — and here it does: Hougang, Sengkang and Punggol have MRT stations in reality, they are simply absent from this station table — then filling with 0 would be a lie, so drop or keep the null. Never silently let nulls propagate into calculations without deciding.

🔵 Theory: Cardinality of joins

A join is one-to-one, one-to-many, or many-to-many depending on how unique the key is in each table. HDB has many rows per town. The raw MRT table also has many rows per town — it is one row per station, up to 17 stations in a town. Joined directly (after fixing the case), every HDB sale is repeated once per station in its town: 50,150 rows become 186,997. Only after collapsing MRT to one row per town (mrt_by_town) is the key unique on the right, the join many-to-one, and the output row count equal to HDB's. Always check key uniqueness on both sides before joining — df["town"].is_duplicated().any() answers it in one line.

Worked Example: Enriching HDB with Town Context

📝 Goal

Combine the HDB resale data with MRT station counts, a town position and school counts, measure each town's distance to the CBD, then produce a district summary that labels towns with a "desirability" tier computed by an if/elif/else function.

A word on what the MRT table can and cannot tell you. It has one row per station (name, town, line, latitude, longitude). Its distance_to_mrt_km column is the gap between that station and its neighbouring station — not the distance from anyone's flat to the MRT. The HDB table has no flat coordinates at all, so a true "distance from this flat to the nearest station" cannot be computed here. What we can compute honestly is town-level context: how many stations a town has, where its stations are centred, and how far that centre is from the CBD.

Zero raw matches: HDB stores "BISHAN", the MRT table stores "Bishan". A raw left join would still return 50,150 rows — so the row count looks healthy — while every MRT column is null. Step 3.

Collapse MRT to one row per town, then left-join it onto HDB. The town's position is the centre (mean latitude and longitude) of its stations.

mrt_by_town = (
    mrt_stations
    .with_columns(pl.col("town").str.to_uppercase())
    .group_by("town")
    .agg(
        pl.len().alias("station_count"),
        pl.col("latitude").mean().alias("town_lat"),
        pl.col("longitude").mean().alias("town_lng"),
    )
)

hdb_enriched = hdb.join(mrt_by_town, on="town", how="left")

print(f"Rows after MRT join: {hdb_enriched.height:,}")
print(f"Rows with no MRT match: {hdb_enriched['station_count'].null_count():,}")
Rows after MRT join: 50,150
Rows with no MRT match: 11,032

Why collapse first? The station table has up to 17 rows per town. Joining it directly (case fixed, not aggregated) repeats every sale once per station in its town and produces 186,997 rows — the many-to-many explosion from the Theory box above.

Step 4.

Schools is one row per school, so we aggregate to one row per town (fixing the case the same way) before joining.

school_counts = (
    schools
    .with_columns(pl.col("town").str.to_uppercase())
    .group_by("town")
    .agg(pl.col("school_name").count().alias("school_count"))
)

hdb_enriched = hdb_enriched.join(
    school_counts,
    on="town",
    how="left",
).with_columns(
    pl.col("school_count").fill_null(0),  # no match → zero schools
)
print(hdb_enriched.shape)   # (50150, 15)

The .fill_null(0) step matters: without it, unmatched towns would carry null, and arithmetic with nulls produces more nulls. But be honest about what the 0 means. Three HDB towns get 0 — Boon Lay, Central Area and Kallang/Whampoa — and at least one of them is a naming mismatch rather than a true zero: the schools table spells that town "Kallang". A fill value is a claim about the world; check it before you make it.

Step 5.

Two helper functions: the great-circle (haversine) distance between two latitude/longitude points, and a desirability classifier built with if / elif / else.

def haversine_km(lat1: float, lon1: float, lat2: float, lon2: float) -> float:
    """Great-circle distance between two points, in kilometres."""
    R = 6371.0  # Earth radius in km
    dlat = math.radians(lat2 - lat1)
    dlon = math.radians(lon2 - lon1)
    a = (math.sin(dlat / 2) ** 2
         + math.cos(math.radians(lat1)) * math.cos(math.radians(lat2))
         * math.sin(dlon / 2) ** 2)
    return 2 * R * math.asin(math.sqrt(a))


def desirability_tier(stations, schools: int) -> str:
    """Classify a town into a desirability tier."""
    if stations is None:
        return "Unknown"           # town not in the MRT table
    if stations >= 4 and schools >= 10:
        return "Prime"
    elif stations >= 4:
        return "Good MRT access"
    elif schools >= 10:
        return "School-rich"
    else:
        return "Fewer amenities"
Step 6.

Aggregate to town level and apply both functions using map_elements. Raffles Place (1.2830, 103.8513) stands in for the CBD.

CBD_LAT, CBD_LNG = 1.2830, 103.8513

district_summary = (
    hdb_enriched.group_by("town")
    .agg(
        pl.col("resale_price").median().alias("median_price"),
        pl.col("station_count").first().alias("stations"),
        pl.col("school_count").first().alias("schools"),
        pl.col("town_lat").first(),
        pl.col("town_lng").first(),
        pl.len().alias("transactions"),
    )
    .with_columns(
        pl.struct("town_lat", "town_lng")
        .map_elements(
            lambda r: None if r["town_lat"] is None
            else haversine_km(r["town_lat"], r["town_lng"], CBD_LAT, CBD_LNG),
            return_dtype=pl.Float64,
        )
        .alias("km_to_cbd"),
        pl.struct("stations", "schools")
        .map_elements(
            lambda r: desirability_tier(r["stations"], r["schools"]),
            return_dtype=pl.String,
        )
        .alias("tier"),
    )
    .drop("town_lat", "town_lng")
    .sort("median_price", descending=True)
)

print(district_summary.head(10))

Mathematical Foundations: Set Operations

Joins are a direct application of set theory. Treat each table's key column as a set. Let $H$ be the set of HDB towns and $M$ be the set of MRT towns.

$$H \cap M = \{t : t \in H \text{ and } t \in M\}$$
$\cap$ — intersection the towns present in both tables

An inner join keeps exactly the rows whose keys lie in $H \cap M$. A left join keeps all rows from $H$, attaching right-side columns when the key lies in $H \cap M$ and nulls otherwise. A full outer join keeps all rows from the union $H \cup M$.

The set difference $H \setminus M = \{t : t \in H, t \notin M\}$ tells you which HDB towns have no matching MRT row — exactly the six towns Step 2 of the worked example listed, and the 11,032 nulls Step 3 counted.

Common Mistakes

⚠ Mistake 1: Inner join when left was meant

You start with 50,150 HDB rows. You inner-join with mrt_by_town. You end with 39,118 rows. 11,032 transactions — every sale in six towns — silently disappeared because those towns have no MRT match. Left join preserves them; inner drops them. Always know which you wanted.

⚠ Mistake 2: Duplicate keys on both sides

If both sides have many rows per key, the join produces a Cartesian product of matches. 5 HDB rows × 5 MRT rows for the same town → 25 output rows instead of 5. On the course data the unaggregated MRT join turns 50,150 rows into 186,997. Aggregate one side to one-row-per-key before joining (as we did with mrt_by_town and school_counts).

⚠ Mistake 3: Ignoring nulls after a join

Left joins produce nulls for unmatched rows. Arithmetic with nulls propagates nulls (null + 5 = null). If you do not fill or drop those nulls, downstream aggregations silently become nulls and you lose data without noticing.

⚠ Mistake 4: Mismatched key types or cases

Joining "BISHAN" with "Bishan" produces zero matches — the strings are not equal. On the course data a raw HDB–MRT left join still returns 50,150 rows, so the row count looks fine while every new column is null. Before joining, normalise both sides with str.to_uppercase() or str.strip_chars(), then check the overlap. Case is not the only trap: the schools table says "Kallang" where HDB says "KALLANG/WHAMPOA".

Reflection

Today you learned the vocabulary of multi-table work: import to load libraries, if/elif/else for code-level branching, and join to combine DataFrames by key. You built a concrete enrichment pipeline: start with HDB transactions, attach MRT station counts and a town position, attach school counts, measure distance to the CBD, and produce a ranked district summary with a Python-function classifier.

The most important habit is the key check before every join — count the unique keys on each side, compute the intersection, decide what to do with the difference. A join without that check is how analysts silently lose eleven thousand rows — or join on keys that never match — and ship a broken report.
